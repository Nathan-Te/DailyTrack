# Circuit du Jour — carte du dépôt et règles communes

Monorepo de jeux web quotidiens (un niveau par jour, identique pour tous, classement validé par rediffusion). Réponses et docs en français. Visions (**ne pas modifier**, c'est Nathan qui le fait) : `docs/seed.md` (DailyTrack), `docs/jump/seed-dailyjump.md` (DailyJump), `docs/plateforme/seed-phase-2.md` et `seed-phase-3.md` (plateforme), et la charte visuelle `docs/plateforme/identite.md` (phase 3).

**Ce fichier est court exprès.** Les consignes détaillées vivent dans le `CLAUDE.md` de chaque zone : Claude Code charge ceux des sous-dossiers **à la demande**, dès qu'on lit ou modifie un fichier du dossier (`docs/plateforme/lots/lot-R2-hygiene.md` cite la doc). **Avant de travailler dans une zone, lis son `CLAUDE.md`** s'il n'a pas été chargé (par exemple `cat apps/jump/CLAUDE.md`).

## Règles communes à tous les lots
- **Un lot = une session = une branche = une PR brouillon.** L'agent s'arrête quand les critères d'arrêt du lot sont verts.
- **Rapport honnête** : ce qui est vérifié, ce qui ne l'est pas, les décisions laissées à Nathan ; un échec se dit avec sa sortie, une étape sautée aussi.
- **Tests jamais affaiblis** : ni désactivés, ni sautés, ni seuil relâché sans mesure, ni commit vide pour être vert (détail dans « Tests et CI » ci-dessous). Sauter une suite *non concernée* par une PR (filtre de CI par chemin) n'est pas l'affaiblir ; le run de nuit lance tout.
- **Zones partagées** (liste ci-dessus) : un seul propriétaire à la fois ; un lot n'en modifie une que si son prompt le dit. Les golden de chaque jeu ne bougent que si le lot le décide.
- **Mentions légales et confidentialité (lot R5 ; lot I6 : aussi en anglais)** : la page `playdujour.com/mentions-legales/` (`apps/portail/mentions-legales/index.html`, **elle fait foi**) et sa traduction fidèle `playdujour.com/legal/` (`apps/portail/legal/index.html`), liées depuis le pied du portail, la pause et les Réglages des deux jeux — **celle de la langue choisie** (`cheminMentions` de `@cdj/ui`) — **disent exactement ce que le code fait**. **Règle de fidélité** : toute nouvelle donnée gardée (table, colonne, stockage du navigateur, traceur, service tiers) ou durée changée met à jour **les deux pages** dans le même lot ; une durée ou un nombre tiré du code y porte `data-constante` / `data-valeur`, et `apps/portail/test/mentions.test.ts` vérifie les constantes, que chaque table de la base y est décrite, et que l'anglaise a les mêmes constantes, rubriques et tables que la française. Effacement d'un joueur : `docs/plateforme/effacement.md`. Publicité, traceur ou cookie tiers = bandeau de consentement et relecture juridique d'abord.
- **Recette avant production** : rien ne part en production sans passer par la recette et la validation de Nathan ; depuis le lot R4 la production part **par le bouton « Mettre en production »**, jamais à la fusion ; un agent ne valide, ne relance et ne crée ni ressource ni secret (`apps/api/CLAUDE.md`, « Recette (lot R1) » ; ce fichier, « Adresses et mise en production »).
- **Toute interface hors partie suit la charte `docs/plateforme/identite.md`** (direction « Cartouches », phase 3) et passe par le socle `@cdj/ui` : jetons, composants, catalogues `fr` + `en` (aucune chaîne ni couleur en dur) ; consignes : `packages/ui/CLAUDE.md`. Les jeux y sont passés aux lots I4 (Track) et I5 (Jump).
- **Lot I6 — pages, budgets, traductions** : **toute nouvelle page a ses balises de partage** (titre, description, Open Graph avec une image de la charte produite à la construction, `twitter:card` : modèle dans `apps/portail/index.html`, test `apps/portail/test/apercus.test.ts`) **et passe axe** (aucune violation « serious » ni « critical » : `apps/web/e2e/axe.ts`, `auditAxe`) ; un écran en surimpression est un dialogue nommé dont le focus entre et revient (`suivreDialogue` de `@cdj/ui`). **`docs/plateforme/budgets.md` est la référence des budgets** (un poids changé = la ligne remesurée : `node scripts/budgets.mjs`). **`npm run traductions` après tout changement de catalogue** (il réécrit `docs/plateforme/traductions.md`, que Nathan relit ; un test échoue s'il n'est pas à jour) ; une clé de catalogue jamais lue est refusée (`packages/ui/test/clesUtilisees.test.ts`).
- Un **nouveau paramètre d'adresse** rejoint la page d'admin / `urlOptions.ts` du jeu ; **tout texte en français** (le portail ; les jeux depuis I4 / I5 : français **et** anglais par les catalogues) ; un nouveau spec e2e s'ajoute à `durees.json` de son jeu.

- **Flux** : PR (CI de PR) → **aperçu** (`apercu.yml`, ou `recette.yml` si la PR touche le serveur) → fusion → **recette** (`recette.yml` sur `main` : serveur, `recette:seed`, site) → bouton **« Mettre en production »** (`production.yml`, à la main, sur un commit de `main`) → production. **Plus aucun déploiement automatique de la production.** Le bouton : refus sans CI complète verte → **figer** → serveur (validation de Nathan, environnement `production`) puis site → `smoke --lecture-seule` contre playdujour.com → étiquette `prod-AAAA-MM-JJ-HHMM` → PR des jours figés → résumé (PR et commits depuis la dernière mise en production). Lot R5 : plus de redirection depuis GitHub Pages (`pages.yml` retiré).
- **Figer avec le code en production avant chaque mise en production** : `freeze:days -- demain` lancé **sur le commit de la dernière étiquette `prod-…`** (le code que les joueurs ont), jamais sur le commit qu'on déploie ; les fichiers figés entrent dans l'image du serveur, le site **et** le dépôt (PR « robot », fusionnée automatiquement avec `ROBOT_TOKEN`). Un jour figé ne change jamais : un fichier différent arrête la mise en production.
- **Retour arrière** : `retour-arriere.yml` (à la main, validation de Nathan) : l'image et la version du site notées dans l'étiquette précédente, puis vérification, puis une nouvelle étiquette sur le commit remis.
- **Stockage** : production, recette et chaque aperçu sont des **origines distinctes** : le navigateur sépare leur stockage (plus de préfixe `apercu:` dans les déploiements). Les jeux appellent `/api/` sur leur propre origine (`VITE_API_URL=/`) ; les liens partagés sont construits sur l'origine courante.
- Sans Firebase configuré, toute étape Firebase est sautée avec « Firebase non configuré : voir docs/plateforme/domaine.md » et la CI reste verte. Un agent ne lance ni le bouton ni le retour arrière (403) : il prépare, Nathan clique.

## Tests et CI (retouche 29b, lot R3) — rouge = vrai problème
- **CI** (`.github/workflows/ci.yml`) : jobs `unit` (Vitest en 3 parts, typecheck et build dans la 1ʳᵉ) et **`test`** (leur verdict) ; job `scope` (portée et **mode**) ; job `e2e-parts` = **matrice** navigateur × **part** (DailyTrack : Chromium en 8 parts composées par durée, un test à la fois, Firefox et WebKit en 2 ; DailyJump : Chromium en 3, Firefox et WebKit en 1) ; job **`e2e`** = **verdict unique** qui fusionne les rapports « blob », écrit le résumé du run et échoue au moindre vrai échec ; job `api-image`. Protection de `main` : statuts `test` et `e2e` obligatoires (réglage GitHub de Nathan, `docs/lots/lot-29b-ci-fiable.md`) ; ils tournent toujours (`if: always()`).
- **Ce qui tourne (lot R3, `docs/plateforme/lots/lot-R3-ci.md`)** — **sur une PR** (mode `pr`) : tous les tests unitaires ; les e2e des **jeux touchés** (`scripts/ci-scope.mjs` : dans `apps/api`, `jump*.ts` → DailyJump, `cdj.ts`/`salon.ts`… → DailyTrack, le cœur et tout doute → tout) **sur Chromium**, plus le **sous-ensemble multi-navigateurs** sur Firefox et WebKit ; **sur `main` (chaque fusion, mode `complet`), la nuit (03 h 17 UTC, mode `nuit`) et à la demande** (« Run workflow » pour Nathan ; pour un agent, à qui il est refusé, un commit de PR dont le message contient `[ci complet]`) : tout, trois navigateurs, sans filtre. Un `push` sur une autre branche ne lance plus rien (la PR le fait). Objectif : moins de 6 min du push au verdict pour une PR DailyJump.
- **Sous-ensemble multi-navigateurs** : `apps/web/e2e/multi-navigateurs.json` et `apps/jump/e2e/multi-navigateurs.json` — les specs dont le sens est la comparaison entre navigateurs (rejeu identique Node ↔ navigateurs, déterminisme), chacun avec sa raison ; testé (`apps/web/test/multiNavigateurs.test.ts`). **Un nouveau test de comparaison entre navigateurs rejoint la liste de son jeu.**
- **La production exige la CI complète** : `production.yml` (« Mettre en production », lot R4) commence par vérifier (`scripts/ci-complete.mjs`) qui attend le run `push` de `main` du commit et refuse de déployer s'il n'est pas vert (résumé avec la raison et le lien) ; la validation et la production en dépendent (la recette, elle, suit chaque fusion) : **une validation de Nathan ne contourne jamais ce refus**.
- **Quarantaine (le filet, pas la règle)** : `e2e/quarantaine.json` (`scripts/e2e-quarantaine.mjs`, testé). Une entrée = le test (nom du résumé : `web/e2e/<fichier> › <titre>`), le navigateur, la date d'entrée, **le lien vers sa dette** (`docs/orchestration.md` § 8 pour DailyTrack, `docs/jump/synthese.md` pour DailyJump, où le test est déjà nommé) et qui doit le réparer. Sur une PR, le test **tourne toujours** mais son échec n'est qu'un avertissement du résumé ; **sur `main`, la nuit et avant la production il reste bloquant**. Garde-fous : entrée sans dette (ou incomplète) refusée, **au plus 3 entrées**, une entrée de **plus de 14 jours fait échouer le run de nuit** (« dette expirée »). Une quarantaine refusée fait échouer le run (et `npm test`). Entrer en quarantaine se décide avec Nathan ; on n'y met pas un test de sa propre zone.
- **Règle d'arrêt des agents** : (1) **un échec dans une zone que le lot ne touche pas** : relancer une fois (nouveau commit ou demande à Nathan : un agent ne relance pas un workflow, 403) ; s'il échoue encore, le noter dans le README du lot (test, run, message) et **s'arrêter** : on ne corrige pas, on ne s'acharne pas, Nathan tranche ; (2) **un échec dans sa propre zone** : un vrai problème, à corriger ; (3) **critère d'arrêt d'un lot : la CI de sa PR est verte**. La CI complète de `main` est vérifiée à la fusion et avant la production.
- **Preuve de stabilité** : `e2e/stabilite.json` + `.github/workflows/stabilite.yml` rejouent un test N fois de suite (`--repeat-each`, `--retries=0`) sur son navigateur et le runner de la CI ; un lot qui répare un instable y ajoute sa ligne et donne le run.
- **Une relance, signalée** : `retries: 1` **en CI seulement** (`playwright.config.ts`). Un test qui échoue puis réussit est **« instable »** : nommé dans le résumé du run (`scripts/e2e-summary.mjs`) et annoté `::warning`, **jamais caché** ; au run de nuit un instable fait échouer le job. Un instable est une dette à corriger (avant tout, la cause : attente sur une durée, fil principal saturé, horloge, page encore en construction…), suivie dans `docs/orchestration.md` § 8 ; on ne relance jamais « pour voir si ça passe ». La trace de tout essai raté est gardée (artefact `resultats-*`).
- **Horloge maîtrisée** : aucun test ne dépend de l'heure réelle ni ne change de jour en route. `e2e/fixtures.ts` (`test`, `newClockedContext`, `TODAY`, `FIXED_NOW`, `clockNow`) décale `Date` des pages ; `playwright.config.ts` fixe le décalage une fois (midi UTC le 20/10/2026) et le donne aux serveurs de test (`TEST_CLOCK_OFFSET_MS`, **refusée en production** par `config.ts`, signalée par `/api/health`). **Un spec qui calcule « aujourd'hui » importe `test` de `./fixtures` et utilise `TODAY`**, jamais `Date.now()` ni `new Date()`. **Pas `page.clock.install`** : il remplace `requestAnimationFrame` par un minuteur de 16 ms qui ignore le rendu logiciel et affame le fil principal (mesuré : 34 images/s simulées contre 3,5 réelles).
- **Écrire un test stable** : attendre un **état** (`__cdj.phase`, `waitForFunction`, événements), pas une durée (`waitForTimeout` n'est admis que pour « rien ne doit changer pendant N ms ») ; pas à pas (`__cdj.manual` + `advance`) plutôt que temps réel dès qu'un résultat dépend du nombre d'images ; **un serveur de test par spec** quand elle compte des présents ou des sessions (8787 classement, 8788 Salon de `salon-serveur`, 8789 `watch-serveur`, 8790 `profil`) ; une mesure de cadence se fait sur l'horloge de la page et sur plusieurs secondes ; une capacité absente (WebGL) se teste par `hasWebGL(page)` avec `test.skip` motivé, jamais par le nom du navigateur seul.
- **Parts Chromium et contextes (retouche 31b, `docs/lots/lot-31b-ci-verte.md`)** : les parts Chromium de la CI sont composées **par durée** (`scripts/e2e-parts.mjs` lit `apps/web/e2e/durees.json` ; **un nouveau spec = une ligne dans `durees.json`**, sinon `e2eParts.test.ts` échoue ; les durées par fichier sont dans le résumé du run) et tournent **un test à la fois** (`--workers=1` : sur 2 cœurs, deux pages en WebGL logiciel côte à côte vont deux à trois fois moins vite). Un contexte ouvert par `newClockedContext` / `newContextAt` est **fermé à la fin du test** (`fixtures.ts`) ; un spec en série qui garde ses appareils le dit avec `keepOpen` et les ferme lui-même ; un contexte ouvert par `browser.newContext()` se ferme dans le test (`try/finally`) — sinon ses pages dessinent pendant tous les tests suivants du worker. Un test qui crée des pseudos sur un serveur de test doit pouvoir être **relancé** (même base en mémoire) : pseudos propres à l'essai (`test.info().retry`). Une bascule ou une durée « à l'image près » se mesure **dans la page** (horloge du Salon, `requestAnimationFrame`), jamais à l'heure de retour d'un appel côté Node.
- **Interdits** : désactiver, sauter (`skip`, `fixme`), affaiblir un test (seuil relâché sans mesure, assertion retirée) ou pousser un commit vide pour être vert. Un test faux se corrige et le README du lot dit pourquoi. « Tous les tests verts » = la CI verte sur la PR.

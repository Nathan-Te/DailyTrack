# Circuit du Jour

Jeu web quotidien : un circuit court par jour, identique pour tous, classement validé par rediffusion. Source de vérité : `docs/seed.md` (ne pas modifier, c'est Nathan qui le fait). Réponses et docs en français.

## Structure
- `packages/sim` — simulation pure (physique, blocs, chrono, générateur, bot). **Aucune dépendance** au DOM, à Three.js ou à Node.
- `apps/web` — le jeu (Vite + Three.js) ; affiche ce que calcule `sim`.
- `apps/api` — classement (lot 5), planning, Salon ; importe le même `sim` pour rejouer les courses. En ligne : Cloud Run + Turso (lot 28, voir « Production »).
- `docs/lots/` — un README d'une page par lot.
- `docs/orchestration.md` — synthèse des lots, règles à ne pas casser, méthode et suite (pour l'agent orchestrateur).

## Plusieurs jeux dans ce dépôt
- **Jeux** : **DailyTrack** (ce fichier : `packages/sim`, `apps/web`, `apps/api`, `docs/seed.md`, `docs/lots/`) et **DailyJump** (`packages/jump-sim`, `apps/jump`, `docs/jump/` ; ses consignes sont dans `docs/jump/consignes.md`, importé en bas de ce fichier). Chaque jeu a sa simulation, son application, sa vision (seed) et ses README de lots ; ils ne s'importent jamais l'un l'autre.
- **Zones partagées** (un seul propriétaire à la fois, conflits à éviter) : `packages/core` (`@cdj/core`, socle sans logique de jeu) et `packages/clock` (jour de Paris), `package.json` et `package-lock.json` racine, `.github/workflows/`, la configuration Vitest / Playwright / TypeScript racine (`vitest.config.ts`, `tsconfig.base.json`, `tsconfig.json`), ce `CLAUDE.md` racine.
- **Règle : un lot ne modifie une zone partagée que si son prompt le dit.** Les consignes d'un jeu vivent dans le dossier de ce jeu, pas ici.
- **Règle : avant de déclarer le lot fini, rebaser sur `main` à jour (ou fusionner `main`) et obtenir une CI verte** sur le résultat. Conflit sur `package-lock.json` : ne pas le fusionner à la main, prendre celui de `main` puis relancer `npm install`, qui le régénère.

## Commandes
- `npm install` · `npm run dev` · `npm test` (Vitest) · `npm run typecheck` · `npm run build` · `npm run measure:generator` (durées, validation par thème, vitesse du pilote, coût d'un rejeu, bas-côtés et moments de choix par thème)
- Mise en ligne (lot 28) : `npm run smoke -- http://localhost:8080` (essai de bout en bout d'une API en marche : crée un joueur « Fumée », jamais contre la vraie base) · `npm run measure:budget` (budget d'un joueur sur Cloud Run + Turso, demande un `sqld` local : `docker run -p 8081:8080 ghcr.io/tursodatabase/libsql-server`) · `npx vitest run --project sqlite|libsql` (les tests d'API tournent sur les deux bases)
- Scénario du lot 21 : `?scenario=bas-cotes` (un virage par bas-côté, vibreurs, portion bosselée) ; captures par thème : `CAPTURES=1 npx playwright test captures` (dans `apps/web`).

## Circuits (lot 2)
- Un circuit = un texte de blocs (`parseTrack`, voir `packages/sim/src/track.ts`) : cellules de 32 m, repère canonique (p = gauche, q = avance) tourné par quarts de tour ; hauteurs enchaînées automatiquement.
- `trackWorld(track)` donne `sample` (hauteur/pente/plaque) et `collide` (rebords) à `stepCar` ; `createRace`/`stepRace` ajoutent portes, chrono et reprises. Les commandes enregistrables sont `{ steer, throttle, brake, respawn }`.
- Tests navigateur : `?debug` expose `window.__cdj`. Scénarios : `?scenario=essai|pilotage|surfaces|largeurs|vitesse|glace|relief|cuves|air|bas-cotes|figures|plat`.
- **Cuves (lot 18)** : `V` cuve droite, `ML` / `MR` mur latéral, `/c` sur un virage (`L2/c` : son mur extérieur) ; voir « Cuves (lot 18) ». **Les boucles restent exclues** (comme les tunnels fermés et les murs au plafond).

## Rediffusions (lot 3)
- Une rediffusion = `Replay` (séries de commandes) ; `encodeReplay`/`decodeReplay` ↔ texte base64url ; `replayRace` rejoue et renvoie le résultat recalculé. **Ne jamais faire confiance à un temps annoncé.**
- **`SIM_VERSION`** (constants.ts) : à incrémenter dès que la physique, un bloc ou un circuit change le résultat d'une course ; puis régénérer la rediffusion de référence : `UPDATE_GOLDEN=1 npx vitest run packages/sim/test/golden.test.ts`.
- `apps/web/src/session.ts` : `RunSession` avance course + enregistrement + fantôme ; `verify.html` : rejeu sans rendu pour les tests de navigateur (`npm run test:e2e`, Playwright ; `CHROMIUM_PATH` pour un Chromium déjà installé, `E2E_ALL_BROWSERS=1` pour Firefox et WebKit).

## Circuit du jour (lot 4)
- `dailyCircuit(jour)` (`generator.ts`) : graine = numéro de jour de la date (`parseDay`/`formatDay`, calendrier sans `Date` ; « aujourd'hui » = **la date à Paris**, voir « Jour de Paris (lot 31) ») ; `composeSpec` construit le texte, `bestPilotRun` (`autopilot.ts`) valide et donne le temps de l'auteur, d'où `medalsFor`. Id du circuit : `jour-AAAA-MM-JJ-g<GENERATOR_VERSION>` (variante 0) ; voir « Admin et planning ».
- **`GENERATOR_VERSION`** (constants.ts) : à incrémenter dès que le circuit d'une date change (règles, pilote, fenêtre de durée) ; puis régénérer `fixtures/daily-golden.json` (`UPDATE_GOLDEN=1 npx vitest run packages/sim/test/golden-daily.test.ts`).
- Web : `?mode=salon` (Salon, lot 26), `?seed=AAAA-MM-JJ` (ou `?day=`), `?theme=<nom>`, `?api=demo`, `?scenario=essai|pilotage|surfaces|largeurs|plat`, `?debug&tune` (réglages), touche **C** (caméra : proche, loin, capot ; lot 23). Palettes dans `apps/web/src/trackMesh.ts` (`PALETTE_DEFS`).
- **`npm run measure:generator`** (`apps/api/scripts/measure-generator.ts`) : durées d'auteur, largeurs, virages serrés, temps de génération et de rejeu sur 60 dates, taux de validation par thème (12 dates × 6 tentatives, thème forcé), bas-côtés et moments de choix par thème (lot 21). **Toute règle de générateur se valide par ce script (durées, taux de validation par thème), pas seulement par les tests.** `FAST=1` pour un passage rapide ; résultats de référence dans `docs/lots/lot-12-circuits-amples.md`.

## Classement (lot 5)
- `apps/api` : `createApi({ db, now })` (`src/api.ts`) ne dépend que de `Request`/`Response` et de `SqlDb` ; adaptateurs : Node (`server.ts`, Docker, Cloud Run) avec **Turso / libSQL** en production et SQLite en local, et Cloudflare Workers + D1 (`worker.ts`, non utilisé). **Le serveur ne fait jamais confiance à un temps annoncé** : il rejoue la rediffusion (`replayRace`) et enregistre son propre résultat.
- **Pseudos réservés (lot 30)** : **un pseudo appartient à son premier propriétaire, sur toute la base**. Clé d'unicité = `nameKey` (`pseudos.ts`) : NFD sans accents, minuscules, espaces réduits (« Nowy », « nowy » et « NÓWY » se confondent) ; colonne `players.name_key` + **index unique** `players_by_name_key` (SQLite et libSQL) ; vérifié avant le rejeu (bon marché) **et** garanti à l'écriture (`isUniqueViolation` → refus propre, jamais une 500). Même règle pour la première course (`submit`), `PUT /api/player` et le Salon : tout passe par `players.ts` (`resolveName` / `save`). Refus = `409 name_taken` + message « Ce pseudo est déjà utilisé. C'est le tien ? Charge ton code. » + `suggestions` libres (« Nowy2 », « Nowy_FR »…) ; le jeu montre ces pseudos à toucher et le bouton « Charger un code ». `GET /api/name?name=` répond seulement `{ available }` (+ suggestions libres si pris), limité à 40 par adresse et fenêtre ; **aucune liste de pseudos n'est exposée**. Pseudos refusés : mots interdits et noms réservés (`FORBIDDEN_WORDS`, `RESERVED_NAMES` dans `pseudos.ts`, liste courte et modifiable ; mot de 6 lettres ou plus refusé n'importe où, plus court seulement en mot entier : pas de faux positif sur « Technique »). Le changement de pseudo passe par le débit limité existant.
- **Migration des doublons** (`migratePseudos`, appelée par `ensureSchemaOn` : une seule fois par changement de schéma, au premier démarrage après le déploiement) : le joueur le plus **ancien** (`created_at`, première course) garde le pseudo, les autres reçoivent un suffixe provisoire (« Nowy·2 », `provisionalName`) et `rename_required = 1` ; **aucun temps n'est touché** ; rapport gardé dans `meta` (`pseudo_migration`). Le jeu leur propose, à leur prochaine visite, de choisir un nouveau pseudo ou de charger leur code. `npm run pseudos:migrate` (essai à blanc) / `-- --apply` : même fonction, avec le rapport, contre Turso (`TURSO_DATABASE_URL`/`TURSO_AUTH_TOKEN`) ou SQLite (`DB_PATH`) ; rattrape un joueur créé par l'ancienne révision pendant la bascule. Le suffixe d'affichage `disambiguateNames` (`Nom·2`) ne sert plus qu'aux données d'avant (démo) ; les comptes migrés portent leur suffixe dans leur pseudo.
- **« Aujourd'hui » = la date à Paris, grâce de 10 min après minuit de Paris** (lot 31 ; **remplace la règle « jour UTC »**) : seul le jour courant accepte des temps, puis le jour d'avant pendant 10 min ; un jour passé est figé. Voir « Jour de Paris (lot 31) ».
- Le client est dans `apps/web/src/{api,identity,online,profileSync}.ts` ; adresse de l'API : `?api=` ou `VITE_API_URL`. Sans elle, aucun classement.
- Tests : `apps/api/test` (SQLite en mémoire, horloge injectée) ; e2e `leaderboard.spec.ts` (Playwright lance le vrai serveur : `npm run test:e2e` construit aussi `apps/api`). Outils `?debug` : `timescale=N`, `__cdj.autoplay(code)`.
- Le Worker ne tient pas dans les 10 ms de calcul de l'offre gratuite de Cloudflare (voir docs/lots/lot-5-classement.md).

## Conduite (lot 7)
- `packages/sim/src/car.ts` : modèle **bicyclette** (deux essieux, force latérale saturée par `tireCurve`) + **4 ressorts** posés sur `world` (hauteur, tangage, roulis en pentes ; charge → adhérence ; butée) + **balistique** en l'air (voir « Air » ci-dessous). 2 sous-pas fixes par pas. Rebords : deux disques, impulsion avec rebond et frottement. Dérapage au frein (`car.drift`). Détail et mesures : `docs/lots/lot-7-conduite.md`.
- **`CarParams`** (`DEFAULT_CAR_PARAMS`) passé à `stepCar(car, input, world, params)` et `createRace(track, params)` ; le serveur et les rediffusions utilisent toujours les défauts. **`SurfaceParams`** `{ grip, traction, rolling }` lu sous chaque roue par `surfaceAt(échantillon)` (`world.ts`, table `SURFACES`, « route » seulement).
- Reprise = état de la voiture au passage du dernier point de contrôle (`race.checkpoints`). Virage large `L2`/`R2` (2 × 2 cellules, `blockCells`).
- Pilote (`autopilot.ts`) : trajectoire lissée (`racingLine`), vitesses par courbure, freinage anticipé ; `PILOT_GRIPS`.
- **Contact par la normale (lot 18)** : dans un bloc de cuve la voiture quitte le modèle à ressorts : `stepCar` appelle `world.shell(x, z, y, hit)` et, s'il répond, `substepShell` (car.ts) — voir « Cuves (lot 18) ».
- Web : panneau `?debug&tune` (`apps/web/src/tune.ts`) — une course avec réglages modifiés n'est **jamais** enregistrée ni classée ; caméras proche/loin (touche **C**, bouton Vue de la manette) ; `?scenario=pilotage`.
- **Réglages par défaut = ceux de Nathan (retouche 7b, `docs/lots/lot-7b-reglages.md`)** : pointe 48 m/s, grip 44 / 47, seuil de glisse 0,14, dérapage doux (angle 0,32, serrage 33), gravité 24,6, rebords durs (rebond 0,6, frottement 0,3). `SIM_VERSION` et `GENERATOR_VERSION` valaient 3 au 7b ; le lot 8 les passe à 4, le lot 12 à 5, le lot 15 à **6**.
- Générateur : **deux lignes droites derrière chaque plaque** (`PAD_RUNOUT`, generator.ts) — à 48 m/s, une plaque suivie d'un virage serré ne se prend pas (frein 40 contre poussée 30 pendant 0,9 s). Le circuit d'essai suit la même règle. Pilote : marge aux rebords de 3,6 m (`WALL_MARGIN`).
- **Vitesse au-delà de la pointe (lot 15)** : la pointe du plat reste **48 m/s** mais n'est **plus un plafond dur** : au-delà, **traînée en cube** `overspeedDrag × ((u ÷ pointe)³ − 1)` (2,5 ; remplace l'ancienne décélération constante de 14 m/s²), appliquée aussi sous plaque et turbo. La gravité (`slopeGravity` **40**, pente 0,125 par bloc de descente) et les poussées vont plus haut : **plaque 66 m/s** (`boostMaxSpeed`), **super turbo 88 m/s** (`turboMaxSpeed`, ≈ 317 km/h) ; la voiture retombe progressivement (88 → 61 m/s en 5 s). Un virage reste limité par l'adhérence (R3 ≈ 60 m/s, L2 ≈ 43, serré ≈ 26). **Garde-fou anti-traversée** : aucun changement de pas (0,375 m par sous-pas à 88 m/s pour un disque de 1 m) ; `vitesse.test.ts` fait heurter des rebords à 88 m/s (angles de 5° à 60°, de face dans un virage, braquage à fond, transition de largeur) et exige que la voiture reste sur la route à chaque pas. **Toute nouvelle poussée ou nouveau relief qui augmente la vitesse maximale doit rejoindre ce test.** Panneau `?debug&tune` : `overspeedDrag`, `boostMaxSpeed`, `turboMaxSpeed`, `slopeGravity`.
- **Chute et reprise automatique (lot 17)** : sous `track.voidY` la voiture tombe sans commande `FALL_TICKS` pas (0,5 s) puis reprend au dernier point de contrôle, chrono qui continue (voir « Relief, sauts et chute »).
- **Cuves rapides (retouche 18b, `docs/lots/lot-18b-cuves-rapides.md`)** : sur une paroi (`substepShell`), la pesanteur n'est pas symétrique — la montée coûte `shellClimb` (0,4) de la pesanteur tant qu'elle n'est pas franche, la descente pousse `shellDescent` (2,6) fois, avec un surplus éteint vers `shellGainTop` (56 m/s) — et la paroi est une **voie rapide** (pointe `shellTop` 1,15 × 48 m/s, poussée `shellPush` 14 m/s² sous cette pointe). **Garde-fou anti-zigzag** : au-delà de `shellGainTop` de vitesse totale une traînée (3 /s) ramène la voiture, et la descente n'ajoute plus rien (un zigzag dans 14 blocs de cuve reste sous 62 m/s à plat, test `cuves-rapides.test.ts`). Les cinq clés sont dans `CarParams` et `?debug&tune`. Pilote : il « pompe » les cuves droites (`STRAIGHT_UP` / `STRAIGHT_DOWN`, bouts libres) et prend la paroi des virages en cuve ; la relaxation longue de la trajectoire ne vaut qu'à `CUVE_NEAR` blocs d'une cuve. Générateur : cuve droite de 6 blocs + 4 droites (`CUVE_RUN`, `CUVE_RUNOUT`), virage en cuve large ou ample (plus de serré). `SIM_VERSION` et `GENERATOR_VERSION` : **10** à la 18b (**12 et 13** depuis le lot 21).
- Tests de comportement chiffrés : `packages/sim/test/conduite.test.ts` (seuils recopiés dans le README du lot, mis à jour au 7b), `vitesse.test.ts` (lot 15, seuils dans `docs/lots/lot-15-vitesse.md`).

## Air et atterrissages (lot 19)
- **Réception** (`land`, `car.ts`) : au premier contact après un vol (≥ `LANDING_MIN_AIR` sous-pas), la vitesse **normale** au sol est absorbée (`landAbsorb` 0,95 : aucun rebond) et la vitesse **tangentielle** garde `1 − landLoss × (écart d'alignement − landTolerance)` (plancher 0,4), l'écart étant |tangage − pente du sol| + |roulis − pente latérale| (pentes, jamais d'angles). Mêmes règles dans une cuve (`landOnShell`) ; la voiture se pose à plat sur la paroi.
- **Rotation héritée** : en l'air la caisse garde tangage, roulis et lacet (`airDamping` 0,4 /s) ; plus de retour à l'horizontale (`airLevel` supprimé). Un vol de moins de `HOP_SUBSTEPS` (6 sous-pas : bosse, frôlement de paroi) garde l'ancien amortissement fort. Pentes bornées à ±1,6 (`AIR_TILT_MAX`). En quittant une paroi (`leaveShell`) seule la **vitesse de rotation** de la courbure est héritée (bornée à 1,5 pente/s), jamais l'inclinaison : une caisse couchée par une paroi verticale lirait ses roues sous la route comme un mur (`STEP_UP`).
- **Frein en l'air = figer** : l'amortissement de la rotation passe à `airDamping + airFreeze × frein` (`airFreeze` 14 /s : < 5 % de la vitesse angulaire en 0,3 s) ; il ne ralentit pas la voiture (rien du moteur ni des freins n'agit en l'air). Accélérateur et direction sont sans effet en l'air.
- **Pilote** : `needsFreeze(car)` (autopilot.ts) = en vol (≥ 6 sous-pas) et la caisse tourne (> 0,12 /s) ; le pilote freine alors. Les tests de saut et de tremplin l'utilisent aussi (un joueur correct fait pareil). Après l'arrivée, une voiture qui repart en arrière freine aussi (`FINISH_REVERSE_BRAKE`, race.ts).
- **Clés de `CarParams`** (toutes dans `?debug&tune`) : `airDamping`, `airFreeze`, `landAbsorb`, `landTolerance` (0,3), `landLoss` (0,7). `landBounce` et `airLevel` n'existent plus. `SIM_VERSION` : **11** ; `GENERATOR_VERSION` : **12** depuis le lot 20 (figures) ; **12 et 13** depuis le lot 21 (bas-côtés).
- **Web** (présentation seule) : indicateur « ❄ FIGÉ » (`#freeze`) tant que le frein agit en vol, caméra qui suit la **direction du déplacement** en vol (`airMix`), son de réception selon sa qualité (`landingQuality` / `landingSound`, audioLogic.ts), secousse plus forte pour une mauvaise réception. `__cdj.air` expose `{ frozen, lastLanding, cameraMix }`.
- Scénario `?scenario=air` (`createAirTrack`, circuits.ts) : dos d'âne à haute vitesse, tremplin `J`, long saut au super turbo, saut vers un virage relevé, chute de trois niveaux, mur latéral quitté en l'air. Tests : `packages/sim/test/air.test.ts` (seuils recopiés dans `docs/lots/lot-19-air.md`), `e2e/air.spec.ts`.

## Commandes tactiles (lot 10)
- `apps/web/src/touch.ts` (logique pure, testée : `TouchPad` = doigts → axes, `dragSteer`, `zoneAt`, réglages `cdj:touch`, seuil de choc) ; `touchUi.ts` (DOM : zones, aides, boutons, réglages, invitation portrait, plein écran) ; `input.ts` (`Controls` fusionne clavier, manette et doigts). Mode actif si `pointer: coarse`, ou `?touch=1` (la souris simule le doigt) ; `?touch=0` le coupe.
- Lot 23 : bouton **🎥** (caméra suivante) en tête de la barre d'actions.
- Disposition paysage : moitié gauche = direction (glissement relatif au point de pose, ou boutons ← →), moitié droite = frein ; accélérateur **automatique** par défaut (ou bouton gaz) ; boutons pause / reprise / départ / réglages / plein écran ; **P** = pause (aussi au clavier). Depuis le lot 29, ⚙ ouvre **Réglages › Commandes** (les réglages tactiles y sont : `touchSettingsControls`, `touchUi.ts`), il n'y a plus de panneau `#tsettings`.
- **Deux pédales par défaut (retouche 18b)** : `autoThrottle` vaut `false` (gaz manuel à droite + frein) ; l'accélérateur automatique reste une option des réglages. Les réglages enregistrés (`cdj:touch`) portent une **version** (`TOUCH_SETTINGS_VERSION`, 2) : un enregistrement sans version (ancien défaut) retrouve une fois le nouveau défaut pour `autoThrottle`, le reste est conservé ; un choix fait depuis est respecté. Les e2e qui conduisent en automatique l'enregistrent d'entrée (`phone(browser, p, { stored })`, `fresh: true` pour le vrai défaut).
- **Règle : le tactile produit les mêmes commandes entières que les autres entrées** (axes flottants → `makeInput`) ; rien dans `sim`, rediffusions identiques. Vibration (point de contrôle, choc) = présentation seule, lecture de la vitesse sans effet sur la simulation.
- **Zones (retouche 10b, `docs/lots/lot-10b-zones-tactiles.md`)** : une seule définition dans `touch.ts` — `zoneSpans` (zones **actives**, sans trou, toute la hauteur : ← 0–25 %, → 25–50 %, frein 50–100 % ou frein 50–75 % | gaz 75–100 %), `zoneAt` en découle, `buttonRects` place le **visuel** (compact, centré dans sa zone, écarté des zones sûres `env(safe-area-inset-*)` et de 24 px des bords). Le toucher se décide par la zone, jamais par le bouton dessiné. Un doigt glisse d'un bouton à l'autre d'une même famille (← →, frein / gaz) ; identifiant de pointeur, `pointerup` / `pointercancel` seulement (pas `lostpointercapture`). **Piège : un petit bouton attire les appuis voisins** (le navigateur corrige le toucher vers lui) : la barre d'actions reste compacte et loin des frontières entre zones. Réglage « taille des boutons » (`buttonSize`), `?steer=boutons|glisser`, `?zones=1` (zones et un point par doigt, rouge hors couche de jeu), options dans `/admin/`.
- Tests : `apps/web/test/touch.test.ts` ; e2e `tactile.spec.ts` (vrais événements tactiles via `Input.dispatchTouchEvent`, gabarits Android et iPhone) ; outils `?debug` : `spec=<blocs>`, `__cdj.input`, `__cdj.manual(true)` + `__cdj.advance(n)` (pas à pas, sans rendu). Aides de mise en page : `e2e/layout.ts`.

## Surfaces et blocs à effet (lot 8)
- **Revêtement = attribut d'un bloc** (`Block.surface`, notation `S/t` terre, `S/g` glace, `S/h` herbe, `S/s` sable (lot 22) ; `/b` = virage relevé : `L2/b`, `R/tb`) ; `parseToken` (`track.ts`) lit la notation. `SURFACES` (`world.ts`) : `{ grip, traction, rolling, slick }` — route `1/1/0`, terre `0,7/0,85/1,5`, herbe `0,5/0,55/7`, glace `0,3/0,4/0` (`slick` 1 : lot 16) ; `surfaceAt(échantillon)` les lit sous chaque roue (adhérence latérale ← grip ; motricité et freinage ← traction ; roulement en m/s²). **Où en ajouter un** : `SurfaceKind` + `SURFACE_LETTERS` (track.ts), une ligne de `SURFACES`, ses couleurs dans `trackMesh.ts` (`SURFACE_COLORS`, `SURFACE_MARKS`), `SURFACE_HUD` (main.ts). **Nouvelle surface ou nouveau bloc = `SIM_VERSION` +1** (et `GENERATOR_VERSION` si le pilote ou le générateur s'en sert).
- **Blocs à effet** : `P` plaque, `T` super turbo (`turboTicks` 180, `turboAccel` 42, `turboMaxSpeed` 68 : trois clés de `CarParams`), `C` moteur coupé (`car.cut` : l'accélérateur n'agit plus ; `stepRace` le rend au pas exact qui franchit le point de contrôle suivant). Les états `boost`, `turbo`, `cut` vivent dans `CarState` (donc rejoués à l'identique) ; après l'arrivée les effets sont coupés (`withoutEffects`).
- **Virages relevés** : `bankAt` (track.ts) donne hauteur et gradient du relevé (pente 0,3 serré / 0,22 large, rampe = `BANK_RAMP_ARC` 0,5 de l'arc, profil quintique `bankFactor` : pente et courbure nulles à l'entrée et à la sortie — lot 24, plus de tremplin ; `SIM_VERSION` 14 / `GENERATOR_VERSION` 15) ; `world.sample` les ajoute à la hauteur et au gradient ; `collide` compare au sol réel ; la voiture reçoit la pente latérale (`ay -= gravity × pente`). Rendu : `trackMesh.ts` (`arcPoint` suit le relevé).
- **Pilote** : `racingLine` module vitesse de passage (grip × revêtement + g × pente) et freinage (traction × revêtement + roulement) ; il reste à 1,5 m de l'axe en virage relevé. Générateur : `PAD_RUNOUT` (2 droites derrière une plaque) et `TURBO_RUNOUT` (5 derrière un super turbo).
- Tests : `packages/sim/test/surfaces.test.ts` (seuils recopiés dans `docs/lots/lot-8-surfaces-themes.md`), `e2e/surfaces.spec.ts`. Outils : `?scenario=surfaces`, `?theme=<stade|rallye|banquise|nuit|campagne|canyon|col|ville>`.
- **Revêtement selon la position en travers (lot 21)** : `world.sample` rend le revêtement **du point** (`Surface.kind`) : la route du bloc, un **vibreur** (`kerb`, bandes de `KERB_WIDTH` 1,5 m aux deux bords d'un virage sur route : **exactement l'adhérence de la route**, seuls le son, la vibration et la caméra changent) ou un **bas-côté**. `SurfaceKind` (sous les roues) ⊃ `BlockSurface` (attribut `S/t`…). Le **sable** (lot 22) est à la fois revêtement de bloc (`S/s`) et bas-côté (`~s`).
- **Bas-côtés (lot 21)** : **bord = attribut de bloc chaîné comme la largeur** (`Block.shoulder`, `Block.open`) : `~h` herbe, `~t` terre et gravier (`gravel`), `~p` neige poudreuse (`snow`), `~v` vide (sans rebords, comme `o`), `~r` retour aux rebords (`S/n~h`, `L2/~t`) ; `o` reste « ce bloc seul sans rebords ». Un bloc qui ne peut pas en porter garde ses rebords **sans casser la chaîne** (départ, arrivée, cuve, vide, rampe, tremplin ; et pour une bande : montée, virage relevé, descente de trois niveaux). La bande va du bord de la route à `SHOULDER_EDGE` = 15 m de l'axe (8 / 5 / 2 m de large sur 14 / 20 / 26 m) où **un rebord ordinaire** l'arrête (« au-delà : un rebord », décidé) ; là où la bande s'arrête contre un bloc plus étroit, une **face de bout** (segment, nez arrondi : `endFaces`, world.ts) ; la porte d'un point de contrôle couvre la bande. Revêtements (`SURFACES`) : terre et gravier `0,6/0,65/4,5`, herbe `0,5/0,55/7`, neige poudreuse `0,42/0,5/8` ; **ordre de ralentissement : gravier < herbe < neige** (pointes 38 / 27 / 20 m/s), jamais de chute ni de calage à plat (`basCotes.test.ts`).
- **Route bosselée (lot 21)** : modificateur `u` (droites, pentes, blocs à effet) : tôle ondulée en travers, bosses de `RIPPLE_HEIGHT` 0,15 m tous les `RIPPLE_LENGTH` 6 m, effacées sur la première et la dernière période (`rippleAt`, polynômes) ; `world.sample` l'ajoute à la hauteur et à la pente, pas `blockHeight`. Effet mesuré : freinage +16 %, réponse latérale −40 %, pointe presque intacte.

## Glace (lot 16)
- La glace réagit au pied (`car.ts`, `SurfaceParams.slick` = 1 ; valeurs = clés `ice*` de `CarParams`, dans `?debug&tune`) : **accélérateur appuyé** = adhérence latérale très faible (`SURFACES.ice.grip` 0,3), sous-virage, motricité 0,4 (patinage) ; **roue libre** (ni gaz ni frein) = adhérence rendue (`iceCoastGrip` 0,38), décélération × `iceCoast` 0,3, et `iceRealign` 0,8 /s éteint la vitesse latérale (le vecteur vitesse se réaligne sur le cap, sans freiner) : gauche-droite en roue libre rattrape la trajectoire ; **frein** = adhérence × `iceBrakeGrip` 0,5, freinage 16 m/s², glisse. Pointe sur glace = pointe du plat × `iceTop` 1,2 (la traînée au-delà de la pointe suit). Aucun roulement sur glace.
- Pilote : vitesse de passage sur glace = roue libre (`racingLine(…, iceCoastGrip)`), il lâche l'accélérateur en braquant (> 0,12) et le rend en ligne droite. Générateur : aucune règle ajoutée ; *Banquise* mesurée comme les autres thèmes. `?scenario=glace` (`GLACE_TRACK_SPEC`), tests `packages/sim/test/glace.test.ts` (seuils dans `docs/lots/lot-16-glace.md`), e2e `glace.spec.ts`. `SIM_VERSION` et `GENERATOR_VERSION` valent **7**. **Un test qui compare des revêtements fixe le pied** (gaz appuyé).

## Largeurs de route et courbes amples (lot 12)
- **Largeur = attribut de bloc** (`Block.w0` entrée, `Block.w1` sortie, en m) : `e` étroite 14 m, `n` normale 20 m, `l` large 26 m (`ROAD_WIDTHS`, track.ts), dans une cellule de 32 m. Notation : `S/n` (constante), `S/e>l` (**bloc de transition**), combinable (`S/n>et`, `L3/lb`). **Chaînée comme les hauteurs** : un bloc sans largeur garde la sortie du précédent (14 m au départ, comme avant) ; une largeur écrite doit la prolonger exactement (`parseTrack` refuse « marche de largeur ») ; seul le premier bloc choisit la sienne. Un virage garde sa largeur (pas de transition dans un virage).
- **Transition** : une droite de 32 m dont la demi-largeur suit un lissage cubique (`blockHalfWidth`, `blockHalfWidthSlope` : pente nulle aux deux bouts, 0,28 au plus) ; `world.sample` l'utilise, `collide` incline la normale du rebord (`√(1 + pente²)`), le générateur ne fait qu'**un cran à la fois** (14 ↔ 20 ↔ 26). Les **plaques** (P, T) font la moitié de la largeur de la route (`blockPadHalfWidth`, 3,5 m de demi-largeur sur 14 m : inchangé) ; `Gate.halfWidth` donne la largeur de la porte (course : tolérance + 2 m) ; le rendu (`trackMesh.ts`) suit : rebords, sillons, damier, portes, tremplin, moteur coupé.
- **Virage ample `L3` / `R3`** (3 × 3 cellules, rayon d'axe 80 m, `curveSize`) : huit cellules réservées (le coin intérieur n'est jamais touché par la route), sortie à 3 colonnes et 2 rangées. Un **virage serré** (rayon 16 m) tient jusqu'à 26 m de large (rayon intérieur 3 m) mais **le générateur n'en met pas sur la route large**.
- **Générateur** (`generator.ts`, `themes.ts`) : 5 à 7 créneaux calme + virage ; virages **larges (L2/R2) ou amples** le plus souvent, S larges (`L2 R2`), demi-tours larges (`L2 L2`) ; **au plus 2 virages serrés par circuit** (passage signature compris), **jamais deux de suite**, jamais sur la route large ; **au moins deux largeurs** par circuit (sinon la tentative échoue), largeur de départ et changements tirés selon `Theme.widths` : *Stade* et *Banquise* plutôt larges (poids 6/5 pour 26 m), *Rallye* et *Campagne* plutôt étroits, *Nuit* mélangé (2 à 3 changements). **Signatures** : Banquise = chicane large sur glace (`iceChicane`), Campagne = **étranglement** (`dirtPinch` : la route se resserre à 14 m puis un virage serré sur la terre, puis s'élargit à nouveau). **Fenêtre du temps de l'auteur : 30–40 s** (`AUTHOR_MIN_MS` / `AUTHOR_MAX_MS`), pour qu'une course correcte (or ×1,08) tienne en 30–45 s.
- **Pilote** : la marge aux rebords reste de 3,6 m (`WALL_MARGIN`) ; l'écart latéral permis est `demi-largeur − marge` en chaque point, donc la corde s'ouvre avec la largeur (14 m : 3,4 m de jeu ; 26 m : 9,4 m) et un virage large se prend plus vite sur la route large (mesuré : L2 en 5,51 s à 14 m, 5,32 s à 26 m).
- Tests : `packages/sim/test/largeurs.test.ts` (notation, chaînage, transition, rebords inclinés, plaques, portes, L3/R3, pilote), `generator.test.ts` (largeurs, virages serrés, largeur dominante par thème). Outil : `?scenario=largeurs` (écrit à la main : `LARGEURS_TRACK_SPEC`).
- **Nouvelle largeur, nouveau bloc de forme ou nouvelle règle de génération = `SIM_VERSION` / `GENERATOR_VERSION` +1**, puis `UPDATE_GOLDEN=1` sur `golden.test.ts` et `golden-daily.test.ts`, `npm run history:seed` et `npm run measure:generator`.

## Mesures : moments de choix (lot 21)

## Relief, sauts et chute (lot 17)
- **Niveaux** : `LEVEL` = 4 m. `U` / `D` = 1 niveau sur une cellule (pente 0,125) ; **`U2` `U3` `D2` `D3`** = 2 ou 3 niveaux (pente 0,25 / 0,375, `RISE_LETTERS`, `track.ts`). `Block.rise` = dénivelé résolu du bloc (les hauteurs s'enchaînent avec `exitDelta(kind, rise)`) ; `Block.open` = sans rebords. Un dos d'âne (`U2 D2`) fait décoller ; une montée raide ne se met jamais sur l'herbe, la terre ou la glace (la voiture cale : `surfaceable`, generator.ts).
- **Sauts** : **`K`** rampe (plate jusqu'à `KICK_START` = 16 m, puis +1 niveau, pente 0,25), **`G`** vide (aucun sol, aucun rebord ; `GU` / `GD` / `GD2` : l'autre bord est 1 niveau plus haut / plus bas / 2 niveaux plus bas), puis une réception (`D`, `S`…). `packages/sim/src/jump.ts` : `trackJumps(track)` → `{ kick, gapCells, gap, rise, landing, runout, minSpeed, maxSpeed }` = **fenêtre de vitesse au bord de la rampe** (balistique pure, marge ×1,05 mesurée ; plancher ≈ 33 m/s pour un vide d'une cellule vers un bord plus bas, 40 au même niveau, 52–58 pour deux cellules, 55 vers un bord plus haut ; plafond = la réception ne suffit plus). **Tester par la simulation** (`test/sauts.test.ts`), pas seulement par la formule. `J` (tremplin, lot 2) reste dans le circuit d'essai et `pilotage`, mais le générateur ne le pose plus.
- **Sans rebords** (`S/o`, modificateur `o`) : `collide` ne retient plus la voiture par le côté ; elle tombe. Le générateur n'en met que sur des blocs ordinaires à ≥ 6 m au-dessus du point le plus bas (`openSection`), selon le thème (`openChance`).
- **Chute** (`race.ts`) : sous `track.voidY` (route la plus basse − `FALL_DEPTH` = 4 m) `race.fallTicks` passe à 1 ; la voiture tombe **sans commande** pendant `FALL_TICKS` = 60 pas (0,5 s), puis reprend au dernier point de contrôle (`respawn`) ; le chrono ne s'arrête jamais (un pas par pas, +1 à la reprise) ; la touche de reprise pendant la chute reprend aussitôt. Rejouable à l'identique. Web : voile sombre `#fall`, bandeau « Chute ! », sons `fall` / `respawn`, caméra qui ne plonge pas ; **ombre d'atterrissage** (`landing.ts`, `predictLanding` : lecture seule) = ombre posée au point de réception prévu, absente si la voiture ne retombe sur rien.
- **Générateur** (`composeSpec`) : dénivelé ≥ `MIN_RELIEF` = 12 m (le premier relief du circuit en fait au moins 12), reliefs `HILLS_GENTLE` / `HILLS_STEEP` (hauteurs gardées entre ±24 m), **vrai saut** (`jumpCalm` : `short` K GD, `flat` P K G D, `long` T K G G D, `longDown` P K G GD D, `up` T K GU) selon `theme.jumpChance` (100 % Stade, Nuit ; le Rallye l'a aussi par sa signature, un saut court sur la terre) ; priorité des créneaux : signature, saut, virages marquants, portions rapides, reliefs. Pas d'intersection (une cellule = un bloc) ; **pas de pont à deux niveaux** (la grille ne le permet pas simplement). Descentes raides dans la portion rapide `drop`.
- **Pilote** : le freinage tient compte de la pente (`slopeGravity × pente`), **aucun freinage en l'air** (la vitesse visée ne baisse pas de la rampe à la fin de la réception : `airborne`), reste au milieu sur rampe / vide / réception, marge de 1 m de plus sans rebords. `PilotRun.jumpsOk` : au bord de chaque rampe, vitesse ≥ `JUMP_ENTRY_MARGIN` (1,08) × plancher et ≤ plafond, sinon le circuit est refusé.
- Rendu : piliers et dalle mince au-delà de `PILLAR_MIN` = 12 m au-dessus du sol lointain, faces pleines au bord d'un vide, rampe claire à bande d'alerte, damier vert de réception, bordure plate rouge et blanche sans rebords. Miniatures : le vide se voit (repli 2D compris).
- Web : `?scenario=relief` (préréglage « Relief et sauts » de `/admin/`). Tests : `test/relief.test.ts`, `test/sauts.test.ts`, `apps/web/test/landing.test.ts`, `e2e/relief.spec.ts`.

## Cuves (lot 18)
- **Notation** (`track.ts`) : `V` cuve droite (deux parois, demi-tube), `ML` / `MR` mur latéral (une paroi, à gauche / à droite), `/c` sur un virage (`L2/c`, `R3/c`, `L/c` : sa paroi est du côté **extérieur**). Une cuve est **une droite ou un virage avec un attribut** : `Block.cuve` (bits `CUVE_LEFT` | `CUVE_RIGHT`), `cuveIn` / `cuveOut` (côtés que le voisin prolonge : pas de rampe à ce bord). Refusés : pas de repère (`@cp`) ni de transition de largeur, ni `o`, ni `b`, ni sur le départ ou l'arrivée ; elle reste plate (aucun relief), la route peut porter un revêtement mais le générateur n'en met pas. `parseToken` renvoie `cuve` seulement s'il y en a une.
- **Géométrie** (`cuve.ts`, pas de trigonométrie) : en travers de la route, fond plat jusqu'à `f`, **quart de cercle** de rayon `R = CUVE_RATIO (0,65) × demi-largeur` (4,6 / 6,5 / 8,5 m pour 14 / 20 / 26 m), qui devient vertical en `demi-largeur`, puis **paroi verticale** jusqu'à `R + CUVE_LIP (8 m)` ; au-delà, c'est le vide (on passe par-dessus). Amplitude `a` ∈ [0, 1] (`cuveAmplitude`) : 0 = rebord ordinaire de 1,4 m, 1 = cuve ; **rampe de `CUVE_RAMP` = 16 m** depuis l'entrée / la sortie d'une droite, **30 % de l'arc** (`CUVE_RAMP_ARC`) dans un virage (7 / 22 / 37 m), sauf si le bloc voisin prolonge la paroi. Un virage est une **surface de révolution** (l'écart est la distance au centre du virage) : la normale reste dans le plan rayon-vertical. `shellAt` (distance signée, normale, avance de la route) ; `world.shell(x, z, y, out)` n'existe que pour `trackWorld` (le sol plat n'en a pas) ; `world.sample` rend une hauteur approchée (paroi tronquée à ≈ 80°) pour les lecteurs de hauteur ; `collide` ne répond pas dans une cuve (les parois sont dans la surface).
- **Physique** (`car.ts`, `substepShell`) : le contact se fait par la **normale** de la surface. La voiture est repérée dans le plan tangent (`tangentFrame` : avance `f`, gauche `l`, normale `n`) ; `car.yaw` reste l'angle d'un cap « à plat » (la voiture tourne autour de la normale : `yaw − cap de la route`) ; mêmes pneus, moteur et freins qu'à plat (formules recopiées de `substep`) ; la pesanteur se projette sur le plan (`ax −= slopeGravity × f_y`, `ay −= gravity × l_y`) ; la paroi repousse la position le long de la normale et supprime la vitesse qui y entre (sans rebond) ; **en l'air** (distance > `SHELL_TOUCH` 0,08 m) : balistique ; elle suit une paroi qui s'éloigne de moins de `SHELL_SNAP` 0,1 m (fin de rampe). Tangage et roulis restent 0 dans une cuve ; `CarState` gagne `nx, ny, nz` (la normale sous la voiture : (0, 1, 0) hors cuve, lue par le rendu). **Les blocs sans cuve rejouent au bit près** (test : même état qu'un monde sans `shell` ; rediffusion de l'essai inchangée à la version près).
- **« Décrochage »** (cuve **droite** seulement) : au-dessus de `shellStickHi` (34 m/s) la pesanteur le long de la paroi est annulée (la voiture tient sur la verticale), sous `shellStickLo` (24 m/s) elle s'applique en entier (la voiture redescend), entre les deux c'est progressif (`smoothstep`) ; l'adhérence suit la charge presque en proportion sur une paroi, et `shellDown` (1,2 g) est l'appui qui charge les pneus à vitesse. **Dans un virage en cuve la pesanteur reste entière** : c'est la géométrie (cône) qui tient la voiture à sa hauteur d'équilibre (`tan θ = v² / (g × rayon)`). Trois clés de `CarParams` (`?debug&tune`).
- **Pilote** : `AutopilotOptions.wall` (faux par défaut : le fond, comme un virage ordinaire) ; `true` = trajectoire **clouée** à la paroi extérieure du virage en cuve (écart latéral imposé : `pin`, entonnoir de 40 m en lissage cubique, `CUVE_INSET` = 1 / 2 / 2,5 m du pied de la paroi verticale selon la taille, `racingLine` compte `g × pente de la paroi` comme un relevé, aucun freinage sur la rampe de sortie). **`bestPilotRun` essaie les deux** (fond et paroi, 4 niveaux d'adhérence chacun) et garde le plus rapide ; `PilotRun.wall` dit lequel. La relaxation de la trajectoire va plus loin (4000 itérations) seulement pour un circuit qui a un virage en cuve : **les autres circuits gardent leur tracé**.
- **Générateur** : `Theme.cuveChance` — Stade 100 %, Nuit 100 %, Banquise 25 %, Rallye et Campagne 0 %. Rien n'est tiré pour un thème sans cuve (même suite de tirages). Motifs (`CuveKind`, poids 3 / 2 / 3) : `bowl` six blocs `S V V V V S`, `wall` `S ML/MR ×4 S`, `turn` un virage en cuve (`L2/c`, `L3/c`, parfois le serré `L/c` qui compte dans le budget de virages serrés). Priorité des créneaux : signature, saut, **cuve**, virages marquants, portions rapides. `bowl` et `wall` ajoutent six cellules : un créneau de moins ; s'il n'y a pas de créneau calme libre, c'est un virage en cuve. Un thème à 100 % refuse la tentative sans cuve (graine voisine).
- **Rendu** (`trackMesh.ts`, `addCuve`) : fond à la couleur du revêtement, quarts de cercle et parois en **damier rouge et blanc** (bandes de 4 m dans le sens de la marche), chapeau de crête, remblai en retrait de 0,15 m derrière chaque paroi (sinon les deux plans scintillent). Voiture et fantôme : `carPose.ts` (`CarPose` : la normale de la voiture, lissée à 12 /s, tourne le « haut » du monde ; **l'axe de rotation est l'avance de la route**, le cap reste donc le long de la paroi) ; **caméra** : son « haut » est entre la verticale et la normale (60 % du roulis, `CAMERA_ROLL_FOLLOW`) ; ombre masquée sur une paroi. `telemetry.ts` : roues posées dans le plan tangent (`tangentFrame`), `tilt`, `onWall` ; `fx.ts` : traces de pneus au ruban orienté par la normale (`Skids.wheel(…, nx, ny, nz)`) et étincelles des roues arrière sur la paroi (> 18 m/s).
- Outils : `?scenario=cuves` (`CUVES_TRACK_SPEC`, circuits.ts : élan, cuve droite, mur latéral, virage en cuve large à pleine vitesse, demi-tour serré, le même virage abordé trop lentement), raccourci « Cuves et murs » de `/admin/`, ligne « Cuves » du planning (`cuvesText`), miniature cadrée sur la cuve s'il n'y a ni signature ni saut. Tests : `packages/sim/test/cuves.test.ts` (seuils recopiés dans `docs/lots/lot-18-cuves.md`), `apps/web/test/carPose.test.ts`, `e2e/cuves.spec.ts` (navigateur et Node calculent la même voiture sur la paroi, à 1e-9 près).

## Figures (lot 20)
- **Un circuit du jour = 5 à 7 figures** (`packages/sim/src/figures.ts`, `FIGURES`, 40 figures) posées à la suite par `composeFigures` (`generator.ts`) ; `composeSpec` n'en rend que le texte, `DailyCircuit.figures` donne `{ name, variant, left, from, to }` (blocs `[from, to)`). Le texte, les temps et les golden d'une date changent avec le lot ; **`SIM_VERSION` ne bouge pas** (aucun bloc, aucune physique).
- **Une figure** = `{ name, label, category, intent, variants, off, build(ctx) }` + drapeaux `jump` / `cuve` / `cut` / `turbo` / `banked` / `relief` / `braking`, `weight`. `build({ L, R, wall, width, variant })` rend des blocs (`L` = sens du premier virage, échangé par le miroir ; `width` = route à l'entrée, la figure se rétrécit d'elle-même si besoin : `toTight`, `reach`) ou `null` si la variante est impossible. Catégories : `technique`, `saut`, `rapide`, `combo`, `cuve`, `relief`. Une figure commence par une droite d'amorce (retirée si le bloc précédent en est une) et garde derrière elle les droites exigées (2 après une plaque, 5 après un super turbo, 3 après un saut court, 5 après une cuve ou un saut long). `turned` ajoute un virage large derrière un saut ou une cuve : sans lui, on les quitte à plus de 55 m/s et on garde le plein gaz jusqu'au bout.
- **Composition** (`selectFigures`) : la signature du thème (`SIGNATURE_FIGURE`) toujours ; un saut et une cuve selon `jumpChance` / `cuveChance` (une figure qui fait les deux, 55 %) ; du dénivelé (de préférence un virage en pente) ; au moins un **freinage franc** (`braking` : plaque ou turbo, puis virage) ; une portion rapide ; une figure favorite du thème ; au moins deux techniques ; le reste au poids (favorites ×4, `braking` ×2, `weight`) dans un budget de durée (`FIGURE_BUDGET`, `figureSeconds`). Plafonds : 2 sauts, 1 cuve, 1 moteur coupé, virages serrés (`minTightTurns`) ≤ `MAX_TIGHT`. **Huit tirages** : le premier budget tenu (`FIGURE_TOTAL_MAX`) qui lâche le plus le gaz (somme des `off`) l'emporte. Ordre aléatoire, jamais de saut en tête ni en queue ; chaque figure prend la première (variante, miroir) qui tient sur la grille, dans les hauteurs permises et le budget de virages serrés, sinon une remplaçante de la même catégorie ; la signature ne se remplace pas. Liaisons `CONNECTORS` ; `MAX_PLAIN_STRAIGHT` (6 blocs) plafonne la plus longue droite ordinaire. Un circuit estimé hors de `ESTIMATE_MIN`–`ESTIMATE_MAX` (`estimateSeconds` : durée du pilote ≈ 0,95 × estimation) est refusé **sans faire rouler le pilote**.
- **Peu de répétition sans historique** : `isRested(nom, jour)` — trois groupes de figures (empreinte du nom), le jour `d` laisse au repos le groupe `d mod 3` (hors signature) ; deux jours de suite n'ont que le tiers des figures en commun, et rien n'est généré pour les jours passés. **Thèmes** : `theme.figures.favor` / `.ban` (glace là où il y a de la glace, terre là où il y a de la terre, cuves là où il y en a).
- **Ajouter une figure** : une entrée de `FIGURES` (nom en minuscules à tirets, `off` provisoire) → `npx vitest run packages/sim/test/figures.test.ts` (le pilote doit finir **chaque** variante, dans les deux sens, sur les trois largeurs) → `RHYTHM=1 npm run measure:generator` pour régler `off` (secondes hors plein gaz par passage) → favorites ou interdites des thèmes → **`GENERATOR_VERSION` +1**, `UPDATE_GOLDEN=1 npx vitest run packages/sim/test/golden-daily.test.ts`, `npm run history:seed`. **Un thème qui interdit trop de figures ou une règle de plus se mesure** (`construit` / `dans la fenêtre` par thème) : au lot 20, trois virages serrés tirés sans compter faisaient échouer 50 % des tentatives de *Campagne*.
- **Pilote** : mesure seule ajoutée à `PilotRun` (`fullThrottleTicks`, `liftEvents`, `grip`) ; un moteur coupé ne compte pas comme plein gaz.
- Web : `?scenario=figures` (tour de onze figures écrit à la main, `FIGURES_TRACK_SPEC`) et `?scenario=figure&f=<nom>&v=<variante>&m=1` (`createFigureTrack` : cinq droites de lancement, point de contrôle juste avant, miroir avec `m=1` ; nom inconnu = circuit d'essai) ; admin : « Les figures », « Une figure en boucle » (sélecteur, variante, miroir) et la carte d'un jour du planning liste ses figures (`figuresText`). Tests : `packages/sim/test/figures.test.ts`, `apps/web/e2e/figures.spec.ts`. README : `docs/lots/lot-20-figures.md`.

### Le Salon oublie (retouche 27b)
- **Règle : une session finie est oubliée.** Décision de Nathan : une fois le circuit changé, on ne garde **rien** de la session précédente — ni courses, ni classement, ni podium, ni circuit. À `fin + 20 s` (depuis le lot 31 : la fenêtre de lecture `SALON_SERVE_MS`, pendant laquelle le classement final et ses fantômes restent servis pour le podium du jeu ; les envois, eux, sont clos à `fin + 3 s`), `salon_runs`, `salon_sessions` et `salon_circuits` de cette session sont **effacés** ; `board` / `ghosts` répondent 404 pour elle ; plus de table `salon_podiums` (supprimée par `MIGRATIONS`), plus de route `GET /api/salon/podiums`. Même règle en mode démo (`DemoSalonApi.forget` : rien de la session précédente après la bascule, la course du joueur comprise).
- **Nettoyage à la demande, jamais en tâche de fond** (`forget`, `apps/api/src/salon.ts`) : appelé au début de chaque route du Salon, il compare un entier (la dernière session oubliée par **cette instance**) et ne fait des `DELETE` qu'à la première requête qui voit une session terminée ; une instance qui démarre refait le nettoyage une fois (rattrape un arrêt prolongé, ou les sessions gardées 48 h par la version précédente). Sur Cloud Run le service peut être éteint : rien ne dépend d'une minuterie (`api.tick()` ne sert plus qu'à préparer le circuit suivant).
- **Présence espacée** : au plus **une écriture par joueur et par 30 s** (`PRESENCE_WRITE_MS`) — l'instance retient sa dernière écriture (aucune requête dans l'intervalle) et l'upsert est **conditionnel** (`WHERE seen_at <= excluded.seen_at − 30 s` : une autre instance ne le fait pas écrire de plus) ; présent = vu dans la dernière minute (`PRESENCE_MS` 60 s, le double de l'intervalle, sinon un joueur qui lit en continu clignoterait). **Un spectateur ne compte pas** : sans identifiant de joueur (`SalonApi.now(null)`, `board(session, null)`), le serveur n'écrit rien.
- **Écritures en base** (Turso facture les lignes écrites) : `npm run measure:salon` compte les lignes écrites par table (`changes()`) ; mesures avant / après et décisions dans `docs/lots/lot-27b-salon-oubli.md`. Piège trouvé par la mesure : le **débit des lectures** (`rate`) écrivait aussi à chaque lecture (947 lignes par joueur et par heure, autant que la présence) : il est maintenant en mémoire.

## Finale du Salon (lot 31)
- **À `fin − 15 s` (`FINALE_MS`)** : plus aucun départ (`startOpen`/`startLocked` ; boutons « Recommencer » et « Rejouer » grisés, message « Dernière chance : plus de départ », la tentative en cours n'est pas remise à zéro) ; ceux qui roulent continuent ; **grand compte à rebours 15 → 0** au centre (`#finale`) ; classement de la session **affiché d'office** et rafraîchi **toutes les 2 s** (`FINALE_POLL_MS`).
- **À l'heure pile (`fin`, horloge recalée sur le serveur)** : la course en cours s'arrête **pour tous, non comptée** (`abortRun`, rien n'est envoyé), le **circuit suivant s'installe tout de suite** (même instant pour tous, mesuré sur l'horloge du Salon) et le **podium final s'affiche par-dessus** (10 s, jeu gelé dessous : le décompte de départ du nouveau circuit court à la fermeture du podium, pour ne rien faire perdre). Le podium est rafraîchi une fois à `fin + 3,5 s` (envois clos). Spectateur (`?watch=best`) : podium, puis retour au Salon normal.
- **Serveur** : un envoi n'est accepté que jusqu'à **`fin + 3 s`** (`SALON_GRACE_MS`, était 60 s) ; marge réseau justifiée dans le code et `docs/lots/lot-31-futur-finale.md` (une course finie *avant* l'heure pile peut arriver après ; une course non finie à l'heure pile n'est jamais envoyée). La session reste **lue** (classement, fantômes) jusqu'à **`fin + 20 s`** (`SALON_SERVE_MS`) pour le podium, puis oubliée (27b). Sessions toujours alignées sur l'horloge (xx:00, xx:10…) ; `?salonMinutes` suit la même règle.
- **Tests** : `apps/web/test/salon.test.ts` (horloge de session), `apps/api/test/salon.test.ts` (envoi à `fin + 2 s` accepté, à `fin + 5 s` refusé), `e2e/salon.spec.ts` (sessions d'une minute : finale, course coupée, deux navigateurs, podium).

## Jour de Paris (lot 31)
- **« Aujourd'hui » = la date à Paris** (Europe/Paris, heure d'été comprise), la même pour tout le monde au même instant, où que soit le joueur (décision du 14/10/2026 ; **remplace la règle « jour UTC »**). Une seule fonction, **hors de `sim`** : `packages/clock` (`@cdj/clock`, `parisDay(ms)`, `parisDayStart(jour)`, `msUntilNextParisDay(ms)`), qui lit `Intl.DateTimeFormat` avec `timeZone: "Europe/Paris"` et se **contrôle** contre la règle de l'Union européenne (dernier dimanche de mars à 01 h UTC → dernier dimanche d'octobre à 01 h UTC) sur des instants de contrôle ; sans fuseaux dans l'environnement, c'est la règle seule (`parisClockSource` : `intl` ou `table`, rendu par `/api/health` → `clock`). `sim` reçoit toujours une date : **les circuits de chaque date ne changent pas**, seul l'instant où « aujourd'hui » passe au jour suivant bouge (aucune version à monter).
- **API** : jour accepté pour un envoi, **grâce de 10 min après minuit de Paris** (`GRACE_MS`), classement du jour, jours figés du planning, `GET /api/day`, `/api/me`, admin : tout passe par `today = parisDay(now())` et `parisDayStart`. Un jour peut durer **23 h, 24 h ou 25 h** (changements d'heure : 25/10/2026, 28/03/2027) : ne jamais supposer 86 400 000 ms.
- **Jeu** : accueil « Prochain circuit dans HH:MM:SS (minuit, heure de Paris) » (`#home-nextday`) ; à zéro la page se recharge sur le nouveau circuit (une course en cours n'est pas interrompue : l'accueil est fermé ; son temps compte s'il est envoyé pendant la grâce). Admin : « Aujourd'hui (Paris) ».

Déploiement par `.github/workflows/deploy-api.yml` à chaque fusion dans `main` qui touche l'API ou `sim` (image → Artifact Registry → Cloud Run, puis contrôle de `/api/health`) ; **ignoré proprement tant que les variables et secrets ne sont pas définis** (le résumé liste ce qui manque). Authentification par fédération d'identité (`GCP_WORKLOAD_IDENTITY_PROVIDER` + `GCP_SERVICE_ACCOUNT`) ou clé JSON `GCP_SA_KEY`. `ci.yml` (job `api-image`) construit l'image, la lance contre un vrai serveur libSQL (`sqld`) et passe `npm run smoke`.
- **Secrets** (Secret Manager → variables d'environnement, jamais dans le dépôt, la configuration en clair ni les journaux) : `TURSO_AUTH_TOKEN`, `ADMIN_TOKEN`, `RATE_SALT`. Variables non secrètes : `TURSO_DATABASE_URL`, `ALLOWED_ORIGINS`, `TRUST_PROXY=1`, `GIT_SHA`.
- **Configuration** (`apps/api/src/config.ts`, pure et testée) : `readConfig(env)` ; `server.ts` sort en erreur (code 1, ligne JSON « configuration refusée ») si **`SALON_MINUTES` est réglée en production** (`NODE_ENV=production`, posé par l'image), si `ALLOWED_ORIGINS` ou `RATE_SALT` (≥ 16 caractères) manquent en production, ou si **`TURSO_DATABASE_URL` manque sur Cloud Run** (`K_SERVICE` : le disque est effacé à chaque redémarrage). Hors Cloud Run et sans Turso : SQLite local (`DB_PATH`), comme avant.
- **Base** : interface `SqlDb` (`db.ts`) ; implémentations SQLite (`node:sqlite`, `node-sqlite.ts`), D1 (`d1.ts`) et **libSQL / Turso** (`libsql.ts` + `libsql-open.ts`). Turso : client HTTP pur JavaScript embarqué dans le paquet (`@libsql/client/http`, `libsql://` lu comme `https://` : aucune connexion qui dure) ; `file:` (développement, tests) : client natif chargé à la demande, absent de l'image. **Une instruction = un aller-retour réseau** : les lectures indépendantes se font en parallèle (`board`), le schéma en un lot (`SqlDb.batch`). **Schéma** : `ensureSchemaOn` crée ou met à jour au premier appel de chaque instance ; l'empreinte du schéma est dans la table `meta` (`schemaVersion()`, calculée du texte de `SCHEMA` + `MIGRATIONS` : **aucun numéro à incrémenter**), une instance qui trouve la bonne empreinte ne fait qu'une lecture. Un échec au démarrage n'est pas gardé (la requête suivante réessaie). Piège : `rowsAffected` de libSQL vaut 0 pour une instruction avec `RETURNING`.
- **Tests sur les deux bases** : `vitest.config.ts` a deux projets (`sqlite`, `libsql`) ; les tests d'API passent par `openTestDb()` (`apps/api/test/helpers.ts`, fichier libSQL temporaire : `:memory:` y perdrait la base). Toute nouvelle requête SQL doit passer sur les deux (`npm test` le fait).
- **CORS** : `ALLOWED_ORIGINS` (virgules ou points-virgules) = origines, **sans chemin** (`https://nathan-te.github.io` couvre le jeu et ses aperçus de branche) ; l'origine de la requête est répétée si elle est listée (`Vary: Origin`), sinon aucun en-tête CORS. `*` autorise tout. `ALLOW_ORIGIN` (une seule valeur) reste pour les anciennes installations.
- **Adresse du client** : `TRUST_PROXY=<n>` = nombre de proxys de confiance, l'adresse est lue **depuis la droite** de `X-Forwarded-For` (chaque proxy ajoute la sienne à la fin ; le début est falsifiable par le client et ferait tomber la limite de débit). 1 sur Cloud Run (à reconfirmer après le déploiement).
- **Règle : pas de tâche de fond indispensable.** Cloud Run n'alloue du calcul que pendant une requête et éteint le conteneur sans joueurs. Le circuit du jour (`getCircuit`) et celui d'une session du Salon (`circuitFor`) sont **générés par la première requête qui en a besoin** (≈ 0,2–0,5 s), **un seul calcul même si deux requêtes arrivent ensemble** (promesse en cours par jour / session), puis gardés en base ; avec deux instances le calcul peut se faire deux fois, le résultat et l'écriture sont identiques (déterministe). `api.tick()` (préparation du circuit suivant du Salon, toutes les 15 s) ne tourne **qu'hors production**. L'oubli du Salon est déjà à la demande (27b).
- **Débit avec 2 instances** : les envois (par adresse, par joueur, échecs d'admin) sont comptés **en base** (exacts quelle que soit l'instance) ; les lectures du Salon sont comptées **en mémoire par instance** (la limite réelle est au plus doublée, voir 27b) ; la présence est limitée en base (`seen_at`).
- **`/api/health`** : `{ ok, db, simVersion, generatorVersion, today, salonMinutes, salonOverride, revision? }`, **503 `db: "error"`** si la base ne répond pas. **Journaux** (`log.ts`) : une ligne JSON par événement (`severity`, `message`, champs courts) ; démarrage, schéma, circuit généré, temps accepté, 429, 5xx. **Jamais** de rediffusion, de pseudo, d'identifiant ni d'adresse (test `production.test.ts`) ; les lectures ordinaires ne sont pas journalisées.
- **Code de transfert** : voir « Profil (lot 30) » (depuis le lot 30 le code ne contient plus que l'identifiant secret, `CDJ2`) ; cartes du profil : accueil et **Réglages › Profil**.
- **Budget** (`npm run measure:budget`, résultats dans le README du lot 28) : un joueur du circuit du jour = ≈ 9 requêtes ; 30 minutes de Salon = ≈ 560 requêtes (le Salon interroge toutes les 5 s) : **ce sont les requêtes du Salon qui limitent l'offre gratuite** (2 millions par mois), puis les lignes lues de Turso quand beaucoup de joueurs sont présents.

## Profil (lot 30)
- **Le serveur fait foi, le stockage local n'est qu'un cache.** Un profil = un identifiant secret (`players.id`, 128 bits tirés par le navigateur) + un pseudo réservé + ses temps (`results`). Plusieurs appareils partagent le même profil en chargeant le même **code de transfert**.
- **`GET /api/me`** (identifiant dans l'en-tête **`X-Player-Id`**, jamais dans l'adresse, qui finit dans les journaux de l'hébergeur ; CORS l'autorise) : `{ name, renameRequired, today, simVersion, stats: { days, medals{author,gold,silver,bronze}, bestRank{date,rank,participants}, streak }, best (temps du jour + `trackId`, `splits`, **rediffusion** + `simVersion`, pour le fantôme « ton record »), past[] (`date`, `trackId`, `ms`, `medal` : les médailles des archives) }`. Erreurs : `404 unknown_player` (jamais classé), `410 code_revoked`. Limité à 60 lectures par joueur et 200 par adresse et fenêtre. **Coût** : ≈ 8 instructions et 2 lignes écrites (compteurs de débit) + ≈ 2 lignes lues par jour d'historique ; la **place d'un jour terminé est calculée une fois** (`results.final_rank` / `final_total`, au premier `GET /api/me` après la minute de grâce) puis gardée : sans cela chaque synchronisation relisait le classement de chaque jour (mesuré : 5 770 lignes lues pour 120 jours contre 248). Mesures : `docs/lots/lot-30-pseudos.md`, `npm run measure:budget`.
- **Synchronisation** (`apps/web/src/profileSync.ts`, `ProfileSync` ; la fusion `mergeProfile` est pure et testée) : au **lancement** et au **retour sur l'accueil** (au plus une fois par 30 s, `SYNC_GAP_MS`), le jeu lit le profil et le fusionne avec le cache — **le meilleur gagne** : pseudo du serveur ; temps du jour du serveur plus rapide que le local → il le remplace **avec sa rediffusion** (`best` rechargé, fantôme « ton record » mis à jour sans course en cours) ; jours passés écrits sans rediffusion (médailles des archives) ; meilleure place retenue (`cdj:rank:`) ; `cdj:sub:<circuit>` prend la valeur du serveur. **Rien n'est jamais supprimé** : un record local meilleur que celui du serveur (fait hors ligne) reste, et `syncProfile` (main.ts) l'**envoie** (`online.submit`, le serveur le rejoue — `needsSubmit`). État observable : `online.sync.state` (`idle|syncing|ok|offline|revoked|unknown|disabled`, `known`, `renameRequired`, `nameProblem`, `error`), `__cdj.sync` avec `?debug`. **Hors ligne** : le cache local sert et la carte du profil le dit discrètement (« Hors ligne : voici le profil de cet appareil… »). Pas de serveur / démonstration : `disabled`, rien n'est synchronisé. Un `fetch` dont le corps est vide sur un 200 (page qui se décharge) est une panne réseau (`api.ts`, `call`), pas une réponse.
- **Pseudo** (`Online.rename`) : joueur connu du serveur → `PUT /api/player` (les autres appareils le voient à leur prochaine synchronisation) ; pas encore classé ou pseudo qui partira avec la course (`viaSubmit`) → `GET /api/name` (libre ou non) ; hors ligne → local pour un joueur que le serveur ne connaît pas, **refusé** pour un joueur connu. Pseudo pris : message, suggestions libres à toucher, bouton « Charger un code » (formulaire de l'arrivée, du Salon et de la carte du profil). Compte renommé par la migration : message sur la carte du profil (`cdj:notice:rename` retient « Garder ce pseudo »).
- **Code de transfert simplifié** (`transfer.ts`) : **`CDJ2.<identifiant : 32 hexadécimaux>.<CRC-32 sur 8 hexadécimaux>`** (46 caractères). « Charger un code » lit le profil **sur le serveur** (`GET /api/me` avec cet identifiant), montre le pseudo et les statistiques du serveur, demande confirmation, puis `applyIdentity` : identifiant et pseudo remplacés, cache des records / places / temps confirmés effacé (il appartenait à l'ancienne identité), **sauf le record d'aujourd'hui pas encore confirmé par le serveur** (`pendingTrackIds`), qui sera envoyé au nom du profil chargé ; rechargement, la synchronisation remplit le reste. Sans serveur (démonstration, aucune API) : « Pas de serveur ici », rien ne change. Les **anciens codes `CDJ1`** (lot 28, avec records) restent acceptés : leurs rediffusions d'hier et d'aujourd'hui sont envoyées au serveur pour validation (`legacyReplays`, `ProfileHost.submitLegacy`), les autres sont ignorées — le serveur ne garde que ce qu'il a rejoué. Le code contient l'identifiant secret : à garder comme un mot de passe.
- **Révocation — « Changer mon code »** (Réglages › Profil et carte du profil de l'accueil, **confirmation obligatoire**) : `POST /api/me/code` avec l'ancien identifiant en en-tête et **`{ newId }` tiré par le jeu** dans le corps ; une transaction (`SqlDb.batch`) copie les `results` et le profil sur le nouvel identifiant, **inscrit l'ancien dans `revoked_codes` (empreinte SHA-256 seulement)** et oublie les courses du Salon en cours ; le pseudo et tous les temps sont conservés. Ensuite l'ancien identifiant est refusé en **410 `code_revoked`** (« Ce code n'est plus valide… ») par `/api/me`, `submit`, `PUT /api/player`, le Salon et un second changement ; les lectures publiques (classement, fantômes) ne lui rendent rien. Limité à 3 par joueur et fenêtre. **Rejouable** : le nouvel identifiant est gardé (`cdj:player:next`) jusqu'à la réponse ; si elle se perd, la même demande réussit encore, et la synchronisation adopte `cdj:player:next` quand l'ancien code est refusé. Les autres appareils voient « Ce code n'est plus valide » (carte du profil, formulaires) et chargent le nouveau code.
- **Règles** : aucun changement de `sim` ni des versions (`SIM_VERSION` et `GENERATOR_VERSION` inchangées, golden et `history:seed` inchangés) ; le serveur ne fait toujours pas confiance à un temps annoncé (un record envoyé par la synchronisation est rejoué comme les autres) ; les joueurs de démonstration ont un identifiant **stable par nom** (`fictionalId`, `history.ts`) puisqu'un pseudo n'appartient qu'à un joueur ; **tout nouvel endpoint qui prend un identifiant secret le lit dans l'en-tête `X-Player-Id` et refuse un code révoqué** (`players.assertActive`) ; ne jamais mettre l'identifiant dans une adresse ni un journal ; un nouvel appel qui crée ou renomme un joueur passe par `players.resolveName` / `save`.
- Tests : `apps/api/test/pseudos.test.ts` (unicité, casse et accents, libération, Salon, course simultanée, migration d'une base à doublons, `GET /api/me`, révocation, transaction, débit ; SQLite **et** libSQL), `apps/web/test/{profileSync,transfer,online,api}.test.ts` ; e2e `profil.spec.ts` (serveur dédié sur le port **8790**, plusieurs appareils : pseudo refusé puis code chargé, record vu sur l'autre appareil avec fantôme et médaille, pseudo changé, hors ligne puis réseau revenu, code changé et ancien code refusé). **Piège de test** : les pages ouvertes qui ne servent plus continuent de dessiner en rendu logiciel et affament la page qu'on regarde (le délai de 8 s d'un appel à l'API court pendant que le fil principal est occupé) → les mettre en sommeil avec `__cdj.manual(true)` (`sleep` / `wake` de `profil.spec.ts`).

## Règles de la simulation (déterminisme)
- Pas fixe (`TICK_RATE` = 120 Hz), jamais de `dt` variable ; interpolation à l'affichage seulement.
- Pas de moteur physique externe. Pas de `Math.sin/cos/exp/pow/tanh/atan2/…` dans `sim` : implémentations maison ou tables (`sin`/`cos` de `math.ts` ; saturation rationnelle `tireCurve` = t / ⁴√(1 + t⁴) ; angles de glissement, tangage et roulis gardés en **pentes** (rapports), jamais convertis en angles ; amortissements en `x * (1 − k·dt)`).
- Modifier une valeur par défaut de `CarParams` (ou la géométrie de `car.ts`) = incrémenter `SIM_VERSION` + régénérer les références (et `GENERATOR_VERSION` si le temps du pilote change, ce qui est presque toujours le cas).
- Commandes de la voiture = entiers (`makeInput`) ; l'état de référence de `car.test.ts` ne change que si la physique change volontairement.
- Pas de `Math.random` ni `Date` dans `sim` : PRNG à graine explicite.
- Une course = la suite des commandes du joueur ; le même code la rejoue côté serveur.

## Tests et CI (retouche 29b) — rouge = vrai problème
- **CI** (`.github/workflows/ci.yml`) : job `test` (typecheck + Vitest + build), job `e2e-parts` = **matrice** navigateur × **part** (`--shard` : Chromium en 8 parts, Firefox et WebKit en 2), job `e2e` = **verdict unique** qui fusionne les rapports « blob », écrit le résumé du run et échoue au moindre vrai échec ; job `api-image`. Protection de `main` : statuts `test` et `e2e` obligatoires (réglage GitHub de Nathan, pas à pas dans `docs/lots/lot-29b-ci-fiable.md`). Objectif : moins de 20 min du push au verdict. Run de nuit (03 h 17 UTC) sur `main`.
- **Une relance, signalée** : `retries: 1` **en CI seulement** (`playwright.config.ts`). Un test qui échoue puis réussit est **« instable »** : nommé dans le résumé du run (`scripts/e2e-summary.mjs`) et annoté `::warning`, **jamais caché** ; au run de nuit un instable fait échouer le job. Un instable est une dette à corriger, suivie dans `docs/orchestration.md` § 8 ; on ne relance jamais « pour voir si ça passe ». La trace de tout essai raté est gardée (artefact `resultats-*`).
- **Horloge maîtrisée** : aucun test ne dépend de l'heure réelle ni ne change de jour en route. `e2e/fixtures.ts` (`test`, `newClockedContext`, `TODAY`, `FIXED_NOW`, `clockNow`) décale `Date` des pages ; `playwright.config.ts` fixe le décalage une fois (midi UTC le 20/10/2026) et le donne aux serveurs de test (`TEST_CLOCK_OFFSET_MS`, **refusée en production** par `config.ts`, signalée par `/api/health`). **Un spec qui calcule « aujourd'hui » importe `test` de `./fixtures` et utilise `TODAY`**, jamais `Date.now()` ni `new Date()`. **Pas `page.clock.install`** : il remplace `requestAnimationFrame` par un minuteur de 16 ms qui ignore le rendu logiciel et affame le fil principal (mesuré : 34 images/s simulées contre 3,5 réelles).
- **Écrire un test stable** : attendre un **état** (`__cdj.phase`, `waitForFunction`, événements), pas une durée (`waitForTimeout` n'est admis que pour « rien ne doit changer pendant N ms ») ; pas à pas (`__cdj.manual` + `advance`) plutôt que temps réel dès qu'un résultat dépend du nombre d'images ; **un serveur de test par spec** quand elle compte des présents ou des sessions (8787 classement, 8788 Salon de `salon-serveur`, 8789 `watch-serveur`, 8790 `profil`) ; une mesure de cadence se fait sur l'horloge de la page et sur plusieurs secondes ; une capacité absente (WebGL) se teste par `hasWebGL(page)` avec `test.skip` motivé, jamais par le nom du navigateur seul.
- **Interdits** : désactiver, sauter (`skip`, `fixme`), affaiblir un test (seuil relâché sans mesure, assertion retirée) ou pousser un commit vide pour être vert. Un test faux se corrige et le README du lot dit pourquoi. « Tous les tests verts » = la CI verte sur la PR.

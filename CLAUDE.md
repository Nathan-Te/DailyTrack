# Circuit du Jour — carte du dépôt et règles communes

Monorepo de jeux web quotidiens (un niveau par jour, identique pour tous, classement validé par rediffusion). Réponses et docs en français. Visions (**ne pas modifier**, c'est Nathan qui le fait) : `docs/seed.md` (DailyTrack), `docs/jump/seed-dailyjump.md` (DailyJump), `docs/plateforme/seed-phase-2.md` et `seed-phase-3.md` (plateforme), et la charte visuelle `docs/plateforme/identite.md` (phase 3).

## Comment lire ces consignes (lot T1 : économie de jetons)
- **Ce fichier est un index et les règles communes.** Il est chargé à chaque session ; **il n'importe plus aucun autre fichier** (un `@fichier` est chargé au lancement, donc ne réduit rien : documentation de Claude Code, « How Claude remembers your project »). Les règles d'un jeu ou d'une zone vivent dans le `CLAUDE.md` de son dossier, que Claude Code charge **à la demande**, dès qu'on lit ou modifie un fichier du dossier (lecture par l'outil Read ou par une commande de lecture comme `cat`). **Si tu travailles dans un dossier sans avoir lu un seul de ses fichiers, lis d'abord son `CLAUDE.md`**.
- **Les `CLAUDE.md` ne portent que les règles en vigueur qui servent à chaque lot de la zone.** Le reste — mécanismes d'un lot, chiffres mesurés, procédures — a été déplacé **mot pour mot** dans `docs/regles/<zone>/<sujet>.md` ; chaque `CLAUDE.md` garde le titre de la section et un renvoi. **Quand ton travail touche un sujet dont le titre est suivi d'un renvoi « → Détail », ouvre ce document avant de modifier** : la règle y est entière. Liste complète des déplacements : `docs/regles/deplacements.md`.
- **Ajouter une règle** : si elle sert à chaque lot de la zone, elle va dans le `CLAUDE.md` de la zone ; si elle ne sert qu'à un sujet (un mécanisme, une procédure, des chiffres mesurés), dans `docs/regles/<zone>/<sujet>.md`, avec un titre et un renvoi dans le `CLAUDE.md`. Plafonds : racine 200 lignes, zone 300 lignes (et 8 000 / 12 000 jetons) ; une règle n'est écrite qu'une fois, les autres endroits y renvoient. `npm run consignes` contrôle (taille, imports, renvois, liens) et `apps/portail/test/consignes.test.ts` le vérifie en CI ; `npm run mesure-jetons` chiffre ce qu'une session charge.
- **Un `CLAUDE.md` ne renvoie jamais à un README de lot** : les README (`docs/**/lots/`) sont l'historique ; la règle qui en est issue est dans le `CLAUDE.md` ou dans `docs/regles/`.

## Règles communes à tous les lots
- **Un lot = une session = une branche = une PR brouillon.** L'agent s'arrête quand les critères d'arrêt du lot sont verts.
- **Rapport honnête** : ce qui est vérifié, ce qui ne l'est pas, les décisions laissées à Nathan ; un échec se dit avec sa sortie, une étape sautée aussi.
- **Tests jamais affaiblis** : ni désactivés, ni sautés, ni seuil relâché sans mesure, ni commit vide pour être vert (détail dans « Tests et CI » ci-dessous). Sauter une suite *non concernée* par une PR (CI de PR courte par zones, lot R10) n'est pas l'affaiblir, ni ranger un test dans la famille « Régression » (lot R13, `docs/tests.md` : il tourne la nuit) ; le run de nuit et la CI complète que lance le bouton « Mettre en production » (lot R12) lancent tout.
- **Zones partagées** (liste ci-dessus) : un seul propriétaire à la fois ; un lot n'en modifie une que si son prompt le dit. Les golden de chaque jeu ne bougent que si le lot le décide.
- **Toute nouvelle table liée à un joueur ou à une partie rejoint la liste de la remise à zéro du lancement (`TABLES_VIDEES`, `apps/api/src/remiseAZero.ts`) et l'effacement d'un joueur (crochet `erase` de son jeu, lot R5 ; lot N1 : `players.eraseStatements` pour les tables de la plateforme)** ; toute nouvelle clé de stockage du navigateur est ou bien une donnée de jeu (effacée au « Nouveau départ ») ou bien un réglage gardé (`CLES_GARDEES`, `packages/profile/src/generation.ts`). Le test de `remiseAZero.test.ts` échoue sinon. **La remise à zéro de la production n'est lancée que par Nathan** (workflow « Lancement : remise à zéro », liste de contrôle `docs/plateforme/lancement.md`) : aucun test ni outil n'écrit dans la base de production.
- **Mentions légales et confidentialité (lot R5 ; lot I6 : aussi en anglais)** : la page `playdujour.com/mentions-legales/` (`apps/portail/mentions-legales/index.html`, **elle fait foi**) et sa traduction fidèle `playdujour.com/legal/` (`apps/portail/legal/index.html`), liées depuis le pied du portail, la pause et les Réglages des deux jeux — **celle de la langue choisie** (`cheminMentions` de `@cdj/ui`) — **disent exactement ce que le code fait**. **Règle de fidélité** : toute nouvelle donnée gardée (table, colonne, stockage du navigateur, traceur, service tiers) ou durée changée met à jour **les deux pages** dans le même lot ; une durée ou un nombre tiré du code y porte `data-constante` / `data-valeur` (lot N1 : aussi le panneau d'administration — session, journal, erreurs, rediffusion retirée), et `apps/portail/test/mentions.test.ts` vérifie les constantes, que chaque table de la base y est décrite, et que l'anglaise a les mêmes constantes, rubriques et tables que la française. Effacement d'un joueur : `docs/plateforme/effacement.md`. Publicité, traceur ou cookie tiers = bandeau de consentement et relecture juridique d'abord.
- **Sécurité (lot R7)** — rapport et preuves : `docs/plateforme/audit-securite-2026-10.md` (constats S-01 à S-22, lots proposés, étapes de Nathan). Règles qui en découlent :
  - **Workflows** (`.github/workflows/`, contrôlés par `node scripts/securite-workflows.mjs` et `apps/web/test/securiteWorkflows.test.ts`, donc par la CI) : un bloc `permissions:` au niveau du workflow (lecture par défaut ; une écriture seulement où `ECRITURES_PERMISES` la prévoit) ; **jamais `pull_request_target`** ; **toute action externe épinglée par l'empreinte de son commit** (`uses: x/y@<40 hexadécimaux> # v1.2.3` ; trouver l'empreinte avec `git ls-remote https://github.com/x/y 'refs/tags/v1*'`, jamais une étiquette seule) ; aucune donnée d'un tiers (`github.head_ref`, `inputs.*`, `github.event.*`) écrite dans un `run:` : elle passe par `env:`. Pas de clé de compte de service : fédération d'identité seulement.
  - **Pas de `innerHTML`** (ni `outerHTML`, `insertAdjacentHTML`, `document.write`, `eval`, `new Function`, `setAttribute("on…"/"style")`) avec une donnée : pseudos et tout texte venu du serveur se posent en `textContent` ; une clé d'attribut ne vient jamais d'une donnée.
  - **`?api=`** : sur la production (`VITE_PRODUCTION=1`) il ne vise que `/`, `demo`, sa propre origine ou la machine locale (`apiFromAddress` de `@cdj/profile`) ; tout nouveau paramètre d'adresse qui désigne un serveur, une URL ou un identifiant suit cette règle. L'identifiant secret et le jeton d'admin ne vont **jamais** dans une adresse.
  - **Site publié** : `firebase.json` porte les en-têtes de sécurité (`nosniff`, `Referrer-Policy`, `frame-ancestors 'none'`…) ; **rien de ce qui révèle un jour à venir ne part en production** (`demo/`, fichiers de démonstration, outils de date) ; la recette et les aperçus sont `noindex` (`robots.txt` et `X-Robots-Tag`). Une CSP stricte est un lot (`audit-securite-2026-10.md`, annexe) : en attendant, **aucun script ni style en ligne, aucune ressource extérieure** dans les pages.
  - **Identifiant secret d'un joueur (lot F2)** : on ne montre jamais l'identifiant secret d'un joueur, ni sur une page ni dans une adresse ; on utilise sa **référence publique** (`players.ref`, empreinte à sens unique, la seule chose qu'une ligne de classement porte). Le lien d'invitation d'un ami ne porte qu'un jeton aléatoire gardé en empreinte, jamais l'identifiant.
  - **Secrets** : jamais dans le dépôt, un rapport, une issue, un commit, un journal (même tronqué) ; dire où ils sont et quoi révoquer. Pas de journal avec un identifiant, un pseudo, une adresse ou un jeton. Aucun outil de test n'écrit dans la base de production.
  - Dépendances : aucune ajoutée sans raison ; `npm audit --omit=dev` doit rester à 0.
- **« Pour les joueurs » dans toute PR de lot (lot N2) — obligatoire** : le modèle de PR (`.github/pull_request_template.md`) a une section `## Pour les joueurs` : **une ligne par changement visible**, `- [Track] Le bouton caméra revient à l'écran sur téléphone. // The camera button is back on screen on phones.` (la zone entre crochets : `Du Jour`, `Track`, `Jump` ou `Tower` — **une zone par jeu du registre**, la liste unique est `ZONES_NOUVEAUTES` de `@cdj/core/nouveautes`, qu'un test relit contre le registre : un nouveau jeu y ajoute sa ligne (et la couleur de son étiquette dans `admin.css` et `portail.css`) ; le français, ` // `, l'anglais ; un anglais manquant bloque la publication de la nouveauté), **ou `rien` seul** si rien ne se voit (outils, tests, serveur sans effet visible). Le panneau `/admin/` lit ces lignes sur les PR fusionnées depuis la dernière mise en production (API publique de GitHub, depuis le navigateur de l'éditeur) pour que Nathan rédige les nouveautés ; la lecture est `lirePourLesJoueurs` (`packages/core/src/nouveautes.ts`, testée). Un agent met la section dans **sa** PR (pas dans le README du lot, qui n'est pas lu) ; le README du lot la recopie. Règles de la diffusion (nouveautés, message en direct, bandeau) : `apps/api/CLAUDE.md` (« Nouveautés et message en direct (lot N2) »), `apps/portail/CLAUDE.md`, `apps/web/CLAUDE.md` et `apps/jump/CLAUDE.md` (« Message en direct »).
- **Recette avant production** : rien ne part en production sans passer par la recette (lot R12 : la répétition est une étape du bouton) ; depuis le lot R4 la production part **par le bouton « Mettre en production »**, jamais à la fusion, et **le lancement du bouton par Nathan vaut validation** (lot R12) ; un agent ne lance, ne relance et ne crée ni ressource ni secret (`apps/api/CLAUDE.md`, « Recette (lot R1) » ; ce fichier, « Adresses et mise en production »).
- **Toute interface hors partie suit la charte `docs/plateforme/identite.md`** (direction « Cartouches », phase 3) et passe par le socle `@cdj/ui` : jetons, composants, catalogues `fr` + `en` (aucune chaîne ni couleur en dur) ; consignes : `packages/ui/CLAUDE.md`. Les jeux y sont passés aux lots I4 (Track) et I5 (Jump).
- Un **nouveau paramètre d'adresse** rejoint la page d'admin / `urlOptions.ts` du jeu ; **tout texte en français** (le portail ; les jeux depuis I4 / I5 : français **et** anglais par les catalogues) ; un nouveau spec e2e s'ajoute à `durees.json` de son jeu **et à sa zone de CI** (lot R10 ; lot K1c : dans **la fiche du jeu**, `e2e.specs`, pas dans `e2e/zones.json`).
- **Règles communes, détail déplacé** (une ligne ici, la règle entière dans le document) :
  - **Date du lancement public** : une seule source, `config/lancement.json` ; jamais une copie ni une date en dur. → [donnees-lancement-turso.md](docs/regles/racine/donnees-lancement-turso.md)
  - **Turso sobre** : les tests et outils de mesure n'utilisent jamais Turso ; un script qui vise une base distante exige `--distant` ; toute requête vérifie son plan. → [donnees-lancement-turso.md](docs/regles/racine/donnees-lancement-turso.md)
  - **Administration** : `/admin/` avec connexion Google ; tout ce que le panneau fait à un joueur est journalisé ; l'identifiant secret d'un joueur ne sort jamais du serveur. **La preuve de l'auteur ne quitte jamais le serveur.** → [administration-et-preuve-de-lauteur.md](docs/regles/racine/administration-et-preuve-de-lauteur.md)
  - **La musique** : un seul lecteur (`@cdj/musique`) ; ajouter un morceau = `musique/musiques.json` + `npm run musique` ; seules licences `mienne`, `CC0`, `CC-BY-4.0`, `achetee`. **Manette** : tout nouvel écran déclare son action principale (`manette.ts`). **iPhone** : marges `env(safe-area-inset-*)` sur tout ce qui touche un bord. **Pages, budgets, traductions** : balises de partage et axe pour toute page, `npm run traductions` après tout catalogue, budgets dans `docs/plateforme/budgets.md`. → [interface-musique-manette-iphone-pages.md](docs/regles/racine/interface-musique-manette-iphone-pages.md)

## Ce qu'un agent n'ouvre pas (lot T1) — et la commande qui le remplace
Ces fichiers sont gros, produits ou historiques : les lire coûte des milliers de jetons et ne dit rien de plus que la commande. `.claude/settings.json` refuse leur lecture (outil Read ; Grep et Glob au mieux — et, pour les chemins refusés, Edit et Write aussi : ces fichiers se produisent par leur commande, jamais à la main). Les scripts, les tests et Bash (`cat`, `jq`, `head`, `git diff`) les lisent sans gêne : s'il faut vraiment en voir une partie, c'est par là.

| ne pas ouvrir | à la place |
|---|---|
| références de bancs et golden : `apps/api/test/fixtures/banc-*.json`, `packages/*/test/fixtures/golden*.json` | lancer le test qui les compare (`npx vitest run --project sqlite <fichier>`) ; le golden ne se régénère que dans un lot qui le décide (sa règle est dans le `CLAUDE.md` du jeu) |
| fichiers produits : `config/jeux/projections/`, `*.generated.*`, `docs/plateforme/traductions.md` | `npm run fiches`, `npm run traductions` (la source est la fiche ou le catalogue) ; `-- --verifier` dit s'ils sont à jour |
| données de niveaux de Jump : `packages/jump-sim/modules/*.json`, `apps/jump/public/levels/`, `apps/jump/public/outils/` | `npm run solve:modules`, `npm run freeze:days` ; leur forme est dans `packages/jump-sim/CLAUDE.md` |
| `package-lock.json` | jamais à la main : `npm install` le régénère (conflit : prendre celui de `main`, puis `npm install`) |
| historique des lots : `docs/lots/`, `docs/jump/lots/`, `docs/tower/lots/`, `docs/plateforme/lots/` (rapports et images), `docs/plateforme/budgets-historique.md` | la règle qui en est issue : `CLAUDE.md` de la zone ou `docs/regles/` ; une synthèse pour l'état d'ensemble (`docs/orchestration.md` fait 170 Ko : `rg -n "^#"` puis la section utile, jamais en entier) |
| journaux de CI et sorties longues | `npm run attendre-ci`, `npm run verifier` : verdict et échecs seulement |

## Plusieurs jeux dans ce dépôt
- **Lots en parallèle** (décision de Nathan, détail : `docs/orchestration.md` § 10) : un lot Track, un lot Jump et un lot Tower peuvent tourner en même temps si chacun reste dans **ses zones** — Track : `apps/web/**`, `packages/sim/**`, `apps/api/src/cdj.ts`, `apps/api/src/salon.ts` et leurs tests / outils listés, `docs/lots/**`, `docs/orchestration.md` ; Jump : `apps/jump/**`, `packages/jump-sim/**`, `apps/api/src/jump*.ts`, leurs tests et outils, `docs/jump/**` ; Tower (lot R15) : `apps/tower/**`, `packages/tower-sim/**`, `apps/api/src/tower*.ts`, leurs tests et outils, `docs/tower/**`. **Tout le reste est partagé et réservé aux lots de la plateforme** (dont `apps/api` hors de ces fichiers, `scripts/**`, `.github/**`, `docs/plateforme/**`, la charte, les seeds, ce fichier) : un lot de jeu qui en a besoin **s'arrête et le propose** dans son README. Exceptions tolérées, rien d'autre : **sa fiche `config/jeux/<id>.json` (lot K1) et ce que `npm run fiches` en tire**, la ligne du jeu dans `budgets.md`, ses entrées de `durees.json` et de `packages/ui/test/applications.ts`, ses clés de catalogue (et `docs/plateforme/traductions.md` régénéré). Une PR de jeu porte l'étiquette `jeu:track` / `jeu:jump` / `jeu:tower` (ou `track` / `jump` / `tower` dans son nom de branche ; un morceau `plateforme` dans le nom de branche fait de la PR une PR de la plateforme, même avec un nom de jeu) : le job `zones` (`scripts/zones-jeu.mjs`, verdict dans `test`) échoue si elle sort de ses zones. Avant la fusion : fusionner `main` (pas de réécriture), CI de nouveau verte ; un conflit hors de ses zones : s'arrêter et le signaler. Budgets : chaque jeu a les siens ; **les plafonds et les marges vivent dans `docs/plateforme/budgets.md` et nulle part ailleurs** (lot K1 : plus aucune marge recopiée en prose, elle périmait — celle de Track y est remesurée à chaque lot ; Track mesuré par la mesure unique `mesureTrack` de `scripts/budgets.mjs`, la page d'admin à part) : un lot de jeu qui dépasse un plafond en retire ailleurs ou demande à Nathan de le relever. Les lignes « à la demande » de Track (décor, palier 2, vie et ciel, post-traitement, mesure de la règle de qualité, Garage) sont au tableau de `budgets.md` (`track.decor`, `track.palier2`, `track.vieCiel`, `track.post`, `track.qualiteMesure`, `track.garage`).
- **Règle : avant de déclarer le lot fini, fusionner `main` à jour (une seule fois, juste avant de s'arrêter) et obtenir une CI verte** sur le résultat. Conflit sur `package-lock.json` : ne pas le fusionner à la main, prendre celui de `main` puis relancer `npm install`, qui le régénère.
- Jeux, liste des zones partagées et règle des zones : [jeux.md](docs/regles/racine/jeux.md).

## Commandes

## Tests et CI (retouche 29b, lots R3, R10 et R13) — rouge = vrai problème
- **Interdits** : désactiver, sauter (`skip`, `fixme`), affaiblir un test (seuil relâché sans mesure, assertion retirée) ou pousser un commit vide pour être vert. Un test faux se corrige et le README du lot dit pourquoi. « Tous les tests verts » = la CI verte sur la PR.
- **Règle d'arrêt des agents** : (1) **un échec dans une zone que le lot ne touche pas** : relancer une fois (nouveau commit ou demande à Nathan : un agent ne relance pas un workflow, 403) ; s'il échoue encore, le noter dans le README du lot (test, run, message) et **s'arrêter** : on ne corrige pas, on ne s'acharne pas, Nathan tranche ; (2) **un échec dans sa propre zone** : un vrai problème, à corriger ; (3) **critère d'arrêt d'un lot : la CI de sa PR est verte**. La CI complète de `main` est vérifiée à la mise en production.
- **Le reste des règles de tests et de CI** — quatre familles (Essentiel, Régression, Doublon, Outil), CI de PR courte par zones, Tower dans la CI, durées des parts, budgets de poids, CI de `main` et complète, étapes e2e tirées des fiches, déclarer un nouveau spec (fiche **et** `durees.json`), quarantaine, preuve de stabilité, relance signalée, horloge maîtrisée, pas de date du calendrier en dur, installations apt, écrire un test stable, parts Chromium et contextes : [tests-et-ci.md](docs/regles/racine/tests-et-ci.md). **Un nouveau spec e2e se déclare dans la fiche de son jeu (`e2e.specs`) et dans `durees.json`.**

### Discipline de l'agent : du temps et des jetons (lot R10)
Chaque poussée relance la CI de la PR, et l'agent qui attend ou qui lit un journal consomme des jetons pour rien.
- **Avant de pousser, tester en local les zones touchées : `npm run verifier`** (typecheck, tests unitaires et specs e2e **choisis comme la CI de PR les choisit**, une ligne par étape, la fin du journal seulement en cas d'échec ; `-- --zones=track-sim,jump-ui` ajoute les specs de ces zones, `-- --liste` montre la sélection, `-- --sans-e2e`). Un **échec en CI se reproduit d'abord en local** (`npm run verifier`, ou la commande du spec seul) **avant de repousser**.
- **Pousser aux étapes**, pas à chaque correction : un lot = quelques poussées (première version complète, puis ce que la CI ou la relecture a trouvé). **Mettre la branche à jour avec `main` une seule fois, juste avant de s'arrêter** (fusion, pas de réécriture) ; pas de fusion de `main` entre deux étapes.
- **Attendre la CI : `npm run attendre-ci`** — **une seule commande bloquante et silencieuse** (jusqu'à 45 min) : elle n'écrit que le verdict par job et, en cas d'échec, le nom des tests rouges et 20 lignes d'erreur au plus. **Jamais** de sondage répété (`gh pr checks`, listes de runs en boucle, `sleep`) et **jamais** de journal de CI lu en entier.
- **Captures** : les produire pour Nathan (outils `CAPTURES=1`), **n'en regarder que quelques-unes (5 au plus par lot)** ; les autres se vérifient par des tests.
- **README de lot : 150 lignes au plus** (le détail va dans les fichiers du lot ou dans les `CLAUDE.md` concernés, pas dans le rapport). **Chaque `CLAUDE.md` de zone reste court** : les règles en vigueur seulement, l'historique des lots va dans `docs/` (taille actuelle et découpage proposé : README du lot R10).
- Mesurer la CI : `npm run mesure-ci -- --depuis AAAA-MM-JJ` (runs par PR, minutes, durée murale, file d'attente) et `npm run mesure-ci -- --specs` (les 20 specs les plus longs).

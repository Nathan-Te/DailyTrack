## Troisième arrêt : `figer`, « l'ancien code sur la base migrée » (run 40712408560)
- **Ce qui a échoué** : le smoke **du code en production** (`prod-2026-10-27-0949`, Jump en g17), lancé sur la base que le nouveau code (g21) vient de migrer et de remplir : « DailyJump : le fantôme du premier renvoyé sous un autre identifiant est refusé (409 replay_copy) » a reçu `409 {"error":"version"}`.
- **Cause** (reproduite en local avec `scripts/base-migree.mjs`) : le nouveau serveur de l'essai était construit **sans les jours Jump figés** que `figer` venait de calculer (ils ne vont que dans l'artefact `jours-figes`, que le déploiement ajoute ensuite). Il régénérait donc **le jour même** (28/10, servi figé en g17 par la production) en g21 ; son smoke y laissait le meilleur temps, en v11 ; l'ancien code renvoyait ce fantôme d'une autre version et recevait `version` avant d'atteindre la règle des copies. Ce n'est pas un défaut du retour arrière, mais un essai qui ne ressemblait pas au déploiement.
- **Correction** (`production.yml`, job `figer`) : avant l'essai, les jours figés sont ajoutés au nouveau serveur par **la même commande que le déploiement** (`mise-en-production.mjs jours-figes prod/… cible/…`). Vérifié en local : sans la copie, l'échec du run ; avec, les deux smokes verts (116 vérifications, code 0).
- **Limite connue** : un jour **sans aucun résultat** en production n'est pas figé (lot R11) ; si le bouton est lancé un tel jour avec un générateur de Jump changé, les deux codes servent encore deux niveaux différents pour aujourd'hui et la même vérification de l'ancien smoke échouera. Ce cas est à traiter par un lot de plateforme (par exemple faire courir l'essai sur un jour figé, ou attendre le premier résultat du jour) ; aujourd'hui le jour a des résultats et le bouton passe.

## Sixième arrêt, et la cause commune (run 40721073471)
La répétition (`recette-verification`) : 21 vérifications du smoke complet en échec (`track_mismatch`, niveau de Jump `g21` contre `g17` servi). **La cause commune des arrêts 3, 5 et 6** : le smoke complet ne fait pas que lire le serveur, **il recalcule lui-même le circuit et le niveau du jour** (`dailyCircuit` lit le registre de Track, le niveau de Jump vient des fichiers figés du dépôt). Il doit donc tourner sur exactement ce que le serveur visé a reçu. `recette-serveur` (deploy-api.yml) applique les artefacts de `figer` (jours figés, registre) avant son smoke ; **`recette-verification` repartait d'un dépôt nu, et du dernier `main` au lieu du commit déployé**. Un jour figé par cette mise en production (le 28/10, servi en g17 / générateur 16 par la production) y était recalculé avec les nouveaux générateurs. Les mises en production d'avant ne figeaient aucun jour dont le générateur avait changé : le défaut ne se voyait pas.
- **Correction** (`production.yml`) : `recette-verification` prend le commit déployé (`needs.verifier.outputs.sha`) et applique les jours figés et le registre (artefacts `jours-figes`, `registre-track`, les mêmes commandes que deploy-api.yml) avant le smoke ; `verification` lit aussi le commit déployé. **Test** (`apps/portail/test/workflows.test.ts`) : tout job qui lance un smoke complet le fait sur le commit déployé, après les jours figés et le registre ; rouge sur l'ancien workflow, vert sur le nouveau.
- **Reproduit en local avec les vrais artefacts du run** : base « recette » remplie d'abord par un serveur `main` nu (le 28/10 en g21), puis serveur avec les artefacts ; smoke depuis un dépôt nu : **21 ✗** (comme le run) ; depuis un dépôt avec les artefacts : **52 ✓, 0 ✗, deux passages de suite**.
- **Étape suivante vérifiée d'avance** : la PR « Jours figés » que `depot` ouvrira (les trois fichiers des artefacts appliqués à `main`) passée à `npm run verifier` en local — résultat dans la PR.
- **La PR « Jours figés » vérifiée d'avance (simulée en local avec les vrais artefacts)** : sa CI aurait été **rouge** (6 tests), donc `depot` se serait arrêté après la mise en ligne. Corrigé ici : (1) `apps/jump/test/figes.test.ts` ne connaissait la version de simulation d'un niveau figé que jusqu'à g15 (premier jour figé en g17 : la table complète, celle de `thawLevel`) ; (2) `packages/sim/test/freinage.test.ts` et `generator.test.ts` prenaient le 28/10 écrit en dur pour « un jour absent du registre » : le lendemain du dernier jour du registre (`jourAbsentDuRegistre`, `test/helpers/versions.ts`) ; (3) la démonstration de Jump (`apps/jump/public/demo`) rejoue les jours figés : `depot` la refait (`jump:seed`, déterministe, ≈ 1 min) quand des niveaux s'ajoutent, et la verse avec eux (test dans `workflows.test.ts`).

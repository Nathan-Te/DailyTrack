## 2. La remise à zéro
- **Le workflow « Lancement : remise à zéro »** (`.github/workflows/lancement-remise-a-zero.yml`, `workflow_dispatch` seulement ; aucun autre workflow ne le lance, testé) et le script `npm run lancement:remise-a-zero` (`apps/api/scripts/remise-a-zero.ts`).
- **Tables vidées** (la liste est **calculée du schéma**, `apps/api/src/remiseAZero.ts` ; l'essai à blanc et le résumé les nomment avec leur contenu) :
  | table | contenu |
  |---|---|
  | `players` | identités, pseudos réservés, comptes (tous les jeux) |
  | `revoked_codes` | codes de transfert révoqués (empreintes) |
  | `rate` | compteurs de débit (empreintes d'adresses et d'identifiants) |
  | `results` | DailyTrack : meilleurs temps, rediffusions (fantômes), places finales |
  | `salon_runs`, `salon_sessions`, `salon_circuits`, `salon_presence`, `salon_throttle` | le Salon et ses sessions |
  | `jump_results` | DailyJump : meilleurs essais, rediffusions (fantômes), places finales |
  | `jump_lives`, `jump_deaths` | DailyJump : vies de chaque joueur, cartes des morts et échantillons du carnage |
  | `meta` (une clé) | le rapport de la migration des pseudos (`pseudo_migration`) est effacé |
  Les **caches du portail et du classement du jour** (en mémoire, par instance) sont vidés par le changement de génération (§ 3) : ce ne sont pas des tables. « Effacements en attente » : il n'y en a pas en base (l'effacement d'un joueur, lot R5, est immédiat).
- **Gardé** : `planning` (le planning de DailyTrack, administration), `circuits` et `jump_levels` (caches de niveaux déterministes), `meta` (empreinte du schéma ; la génération y est écrite), les jours figés (fichiers de l'image) et la configuration. Le test `remiseAZero.test.ts` échoue si une table du schéma n'est ni dans `TABLES_VIDEES` ni dans `TABLES_GARDEES`, si une liste cite une table disparue, ou si une table gardée a une colonne qui nomme un joueur, un pseudo ou une rediffusion ; **règle ajoutée au `CLAUDE.md` racine** : toute nouvelle table liée à un joueur rejoint cette liste et l'effacement d'un joueur.
- **Gardes du workflow** (étape « Gardes », simulée sans secrets par `apps/portail/test/lancement.test.ts`, puis refaites par le script avec `refusDesGardes`) : (1) **deux confirmations saisies** : le nom de la base (celui de Turso, ou le premier mot complet de l'adresse) et la phrase « tout le monde repart de zéro » ; (2) **la production seulement depuis `main`**, après la **validation de Nathan** (environnement GitHub `production`), avec la case **« sauvegarde faite »** cochée (la sauvegarde est une étape de Nathan sur son ordinateur : commande `turso db shell dailytrack-misterzcool .dump` dans la liste de contrôle) ; (3) **la production exige que le serveur déployé serve une date de lancement d'aujourd'hui ou de demain** (`lancement` de `GET /api/portail/jour`, `refusDuLancement`) ; (4) **la règle des noms de base** (« recette » dans le nom d'une base de recette, jamais dans celui d'une base de production, jamais la même) ; (5) sans configuration : refusé, avec la raison (rien n'est vidé). Option **« essai à blanc »** : compte les lignes, n'écrit rien. Le jeton de la base est lu dans Secret Manager (production `cdj-turso-token`, recette `cdj-recette-turso-token`), masqué, jamais écrit ; refus de permission = la commande à lancer une fois est dans le résumé.
- **Aucune donnée personnelle ne sort** : le résumé et les journaux ne portent que des noms de tables et des nombres de lignes (test : le résumé ne contient pas le pseudo de la base d'essai) ; aucun artefact (testé : pas de `upload-artifact`) ; le dépôt est public.
- **Après** : attente de 40 s (les instances lisent la génération au plus toutes les 30 s), puis **`smoke --lecture-seule --vide`** contre le **service** (Cloud Run, pas Hosting : son cache public garderait 30 à 60 s l'ancien classement) — génération annoncée, aucun classé aujourd'hui dans Track, Jump ni au classement du jour du portail, aucune mort (`verifierVide`, `apps/api/scripts/smokeRead.ts`, testé : échoue tant que la base n'est pas vidée). **Vidage des caches des instances : par la génération de données** (choix justifié) — chaque instance lit `meta.generation` au plus toutes les 30 s (une ligne) et, si elle a changé, oublie sa mémoire (`onErased` des jeux, `portail.oublier`). Le redémarrage de la révision a été écarté : `gcloud run services update` crée une révision à partir du modèle du dernier déploiement (qui peut être celui d'une PR), et la recette épingle son trafic sur une révision nommée.

## 3. Les navigateurs repartent de zéro
- **La génération de données** : `meta.generation` (l'instant de la remise à zéro en ms ; 0 tant qu'il n'y en a pas eu), servie par `GET /api/portail/jour`, la lecture regroupée de DailyJump (`bundle`) et `GET /api/day/<date>` de DailyTrack.
- **L'effacement local, une seule fois pour les trois applications** : `packages/profile/src/generation.ts` (`initialiserGeneration`, `appliquerGeneration`, `lireNouveauDepart`, `CLES_GARDEES`). Un navigateur qui garde une génération plus ancienne efface **toutes** ses clés `cdj:*` et `jump:*` (identité, pseudo, révision d'identité, historiques et séries, records, rangs, envois en attente, mémoire du jour, Garage, aide vue) **sauf** la langue, le son, les commandes, les réglages d'affichage et de jeu, la qualité, la caméra, les outils d'essai et d'administration ; puis recharge la page. Le portail, Track et Jump l'appliquent sur la réponse qu'ils lisent déjà (aucune requête de plus). Un navigateur sans donnée de jeu est « neuf » (marqué avant que l'application écrive quoi que ce soit) : il adopte la génération sans message. Une génération plus ancienne ou égale n'efface jamais rien ; si le stockage ne retient pas la nouvelle génération, rien n'est effacé (pas de boucle de rechargement).
- **Le message** : « Nouveau départ : tout le monde repart de zéro. Bonne chance ! » / “Fresh start: everyone begins from zero. Good luck!” (`nouveauDepart.message`, catalogue commun, `npm run traductions` relancé), composant `avisNouveauDepart` du socle, sur l'accueil de chaque application, **une seule fois**.
- **`unknown_player` n'est plus un état d'erreur** : le jeu s'ouvre en joueur neuf, sans message ni texte d'erreur (le catalogue dit « Ce profil n'a encore aucun résultat. », et aucun écran ne l'affiche en alerte) ; vérifié par l'e2e sur les trois applications.
- **Mentions légales** (règle de fidélité) : les deux pages (fr, en) nomment `cdj:generation` et `cdj:nouveau-depart` (test de `mentions.test.ts`).

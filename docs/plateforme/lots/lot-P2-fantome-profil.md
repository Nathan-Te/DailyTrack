## Routes et règle de fusion
- **`GET /api/jump/day/<date>/ghost/first`** : la rediffusion du premier (règle du P1 : temps, premier envoyé, identifiant), pseudo, temps et morts rejoués, versions, `mine` (avec `X-Player-Id`). Jamais l'identifiant du premier. 404 `no_ghost` sans classé. Lecture comptée en mémoire ; un jour passé, figé, est gardé en mémoire (oublié à un changement de pseudo ou de code).
- **`GET /api/jump/me`** (`X-Player-Id`) : chaque jour classé (temps rejoué, morts de cet essai, médaille), jours, médailles, série ; 404 inconnu, **410 code révoqué**. **Un profil par jeu** : le `GET /api/me` de DailyTrack ne change pas (test : un joueur des deux jeux reçoit la même réponse qu'avec DailyTrack seul).
- **Fusion** (`apps/jump/src/jumpProfile.ts`, pure) : par jour, **le temps le plus court gagne** (avec sa médaille) ; **morts et essais du jour : la valeur locale** (seul l'appareil les connaît jusqu'au lot P3) ; un jour **seulement sur le serveur** est ajouté (morts de l'essai classé, un essai) ; rien n'est supprimé (un jour dont l'envoi est en file reste local) ; la série se calcule sur l'historique fusionné. Au chargement, au retour sur l'accueil (≤ 1 fois / 30 s), après chaque envoi accepté. `ProfileSync` de `@cdj/profile` est devenu générique sur le profil du jeu (DailyTrack : mêmes types, même comportement).
- **Charger un code dans DailyJump** : `writeIdentity` (`cdj:player`, `cdj:name` : DailyTrack la retrouve) ; DailyJump oublie ses rangs connus et les jours passés de l'ancienne identité, garde aujourd'hui et la mémoire du jour (son meilleur essai part au nom du profil chargé, comme le record du jour de DailyTrack).

## `recette:seed` automatique
`.github/workflows/recette-seed.yml` (+ `apps/api/scripts/recette-seed-auto.sh`) : **chaque jour** à 00:17 UTC, et **après chaque déploiement d'une révision de recette** (job `seed` de `recette.yml` ; job `recette-seed` de `production.yml`, que la production n'attend pas). **Aucun secret GitHub de plus** : fédération d'identité du workflow « Recette » ; le jeton de la base de recette est lu dans Secret Manager, masqué. **Garde** : seulement `RECETTE_TURSO_DATABASE_URL`, différente de la base de production, nom contenant « recette » (workflow, script, puis `recetteSeedTarget`, qui exige `ENVIRONMENT=recette`). **Il faut une commande, une fois** (le compte `cdj-deploy` ne lit pas encore ce secret) :
```bash
gcloud secrets add-iam-policy-binding cdj-recette-turso-token --member=serviceAccount:cdj-deploy@dailytrack-511513.iam.gserviceaccount.com --role=roles/secretmanager.secretAccessor
```
Sans elle, le job reste vert et l'écrit (« non lancés » + la commande). Vérifié en local : le script complet contre un `sqld` nommé « recette » (19 pilotes sur 2 jours, 19 joueurs DailyJump, 7 s) ; refus d'une base sans « recette » ; droit manquant → message, sortie 0.

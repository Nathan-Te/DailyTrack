Branche `claude/p4-consolidation-ijruau`, PR brouillon #82. Aucune fonction nouvelle : moins de requêtes, des alertes de coût, la production vérifiée après chaque déploiement, le cache de DailyTrack suivi au changement d'identité, de la marge pour le carnage, la synthèse de la plateforme (`docs/plateforme/synthese.md`).

## Ce qui a été fait
- **Lecture regroupée** `GET /api/jump/day/<date>/bundle` : classement (ta ligne), fantôme du premier (`null` sans classé), carte des morts, et **le profil DailyJump du jour** avec `X-Player-Id` (décision 1). Les routes séparées restent. **L'envoi rend le classement** (`board`). Le jeu (`dayReads.ts`) lit le jour en une requête, jamais deux fois en moins de 30 s, à l'arrivée seulement après 3 min, rien après un envoi (sauf le profil d'un joueur que le serveur découvre) ; repli sur les routes séparées face à un serveur plus ancien (**vérifié en vrai** : un aperçu en cache visait la recette par défaut, sans `bundle`).
- **Cache** (`cache.ts`) : jour fermé `max-age=86400`, jour ouvert `max-age=30`, **`private` + `Vary: X-Player-Id` pour tout ce qui dépend du joueur** (`private` seul : le navigateur resservirait la ligne d'une ancienne identité après un code chargé ; `Vary` seul : un cache partagé garderait des réponses personnelles indexées par l'identifiant secret) ; profil du jour `private, no-cache` ; DailyTrack inchangé (`no-store`).
- **Coûts** : `docs/plateforme/couts.md` (budget 5 € à 50/90/100 %, Turso, décisions écrites à l'avance) ; `npm run measure:platform -w @cdj/api -- --jump N --track N --salon N` (`scripts/platformBudget.ts` : chaque coût unitaire avec sa source).
- **Production vérifiée** : `smoke --lecture-seule` (GET seulement, sans identifiant, rien n'est écrit ; **seul mode permis contre la production**, le mode complet la refuse) ; `production.yml`, job `verification` après le déploiement : rouge au moindre échec, résumé avec route, réponse et commande de retour arrière.
- **Révision d'identité** (`@cdj/profile`) : `cdj:identite:rev` / `cdj:identite:code`, avancée par toute création, rotation, code chargé ; DailyTrack (`followIdentityRevision`) et DailyJump (`followJumpIdentity`) la lisent au démarrage ; **seul un code chargé ailleurs** vide le cache (décision 2).
- **Carnage adaptatif** (`carnageGovernor.ts`) : 150 → 100 → 60 vies, puis particules ½, puis 0, sur les 5 premières secondes (travail > 12 ms par image ou < 50 i/s) ; compteur exact ; ton carnage jamais allégé.

## Le joueur type et l'offre gratuite, avant / après
`npm run measure:jump-api -w @cdj/api` (sqld local, 19/10/2026 ; mêmes hypothèses qu'au P3 : 2 chargements, 4 arrivées dont 2 envois, 1 pseudo, 30 morts envoyées en 3 lots, carnage ×2, 30 jours d'historique) :

| DailyJump, une journée | requêtes | pré-vols CORS (2 visites > 2 h) | total Cloud Run | lignes lues | écrites |
|---|---|---|---|---|---|
| P3 | 30 | ≈ 11 | ≈ 41 | 1 252 (P3) | 32 |
| **P4** | **12** | ≈ 7 | **≈ 19** | 1 120 | 32 |

Lecture regroupée : 8 à 11 instructions, ≈ 150 lignes lues (profil de 30 jours compris), 0 écrite, 4,9 ko ; l'envoi qui rend le classement : +1 instruction, ≈ +20 lignes lues. **Les pré-vols** (OPTIONS) n'avaient jamais été comptés : Cloud Run les facture comme des requêtes.

**Seuil de l'offre gratuite, DailyJump seul** : en ne comptant que les requêtes (méthode du P3) **2 231 → 5 561** joueurs/jour ; pré-vols compris **1 631 → 3 511** ; mais **le premier plafond est le calcul facturé de Cloud Run** (borne haute de `measure:budget` : 100 ms par requête) : **≈ 1 430 → ≈ 3 100** joueurs/jour. **Avec DailyTrack** (`measure:budget` : 13 requêtes par joueur du jour, profil compris ; Salon : 558 par demi-heure ; `measure:salon` : une instance tient ≈ 770 joueurs du Salon à 50 %) : `measure:platform -- --jump 1000 --track 300 --salon 20` → 53 % des requêtes, **81 % du calcul** (marge ×1,2) ; le Salon pèse autant que 1 000 joueurs de DailyJump ; 100 joueurs × 30 min de Salon par jour dépassent seuls le calcul gratuit (≈ 2,7 $ par mois au-delà).

## Le carnage, mesuré (méthode des lots 3 et P3)
`MESURE=1 npx playwright test mesure-carnage -g "adaptatif" --project=chromium` (téléphone 844 × 390 @2, SwiftShader, 4 cœurs ; image estimée à 60 i/s = 2 pas + 1 dessin), **après un carnage d'échauffement** : la partie jouée pas à pas sans rendu laisse les fanions des points de passage jamais dessinés, dont les programmes se compilent pendant la fenêtre mesurée (≈ 0,3 s en rendu logiciel) — **la mesure du P3 (15,35 ms à ×4) comptait cette compilation**. Même machine, méthode du P3 sans échauffement : 26,3 ms à ×4.

| Processeur | Palier | Vies · particules | En course | Simulation / pas | Dessin / image | **Image estimée** |
|---|---|---|---|---|---|---|

**Marge à ×4 : au moins 5,4 ms sous 16,7 ms** à tout palier (objectif : 2 ms). La simulation baisse nettement avec les vies (1,01 → 0,36 ms par pas) ; le dessin, dominé par le niveau, bouge peu et reste bruité (rendu logiciel) : ordres de grandeur, non vérifiés sur un vrai téléphone. Le gouverneur choisit le palier 4 en SwiftShader (moins de 50 i/s même à ×1, ce que fait un appareil sans processeur graphique).

## Date du lancement public

- **Date du lancement public (lot R8) — une seule source** : **`config/lancement.json`** (`{ "premierJour": "AAAA-MM-JJ" }`, aujourd'hui le lundi 26/10/2026 : la journée n° 1). Le serveur (`journee` de `GET /api/portail/jour` et du classement, `lancement` pour le workflow de remise à zéro), le portail (numéro affiché sans attendre le serveur, ligne `Du Jour #N`, jours du classement) et les deux jeux (archives : elles commencent à la journée n° 1) la lisent par `@cdj/core/lancement` (`PREMIER_JOUR_DU_JOUR`, `numeroDeJournee`, `premierJourDuJour(surcharge)`) : **jamais une copie ni une date écrite en dur** (testé : `apps/portail/test/jours.test.ts`). La déplacer = changer cette seule ligne (PR d'une ligne, puis « Mettre en production »). La recette et les aperçus peuvent l'essayer un autre jour (variable du dépôt `RECETTE_PREMIER_JOUR` → `LANCEMENT_PREMIER_JOUR` du serveur et `VITE_LANCEMENT_PREMIER_JOUR` de la construction) ; **la production les refuse** (`config.ts`, `scripts/site.mjs`). Les e2e épinglent leurs propres dates (`apps/web/playwright.config.ts`, builds de la CI) : voir `apps/web/CLAUDE.md`.

## Turso sobre

- **Turso sobre (lot R14)** — **le quota Turso du mois est commun à toutes les bases de l'organisation (offre gratuite : 500 M de lignes lues, 10 M écrites) : la recette peut bloquer la production** (29/10/2026 : 99 % du quota pris par la recette). **Turso compte les lignes *parcourues*, pas rendues** (un `SCAN` lit toute la table ; une écriture compte les index). Règles : (1) **les tests et les outils de mesure n'utilisent jamais Turso** (base `file:` ou mémoire ; `openLibsql` refuse une base distante sous Vitest ; `apps/api/test/pasDeTurso.test.ts` échoue si un test cite une adresse `libsql://`) ; (2) **un script qui vise une base distante (ou `smoke` complet contre un serveur déployé) exige `--distant`** (`apps/api/src/distant.ts`) ; (3) **`recette:seed` n'écrit que ce qui manque** (marqueurs `recette_seed:…` de `meta`, `--refaire` pour tout rejouer) et **ne tourne qu'au déploiement de la recette par défaut** (fusion dans `main`, puis chaque jour), jamais pour la révision d'une PR ; (4) **toute nouvelle requête vérifie son plan (`EXPLAIN QUERY PLAN`) et ses lignes lues** : `openTestDb` examine chaque requête du serveur que les tests font tourner et refuse un `SCAN` d'une grande table non justifié (`PARCOURS_PERMIS`, `apps/api/src/plans.ts`) ; `routesChaudes.test.ts` plafonne les lignes lues des routes les plus appelées (`npm run measure:lignes`). Détail : `apps/api/CLAUDE.md`, « Turso sobre (lot R14) » ; guide : `docs/plateforme/couts.md` § 10.

- **Flux** : PR (CI de PR) → **aperçu** (`apercu.yml`, ou `recette.yml` si la PR touche le serveur) → fusion → **recette** (`recette.yml` sur `main` : serveur, `recette:seed`, site) → bouton **« Mettre en production »** (`production.yml`, à la main, sur un commit de `main`) → production. **Plus aucun déploiement automatique de la production.** **Lot R12 — un seul bouton, une CI** : la CI complète du commit (ci.yml appelé, mode `complet`, sans aucun accès à la production ; reprise si un run complet vert de ce commit existe déjà ; rouge → arrêt et « Lance le lot de mise en production avec ce run : <lien> ») → **figer** (garde-fou) → **répétition** sur la recette → **sauvegarde** de la base (bucket privé, 30 jours) → serveur puis site (plus de « Review deployments » : le lancement vaut validation ; environnement `production` limité à `main`) → `smoke --lecture-seule` contre playdujour.com → étiquette `prod-AAAA-MM-JJ-HHMM` → jours figés **versés dans `main` par le workflow** → résumé (✅ / ⛔ et une phrase). Mode `essai` : tout contre la recette ; `repetition` : la répétition seule, heure simulée. Pas à pas en une page : `docs/plateforme/mise-en-production.md`. **Lot R16 — plus court** : le garde-fou (`figer`, lecture seule) et la répétition (la recette) tournent **en même temps que la CI** ; la sauvegarde part dès le verdict vert ; **le serveur de production exige explicitement, un par un, le verdict vert, le garde-fou, la répétition et la sauvegarde** (une nouvelle étape d'avant la production s'ajoute à ses `needs` et à son `if`, `ciComplete.test.ts`) ; les jours figés sont versés par un workflow à part, **« Jours figés dans main »** (`jours-figes.yml`, lancé par le job `depot`, entrées vérifiées), que le bouton suivant attend. Lot R5 : plus de redirection depuis GitHub Pages (`pages.yml` retiré).
- **Règle de bascule (lot R6, précisée au lot R11) — aucun jour protégé ne change jamais** : le **jour de bascule** est le premier jour de Paris qui commence **après le déploiement**, calculé **au moment du clic** (`scripts/mise-en-production.mjs bascule`, jamais écrit en dur). **Jours protégés** (décision de Nathan, lot R11) : les jours **antérieurs au lancement public** (`config/lancement.json`), les jours **déjà figés** et **les jours qui ont au moins un résultat en production** (Track ou Jump : lu **en lecture seule** sur le classement du jour, `GET /api/portail/classement?date=`, jamais en écrivant) ; leur carte est **exactement** celle que la production sert. **Un jour à partir de la journée n° 1 sans aucun résultat est traité comme non servi** : la mise en production le régénère avec le code déployé (au lancement : après la remise à zéro, la mise en production du 26 ou du 27 octobre régénère le 27 avec la dernière version, quelle que soit l'heure du clic) ; le jour de bascule et les suivants aussi. Le workflow de production le **vérifie avant de déployer** : il compare l'empreinte de chaque jour protégé (identifiant, contenu, temps de l'auteur, médailles) entre le code en production et la nouvelle construction, et **la moindre différence arrête la mise en production** (jours en cause dans le résumé) ; il relit les résultats des jours qu'il régénère juste avant de déployer (un résultat arrivé entre-temps arrête). **Un lot qui change un générateur ou une physique monte sa version et n'écrit plus aucune date** : c'est la mise en production qui décide du premier jour concerné. Guide en une page (le bouton, le résumé ; annexes : répétition seule, retour arrière, sauvegarde) : **`docs/plateforme/mise-en-production.md`**.
- **Les trois jeux figent leurs jours (lots R11 et R16)** : voir ci-dessous pour Track et Jump ; **Tower a un fichier par jour servi** (`apps/tower/public/jours/AAAA-MM-JJ.json`, sans exception : le job `figer` fige avec le code en production tout jour **protégé** qui n'a pas de fichier — `figer-jeux` (forme `jours-proteges` de sa fiche : `figer:tower` dans le dépôt de la production, **arrêt** s'il en manque un) —, avant la comparaison des empreintes, qui couvre aussi Tower) ; un jour de Tower sans fichier prend le générateur courant, donc un jour servi sans fichier changerait à la prochaine `TOWER_GENERATOR_VERSION`. **Changer le générateur de Tower = monter sa version et garder l'ancienne dans `GENERATEURS`** tant qu'un fichier la nomme (`apps/api/test/towerJoursFiges.test.ts`, générateur factice : aucun jour servi ne change). Ci-dessous, **les deux premiers** : **Jump** a un fichier par jour (`apps/jump/public/levels/AAAA-MM-JJ.json`, niveau complet et preuve) ; **Track** a un seul registre, `packages/sim/src/jours-track.json` (plages de jours protégés : version du générateur `g` et de la simulation `sim`), lu par `generatorVersionOf` — un jour qu'il ne nomme pas prend la dernière version ; **il n'y a plus de date de bascule dans le code** (`BASCULE_LOT_34/48/49` n'existent plus ; seule `BASCULE_LOT_35`, les facteurs des médailles d'avant le lot G1, reste ; **lot G1 : les médailles suivent la version, comme le circuit** — Track : celle du générateur du jour lue dans le registre, Jump : celle du niveau, figé avec ses médailles — : un recalibrage ne s'applique qu'à partir du jour de bascule, sans date écrite). Les trois sont écrits **par « Mettre en production »** (jamais par un lot), avec le code alors en production, et entrent dans l'image du serveur, le site **et** le dépôt (commit « Jours figés », versé dans `main` par le workflow : lot R12).
- **La chaîne de production lit les fiches (lot K4b)** : **comment un jeu fige, prépare et compare ses jours est dans sa fiche** (`jours.fabrication` : le module d'empreinte `apps/api/scripts/<id>-empreintes.ts`, le module de registre d'un jeu à registre, le script `figer` et sa forme, le script `preparer` avec sa fenêtre et son garde-fou, `apresPose`). `scripts/mise-en-production.mjs` (commandes `figer-jeux`, `preparer-jeux`, `poser-jours`, `empreintes`, `registre --jeu`, `jours-servis --jeu`…) et les workflows `production.yml`, `jours-figes.yml`, `deploy-api.yml` et `deploy-site.yml` **n'écrivent le nom d'aucun jeu** (testé : `apps/portail/test/workflows.test.ts`) : **un jeu neuf, avec sa fiche, n'ajoute aucune ligne à la chaîne**. Les jours de tous les jeux voyagent dans **un seul artefact `jours`** (un dossier par jeu, plus `proteges.json`) ; le job `figer` rend `jours` et `preparation` en JSON (`{ <jeu>: ligne }`, lus par `scripts/resume-bouton.mjs`). **Un lot qui touche `production.yml`, `jours-figes.yml`, `deploy-*.yml` ou `scripts/mise-en-production.mjs` ne se fusionne qu'après un essai du bouton sur sa branche, en mode `essai` puis `repetition`** (Nathan le lance ; marche : `docs/plateforme/mise-en-production.md`, annexe E).
- **Figer avec le code en production avant chaque mise en production** : le job `figer` lit les jours protégés (`proteges`), puis (`figer-jeux`) lance **sur le commit de la dernière étiquette `prod-…`** (le code que les joueurs ont) le script `figer` de la fiche de chaque jeu à fichiers (Jump : `freeze:days -- <veille du jour de bascule>`) (les niveaux des jours sans résultat sont retirés) et le calcul du registre des jeux à registre (Track : `generatorVersionOf` du code en production), avec d'abord les jours que la production sert déjà (`jours-servis` : les fichiers et le registre des commits « Jours figés » versés depuis), jamais sur le commit qu'on déploie ; les fichiers figés et le registre entrent dans l'image du serveur, le site **et** le dépôt (PR « robot » que le workflow fusionne lui-même dès sa CI verte, lot R12), avec les empreintes des jours passés protégés (`apps/api/test/jours-passes.json`). Un jour figé ne change jamais : un fichier ou une version différents arrêtent la mise en production. **Répétition** : « Mettre en production » en mode `repetition` fait tout contre la recette avec une heure simulée (rien n'est étiqueté ni fusionné).
- **Lancement public (lot R8)** : « Lancement : remise à zéro » (`lancement-remise-a-zero.yml`, à la main, recette ou production) vide la base le jour du partage ; pas à pas : `docs/plateforme/lancement.md` ; règles : `apps/api/CLAUDE.md`, « Lancement public et remise à zéro (lot R8) ». **Depuis le lot R6, « Mettre en production » est de nouveau permis** : il suit la liste de contrôle `docs/plateforme/mise-en-production.md` (garde-fou des jours, sauvegarde, répétition).
- **Retour arrière** : `retour-arriere.yml` (à la main, environnement `production`) : l'image et la version du site notées dans l'étiquette précédente, puis vérification, puis une nouvelle étiquette sur le commit remis.
- **Stockage** : production, recette et chaque aperçu sont des **origines distinctes** : le navigateur sépare leur stockage (plus de préfixe `apercu:` dans les déploiements). Les jeux appellent `/api/` sur leur propre origine (`VITE_API_URL=/`) ; les liens partagés sont construits sur l'origine courante.
- Sans Firebase configuré, toute étape Firebase est sautée avec « Firebase non configuré : voir docs/plateforme/domaine.md » et la CI reste verte. Un agent ne lance ni le bouton ni le retour arrière (403) : il prépare, Nathan clique.

## Un jour figé fige aussi ses seuils (lot « manques de Blocks »)
Le Diamant de Blocks est la partie d'un bot (`BLOCKS_BOT_VERSION`), l'or, l'argent et le bronze en sont des fractions : si le bot ou les fractions changent, les médailles des jours déjà servis changeraient. **Le fichier d'un jour figé (`apps/blocks/public/jours/AAAA-MM-JJ.json`, format 2) porte donc `seuils` (bronze < argent < or < Diamant, quatre entiers) et `bot`** ; `lireJourFige` rend un contenu qui porte `seuilsFiges`, `seuilsDuJour` (`@cdj/blocks-sim/diamant`) les préfère au calcul — le serveur (`seuilsDeBlocks`) comme le jeu (`corps.ts`). `npm run figer:blocks` (donc le job `figer`, avec le code **en production**) écrit les seuils que **ce** code calcule. **L'empreinte du jour couvre les seuils** : un jour protégé sans fichier voit son empreinte changer si le bot change, et la mise en production s'arrête (comme pour un générateur). Un changement du bot ou des fractions monte `BLOCKS_BOT_VERSION` (règle de `apps/blocks/CLAUDE.md`) ; il ne touche que les jours non figés. Même règle pour tout jeu dont les médailles se calculent. **Pas encore faite pour Cibles et Rush** (leur bot calcule encore les seuils à chaque lecture) : README du lot.

## Réparer un jour servi à tort (run 45, 09/11/2026) — `config/reparations-jours.json`
`servi-verifier` (« Mettre en production », lot 33) arrête si un jour figé n'est pas le niveau que la production sert **en ce moment**. Quand c'est la production qui sert à tort un niveau qui n'est pas celui que les joueurs ont joué (l'incident du 06/11/2026 : Jump du 03 au 06/11 servis avec les hashs `a1ecd408`, `87339d47`, `b3032d69`, `4aa5e402` au lieu de `be47f97c`, `3c564234`, `37283e5a`, `29108be0`), le garde-fou ne peut plus laisser passer le déploiement qui les répare : sans autre issue, il faudrait un retour arrière, qui renvoie aussi tout le code d'avant. **Une réparation se déclare** dans `config/reparations-jours.json` (`jeu`, `date`, `id`, `servi`, `fichier`, `pourquoi`) ; `comparerAuServi` l'accepte **seulement si** le serveur sert exactement l'empreinte `servi` ET le fichier figé a exactement l'empreinte `fichier`, avec le même identifiant. Tout autre écart arrête, et le résumé du run dit les jours réparés (« ♻️ »). Le test `apps/jump/test/jourServiChaine.test.ts` relit les fichiers figés du dépôt : un `fichier` déclaré qui n'est pas leur empreinte échoue. **Une entrée ne se déclare que pour remettre un jour à ce que les joueurs ont réellement joué, preuve à l'appui** (rapport du lot, comme `docs/jump/lots/lot-33-incident.md`) ; une fois le jour réparé (servi = fichier) elle ne sert plus et peut être retirée.

## Un jeu que la production ne sert pas n'a rien à conserver (run 46, 09/11/2026)
Les jours qu'un joueur a vus ne changent jamais ; un jeu `off` ou `preview` en production n'en a montré aucun. **Étape « Les jeux que la production ne sert pas »** (commande `non-servis`, lecture seule de `GET /api/jeux`, avant le figeage) : `figer-jeux` et `empreintes prod` laissent ces jeux de côté (`--non-servis`, rien à figer avec le code en production, aucune empreinte à comparer), et `comparer` les traite comme un jeu que le code en production ne connaît pas (lot TP) : leurs jours se régénèrent avec le nouveau code. Sans cela, tout changement de générateur d'un jeu en préparation (Blocks `g3` → `g6`, Rush `g2` → `g7`) arrêtait le bouton sur des jours que personne n'a vus. **En cas de doute on conserve** : seul un état explicitement `off` ou `preview` écarte un jeu (absent de la liste ou état inconnu = protégé), et une liste illisible arrête la mise en production. Le résumé du run dit l'état de chaque jeu. **Limite connue** : `GET /api/jeux` ne dit pas si un jeu a été `on` puis remis `off` (ses périodes sont dans l'administration) ; passer un jeu publié en `off` avant de changer son générateur le ferait traiter comme non servi — le garder `on` ou fixer une bascule.
**Repli du module d'empreinte** (`empreintesDuJeu`) : les modules d'empreinte d'aujourd'hui sont copiés dans le code en production et compilés avec ses paquets ; si l'un emploie une pièce que ce code n'a pas encore (Blocks : `seuilsDuJour` de l'index), le module que ce code a lui-même est utilisé à sa place (avertissement dans le journal) — `comparer` voit toute différence de forme comme un jour qui change, jamais comme un accord.

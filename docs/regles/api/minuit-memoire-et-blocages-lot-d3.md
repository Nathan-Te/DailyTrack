## Minuit, mémoire et blocages (lot D3)
README : `docs/plateforme/lots/lot-D3-serveur-minuit-memoire-blocages.md` ; enquête : `docs/plateforme/analyse-refus.md` (C8, C9, C10). Code : `src/mesures.ts`, `src/niveauxFil.ts` + `niveauxFilTravail.ts`, `preparerLeLendemain` d'`api.ts` ; tests : `mesures`, `niveauxFil`, `towerFil`, `admin` ; mesures : `npm run measure:minuit`, `measure:memoire` (`-w @cdj/api`).
- **Le niveau du lendemain est calculé avant minuit.** Dans la **demi-heure qui précède minuit de Paris**, la première requête qui arrive sur une instance lance, sans que sa réponse l'attende, `dailyLevel(demain)` de chaque jeu **ouvert** (`api.preparerLeLendemain()` ; un jeu `off` n'est pas préparé) : le calcul et l'écriture en base sont ceux de minuit, donc **aucun niveau ne change** (la règle de chaque niveau — versions, fichier figé — est vérifiée à la lecture comme avant) ; après minuit toute instance le lit en base. Pas de tâche de fond (Cloud Run) : une instance sans requête dans la demi-heure ne prépare rien, le premier joueur d'après minuit calcule alors dans le fil. Un échec est retenté au plus toutes les 2 min et ne casse jamais une requête.
- **Le calcul d'un niveau ne se fait plus dans le fil principal** : Jump (`computeJumpDay`, 1,9 s) et Track (`dailyCircuit`, 0,4 s) passent par `calculerNiveau` (`niveauxFil.ts`, pur) dans **un fil de calcul** (`dist/niveaux-fil.mjs`, posé à côté de `server.mjs` par `build-node.mjs` et le `Dockerfile` ; `server.ts` le charge s'il est là, sinon repli sur place, comme avant). Ce qui traverse le fil est des données (le circuit de Track est reconstruit par `parseTrack`). **Un nouveau calcul de niveau long passe par `calculerNiveau`** (une demande de plus dans `DemandeNiveau`). **Piège (trouvé par le smoke de l'image, `api-image`)** : un fil n'a pas l'état de module du fil principal — le thème d'un jour de Jump dépend de `declareFrozenGenerators` (les niveaux figés de l'image) ; sans elle le fil calculait **un autre niveau**. Tout état que le calcul lit hors de ses arguments **voyage avec la demande** (ici `generateurs`) ; `niveauxFil.test.ts` le prouve (le niveau du fil diffère sans la déclaration).
- **L'examen d'un jour préparé de Tower passe par le fil de Tower** (`examinerParLeFil`, même fil que les rejeux) : Rapier n'est plus chargé que dans le fil de calcul de l'instance (jamais aussi dans le fil principal) et l'examen de la preuve (0,4 à 1 s) ne bloque plus personne.
- **Un rejeu ne garde aucune mémoire après sa réponse.** Mesuré (`measure:memoire`, 1 000 rejeux de chaque jeu, `rss`/`external`/tas après ramasse-miettes) : le tas JS, `external` et la mémoire WebAssembly de Rapier sont plats ; seul le `rss` de Tower monte d'une centaine de Mo pendant les ~100 premiers rejeux (le compilateur du WebAssembly optimise Rapier) puis reste sur son plateau. Un test ou un lot qui ajoute un rejeu n'a le droit de **ni garder la rediffusion, ni le monde, ni un cache sans plafond** ; Tower libère son monde (`Partie.dispose`).
- **Les mesures** (`mesures.ts`, créées par `server.ts`, sans donnée personnelle, volume borné) — **lire en production** : Cloud Run › `cdj-api` › Journaux, filtre `jsonPayload.message="boucle d'événements"` (un relevé par minute et par instance qui sert : `p50Ms`, `p99Ms`, `maxMs`, `maxEnRequeteMs`, `requetes`, `gcMaxMs`, `rssMo`, `tasMo`) ; `jsonPayload.message="blocage de la boucle d'événements"` (un écart > 1 s : `retardMs`, `cpuMs`, **`type`** `calcul` = le fil de Node était occupé, `attente` = il n'a rien consommé — gel du conteneur hors requête ou hôte lent —, `enRequete`, `routes` = ce qui tournait) ; `jsonPayload.message="envoi lent"` (un envoi > 3 s : `lectureMs`, `controlesMs`, `rejeuMs`, `ecritureMs`, `sqlMs`, `sqlN`, `retardBoucleMs`) ; `jsonPayload.message="ramasse-miettes long"` (> 500 ms) ; `jsonPayload.message="niveau du lendemain prêt"` (la préparation d'avant minuit). Les étapes sont posées par la plateforme (`readJson` → contrôles, `spendReplays` → rejeu, première écriture qui suit → écriture) : un jeu n'a rien à marquer. `GET /api/admin/tableau` rend `etat.instance` (mémoire de l'instance qui répond et plus grand retard de boucle pendant une requête, 24 h) quand l'instance est mesurée.
- **Les tests des mesures injectent leurs durées ; un vrai chronométrage est un outil, jamais dans la CI** (lot D3b : `typeDeBlocage`, `analyserPassage` et `cpuDuFil` sont purs ; `creerMesures` prend `horloge` et `cpu` et rend `passage` / `releve` pour piloter la sentinelle sans minuteur).

## Publication des jeux (lot P)
README : `docs/plateforme/lots/lot-P-interrupteur-des-jeux.md` ; règles communes : `CLAUDE.md` racine, « Publication des jeux (lot P) » ; marche à suivre : `docs/mise-en-ligne.md`. Code : `src/jeux.ts` (`createJeux`), logique pure `packages/core/src/jeux.ts` (`@cdj/core/jeux`), garde dans `api.ts`, état lu par `portail.ts` ; tests `test/jeux.test.ts` (SQLite **et** libSQL `file:`, jamais Turso), `packages/core/test/jeux.test.ts`, e2e `jeux-interrupteur.spec.ts`.
- **Table `jeux`** (`PLATFORM_SCHEMA`, migration **réversible** : `DROP TABLE jeux`, `ALTER TABLE results|jump_results DROP COLUMN apercu`) : une ligne par jeu, nommé par son dossier sur le site (`track`, `jump`, pas le code du registre `cdj`) = `etat` (`off` | `preview` | `on`), `live_from` (jour de Paris), `periodes` (JSON `[[du, au|null], …]` : les jours où le jeu compte dans la journée), `cle_hash` (SHA-256 de la clé d'aperçu, **jamais la clé**), `cle_creee_le`, `modifie_le`. **Un jeu sans ligne (ou à l'état illisible) vaut `off`** (test). Track et Jump sont semés `on` **une seule fois, par le schéma** (`semerJeux` de `db.ts`, drapeau `meta.jeux_semes` : une lecture n'écrit jamais ; `INSERT OR IGNORE`, jamais en écrasant un choix). **Gardée** par la remise à zéro (`TABLES_GARDEES` : aucune donnée de joueur). Mentions légales : la table est décrite (`data-tables`) dans les deux pages, et la clé `cdj:apercu:<jeu>` nommée.
- **La garde** (`api.ts`, avant chaque route d'un jeu ; sauf `/api/admin/…`, la porte des outils de DailyTrack) : `interrupteur.garde(site, req)` → `on` ; `preview` avec la bonne clé (`X-Preview-Key`, empreinte comparée à temps constant) ; **un aperçu de PR** (recette et local, **jamais la production** : `Origin`, `X-Forwarded-Host` ou `X-Fh-Requested-Host` de la forme `<site>--pr-<n>-<empreinte>.web.app`) ouvre aussi un jeu `off` ; sinon **`404 game_unavailable`** (liste unique des codes, `erreur.game_unavailable` fr + en). Une clé n'ouvre jamais un jeu `off`. En aperçu, une **écriture** n'est permise que si le jeu la déclare (`GameInstance.ecrituresApercu` : Track `/api/submit`, Jump `/api/jump/submit`), sinon `game_unavailable` ; le jeu reçoit `info.apercu = true` et **range le résultat à part** : `apercu = 1` et `hidden = 1` (tous les classements écartent `hidden = 1`), sans jamais remplacer ni être remplacé par une ligne publique du même joueur ; `viderApercu` (instructions SQL) efface ces lignes **dans la transaction** qui passe le jeu à `on` (un résultat d'aperçu ne devient jamais public).
- **Cache** : l'état est lu en mémoire, par instance, au plus toutes les 30 s (`JEUX_TTL_MS`), relu tout de suite après un changement fait par cette instance ; `GET /api/jeux` → `{ jeux: { track: "on", … } }`, `public, max-age=0, s-maxage=30` (le cache de Firebase Hosting) ; sur un aperçu de PR `{ …, apercu: true }` en `no-store`. **Coût (calculé, non mesuré sur Turso : pas de `sqld` ici)** : une instruction et 2 lignes lues par instance et par 30 s d'activité (toutes les routes d'un jeu partagent la même lecture), aucune écriture ; `GET /api/jeux` : 1 requête par ouverture d'un jeu, servie par le cache de Hosting (≤ 120 par heure et par point de présence), 0 instruction hors lecture périodique. **Délai d'un changement : 30 s au plus** pour les pages des jeux, **jusqu'à 60 s** pour l'accueil (`GET /api/portail/jour`, cache public de 60 s, par conception).
- **Administration** (`/api/admin/jeux`, session et `X-Cdj-Admin`, `confirmer: true`) : `GET` (états, périodes, `liveFrom`, clé présente ou non — jamais sa valeur), `POST jeux/<jeu>/etat { etat }`, `POST jeux/<jeu>/cle` (génère : 192 bits tirés au hasard, **rendue une seule fois**, remplace la précédente), `POST jeux/<jeu>/cle/revoquer`. **Chaque changement est inscrit au journal dans la même transaction**, sans donnée personnelle (jeu, état avant / après, jamais la clé ni son empreinte) ; un changement vers le même état n'écrit rien. Les caches du portail de l'instance sont vidés (`oublier`).
- **La journée** (`portail.ts`) : `compteLe(jeu, jour)` (périodes) décide de ce qui compte pour la série, la journée parfaite (`serieEtParfaites`, option `compte`), le cumul et les vues du classement du jour (un jeu qui ne compte pas ce jour-là n'a pas de vue : `invalid_view`) ; `GET /api/portail/jour` ne liste que les jeux `on` (tous, marqués `brouillon`, pour un aperçu de PR) avec **`compte`** : faux le jour de l'activation. Le profil commun ne liste que les jeux `on`. Règle des périodes (`periodesApres`) : activer ouvre une période **demain** (réactivation le jour même d'une désactivation : elle se rouvre, aucun trou) ; désactiver ferme la période **demain** (le jeu compte encore aujourd'hui côté serveur : classement du jour et séries) ; activé puis désactivé le même jour : aucune période. **Limite assumée** : le jour de la désactivation, l'accueil n'a déjà plus le jeu (`jeux[]`) alors que `aujourdhuiParfaite` le compte encore.
- **Un nouveau jeu** : rien de plus à écrire côté API que le registre (recette de « Plateforme (lot P0) ») ; s'il écrit des résultats d'un joueur, il lit `info.apercu` (voir `cdj.ts`, `jump.ts`) et déclare `ecrituresApercu` et `viderApercu`. Un test qui a besoin d'un faux jeu n° 3 l'ouvre à la main (`ouvrirJeu`, `test/helpers.ts`).

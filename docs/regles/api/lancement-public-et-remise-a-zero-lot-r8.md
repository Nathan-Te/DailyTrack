## Lancement public et remise à zéro (lot R8)
README : `docs/plateforme/lots/lot-R8-lancement.md` ; liste de contrôle de Nathan : `docs/plateforme/lancement.md`. Code : `src/remiseAZero.ts` (le plan, la remise à zéro, les gardes), `scripts/remise-a-zero.ts` (`npm run lancement:remise-a-zero`), `.github/workflows/lancement-remise-a-zero.yml` ; tests `test/remiseAZero.test.ts` (SQLite **et** libSQL), `apps/portail/test/lancement.test.ts` (le workflow et la liste de contrôle).
- **La date du lancement** : une seule source, `config/lancement.json` (voir le `CLAUDE.md` racine) ; le serveur la prend de `@cdj/core/lancement` (`createApi({ premierJourDuJour })` pour les tests ; `LANCEMENT_PREMIER_JOUR` pour la **recette et le local seulement**, **refusée en production** par `readConfig`). Le fichier entre dans l'image (`COPY config config`) et dans les chemins qui déclenchent la recette (`SERVER_PATHS`, `recette.yml`). `GET /api/portail/jour` rend `lancement` (AAAA-MM-JJ) : c'est ce que le workflow de la production lit pour s'assurer qu'il est aujourd'hui ou demain. **Depuis le lancement** (la date est passée), `GET /api/portail/classement?date=` refuse un jour d'avant (404 `unknown_day`) ; avant lui rien n'est refusé (période d'essai).
- **La remise à zéro** (`remiseAZero(db, { now, applique })`) : **en une transaction** (`SqlDb.batch`), `DELETE` de chaque table de `TABLES_VIDEES`, effacement des clés de `meta` qui nomment d'anciens joueurs (`pseudo_migration`), et écriture d'une **nouvelle génération de données**. **La liste est calculée du schéma** (`planDeRemiseAZero` lit les `CREATE TABLE` de `SCHEMA` : plateforme + chaque jeu du registre) : **chaque table est ou vidée (`TABLES_VIDEES`, elle tient une donnée de joueur ou de partie) ou gardée (`TABLES_GARDEES` : `planning`, `circuits`, `jump_levels`, `meta` — le planning de l'administration, deux caches déterministes, la table de service)** ; le test échoue pour une table du schéma classée nulle part (ou citée à tort), et pour une table gardée qui a une colonne nommant un joueur, un pseudo ou une rediffusion. **Toute nouvelle table liée à un joueur rejoint `TABLES_VIDEES` — et le crochet `erase` de son jeu** (effacement d'un joueur). Ne rend que des **nombres de lignes** : rien de personnel (le dépôt est public, les journaux aussi). Les jours figés (fichiers) et la configuration ne sont pas dans la base.
- **La génération de données** : `meta.generation` = l'instant de la remise à zéro en millisecondes (croissant : toujours supérieur à la précédente ; 0 tant que la base n'a jamais été remise à zéro). `Platform.generation()` la lit **au plus toutes les 30 s par instance** (`GENERATION_TTL_MS`, une ligne), `api.ts` l'appelle au début de chaque requête ; **quand elle change, l'instance oublie sa mémoire** (`onGenerationChange` → `onErased` de chaque jeu et `portail.oublier` : classements gardés, premier d'un jour fermé, cartes des morts) — **pas de redémarrage de révision** (décision justifiée : `gcloud run services update` créerait une révision à partir du modèle du dernier déploiement, qui peut être celui d'une PR, et la recette épingle son trafic sur une révision nommée ; la lecture de la génération vide la mémoire de toutes les instances, sans rien redéployer). Elle est **servie** par `GET /api/portail/jour` (`generation`, partie publique, cache 60 s), la lecture regroupée de DailyJump (`bundle`) et `GET /api/day/<date>` de DailyTrack : un navigateur en garde une plus ancienne = il repart de zéro (`packages/profile/CLAUDE.md`, « Nouveau départ »). Un cache qui rend une vieille réponse ne vide jamais un joueur neuf (la génération est monotone côté navigateur). **Coût** : une ligne lue par instance et par 30 s d'activité, aucune écriture.
- **Le workflow « Lancement : remise à zéro »** (`workflow_dispatch` seulement, aucun autre workflow ne le lance) : cible `recette` ou `production`, **deux confirmations saisies** (le nom de la base : celui de Turso ou le premier mot complet de l'adresse — `nomDeBaseCorrespond` ; la phrase « tout le monde repart de zéro »), `sauvegarde_faite` (exigée pour la production : la sauvegarde est une étape de Nathan sur son ordinateur, commande exacte dans `docs/plateforme/lancement.md`), `essai_a_blanc` (compte, n'écrit rien). **Gardes** (étape « Gardes », testée en bash sans secrets, puis refaites par le script) : production **depuis `main` seulement**, après la validation de Nathan (environnement `production`) ; **la règle des noms de base** (« recette » dans le nom de la recette, jamais dans celui de la production, jamais la même base) ; **la production exige que le serveur déployé serve une date de lancement d'aujourd'hui ou de demain** (`refusDuLancement`, lu sur `https://playdujour.com/api/portail/jour`). Le jeton de la base est lu dans Secret Manager (production `cdj-turso-token`, recette `cdj-recette-turso-token`), masqué, jamais écrit ; `PERMISSION_DENIED` = la commande à lancer une fois est donnée dans le résumé. **Aucun artefact, aucun journal personnel.** Après : attente de 40 s (la génération est lue au plus toutes les 30 s), puis `smoke --lecture-seule --vide` **contre le service lui-même** (pas Hosting, dont le cache garde 30 à 60 s l'ancien classement) : génération annoncée, aucun classé aujourd'hui dans les deux jeux ni au classement du jour du portail, aucune mort. Un `recette:seed` (cron de 00 h 17 UTC, déploiement) qui passe entre la remise à zéro et la vérification peut la faire échouer : relancer.
- **`LANCEMENT_PREMIER_JOUR`** (recette) : posée par `deploy-api.yml` depuis la variable du dépôt `RECETTE_PREMIER_JOUR` (la production ne la reçoit jamais) ; `deploy-site.yml` pose `VITE_LANCEMENT_PREMIER_JOUR` pour la recette de même.

## Moins de requêtes, coûts et vérification de la production (lot P4)
README : `docs/plateforme/lots/lot-P4-consolidation.md`. Synthèse de la plateforme : `docs/plateforme/synthese.md`. Guide des coûts : `docs/plateforme/couts.md`.
- **`GET /api/jump/day/<date>/bundle`** (la **lecture regroupée**, `jump.ts`) : `{ date, open, board, ghost, deaths }` — les réponses mêmes de `/board` (ta ligne avec `X-Player-Id`), de `/ghost/first` (`null` sans classé, au lieu de 404) et de `/deaths` — et, **avec `X-Player-Id` pour le jour en cours**, `profile` (celui de `/api/jump/me`) ou `profile: null` + `profileError` (`unknown_player`, `code_revoked`). **Une seule adresse par jour** pour toutes les lectures personnelles : un seul pré-vol CORS par 2 heures. L'échantillon du carnage reste à part (lourd, pas toujours regardé). Les routes séparées restent (compatibilité, `smoke`, repli du jeu face à un serveur plus ancien). Lecture comptée en mémoire, n'écrit rien. **`POST /api/jump/submit` rend aussi `board`** (le classement juste après l'envoi : le jeu ne relit rien).
- **Règle des en-têtes de cache** (`cache.ts`, `WithHeaders` + `cacheHeaders`) : par défaut toute réponse est `no-store` (DailyTrack ne change pas) ; une lecture de jeu peut porter son cache : **jour fermé** (après la grâce) `max-age=86400`, **jour ouvert** `max-age=30`. **Jamais en cache partagé quand la réponse dépend de `X-Player-Id`** : `private` **et** `Vary: X-Player-Id` (`private` seul laisserait le navigateur resservir la ligne d'une ancienne identité après un code chargé ; `Vary` seul laisserait un cache partagé garder des réponses personnelles indexées par l'identifiant secret). Le profil du jour (`bundle` avec identifiant) : `private, no-cache` (un code changé ailleurs se voit au chargement suivant). Niveau, carte, échantillon : `public`. `Vary: Origin` de CORS est fusionné (`mergeVary`). Erreurs et envois : `no-store`.
- **Pré-vols CORS** (OPTIONS) : toute requête avec `X-Player-Id` ou un corps JSON en déclenche un, gardé **par adresse** 2 heures par Chrome (`Access-Control-Max-Age` est plafonné) ; Cloud Run les compte comme des requêtes. **Tout nouveau point d'accès les compte dans son coût** ; regrouper les lectures personnelles sous une seule adresse en évite.
- **`smoke --lecture-seule`** (`scripts/smokeRead.ts`) : **des GET seulement** (le `fetch` refuse tout le reste, un corps ou un `X-Player-Id`), aucun joueur, aucune ligne de débit (lectures en mémoire) : `/api/health` (mêmes champs), `/api/jump/info` (`--environnement production`), niveau du jour, classement, fantôme, carte, lecture regroupée (aujourd'hui et hier), en-têtes de cache. **C'est le seul mode permis contre la production** ; le mode complet la refuse (`smokeRefusal`, testé : `apps/api/test/smokeLecture.test.ts`), sauf l'image locale de la CI. `production.yml` (job `verification`) le lance après le déploiement validé : un échec rend le run rouge, le résumé dit la route et la réponse et donne la commande de retour arrière (manuel). Seule écriture possible : celle du **serveur** (caches du niveau du jour, carte d'un jour fini figée), comme à la première requête de n'importe quel joueur.
- **Coûts** (`npm run measure:jump-api -w @cdj/api`, `npm run measure:platform -w @cdj/api -- --jump N --track N --salon N` ; chiffres unitaires dans `scripts/platformBudget.ts`, chacun avec sa source) : joueur type DailyJump **12 requêtes** par jour (P3 : 30), **≈ 19 pré-vols compris** (P3 : ≈ 41), 1 120 lignes lues, 32 écrites. **Premier plafond de l'offre gratuite : le calcul facturé de Cloud Run** (borne haute : 100 ms par requête), puis les requêtes : DailyJump seul ≈ 3 100 joueurs/jour (P3 : ≈ 1 430). **Seuils et décisions** (`docs/plateforme/couts.md`, § 4, à valider par Nathan) : ≥ 50 % de la ressource la plus chargée, surveiller chaque lundi ; ≥ 70 %, le Salon moins souvent ; ≥ 80 %, moins de relectures ; ≥ 90 %, carte des morts toutes les 10 min ; ≥ 100 % prévu, accepter une petite dépense (le plafond de 2 instances borne la facture) ; emballement, couper (`docs/securite-facturation.md`). Un lot qui change ce qu'un jeu lit ou écrit met à jour `platformBudget.ts`.
- Tests : `apps/api/test/jumpBundle.test.ts` (contenu, joueur, profil, jour passé et en cours, aucune écriture, l'envoi rend le classement, en-têtes de cache sur toutes les lectures, DailyTrack `no-store`), `smokeLecture.test.ts` (aucune écriture, base identique avant et après, refus du mode complet en production), `platformBudget.test.ts` ; SQLite **et** libSQL.

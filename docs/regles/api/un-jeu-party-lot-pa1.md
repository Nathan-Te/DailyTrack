# Un jeu Party (lot PA1)

> Détail du lot PA1 (écrit directement ici : le `CLAUDE.md` de la zone ne garde que le titre et le renvoi). Le renvoi est dans [`apps/api/CLAUDE.md`](../../../apps/api/CLAUDE.md).

## Un jeu Party (lot PA1)
**Catégorie `party`** (fiche : `categorie`, hors journée et hors cumul comme l'arcade ; règles : `docs/regles/racine/publication-des-jeux.md`). **Contrat serveur** : `src/jeux/party.ts`, `definirJeuParty({ fiche, nom }, contrat)` — le « niveau » d'un jour est **la graine du jour et rien d'autre** (`NiveauParty { jour, graine }`, `graineDuJour(code, jour)` de `@cdj/core/graine`, rendue par `GET /api/<jeu>/day/<date>` dans `contenu.graine`) ; le contrat n'écrit que `versions` (la version de la dérivation de la graine et du tirage), `decoder`, **`rejouer(niveau, texte)`** (le rejeu **valide le score**, comme pour tout jeu : le serveur ne garde que son résultat), `score`, `entrees` (et `mesures`, `ticksParSeconde`) ; **aucune médaille** (`seuils` rend `null`), aucun thème, aucun robot, aucun jour figé (`joursFiges` vide, pas de bloc `jours` dans la fiche : la chaîne de production, le garde-fou des jours et `figer` ignorent le jeu). Tout le reste (routes, ordre de validation, table commune `resultats_jeu`, classement, copies, aperçu, effacement, amis, « Mon groupe ») est le module des jeux. Tests : `test/partyJeu.test.ts` (graine reçue par le rejeu, refus par les codes de la liste), `test/partyPortail.test.ts` (hors journée, hors cumul), un jeu jouet dans `test/partyAide.ts`.

## Le jeu Party du jour (lot PA1b)
**Tour de rôle** (`jeuPartyDuJour`, `ordreParty`, `prochainJourParty`, `debutDePeriode` de `@cdj/core/jeux` : purs, testés) : chaque jour de Paris, un jeu Party `on` est le jeu du jour — **dans l'ordre des dates d'ouverture** (début de sa période `[du, au)` de l'interrupteur, puis le dossier), **en boucle**, à partir du seul numéro du jour (`jour mod N`), **sans table**. Seuls comptent les jeux Party **qui comptent ce jour-là** (périodes du lot P) : un jeu ouvert ou fermé en cours de journée compte à partir du lendemain, donc **ne change pas le jeu du jour commencé** ; un jour passé se recalcule à l'identique. Sans jeu Party `on` : pas de jeu du jour. **En aperçu** (aperçu de PR, clé d'aperçu), tous les jeux Party du registre sont en lice dès leur premier jour (un brouillon se montre « classé » à son tour). Le serveur : `Jeux.partyDuJour(jour, tout)`, `partyProchain`, `party` (`apps/api/src/jeux.ts`), posé aux jeux par `api.ts` dans `info.party` (`RequestInfo`).
**Ce que le serveur dit** : `GET /api/jeux` et `GET /api/portail/jour` portent `party: { jeu, prochains }` (le dossier du jeu du jour ou `null` ; la prochaine date `AAAA-MM-JJ` de chaque jeu en lice, calculée sur les jeux de demain) — **le champ n'existe que si le registre a un jeu Party** (la forme et les bancs des autres jeux sont inchangés) ; `/api/jeux` y ajoute `date` (gardé 30 s). Le classement d'un jeu Party (`…/day/<date>/board`) porte `party: { classe, prochain }` : **le jeu sait avant la partie s'il est classé**.
**Seul le jeu du jour est classé** : un envoi d'un autre jeu Party est refusé **avant tout rejeu** par `not_party_of_the_day` (409, liste unique, `docs/plateforme/codes-erreur.md`, `erreur.not_party_of_the_day` fr + en) ; le jour jugé est celui de la partie (la veille pendant la grâce : le jeu de la veille). Le portail ne compte un jeu Party que le jour où il est en tête (`comptes(day)`) : pas d'onglet, pas de vue, pas de ligne les autres jours. **Tests** : `apps/api/test/partyTourDeRole.test.ts` (alternance, refus, `party.classe` / `prochain`, ouverture en cours de journée, aperçu) ; la preuve sur le jeu fictif : `scripts/modele-fictif/partyessai.test.ts.modele`, écrit par `scripts/jeu-fictif.mjs` dans sa copie (partyessai classé le jour où il est en tête, refusé l'autre jour, horloge maîtrisée).
**Identité** : le motif de la catégorie est `confettis` (Pinball porte déjà les losanges ; `fondDuMotif`, deux tons, arrêts francs, aucune face de plus).


## Côté portail
Un jeu de catégorie `party` est **hors de la journée et du cumul** comme l'arcade (`categorie: "party"`, `compte: false`) : `categorieDuJeu` rend `party`, l'accueil et le profil le rangent avec l'arcade, `onglets` le place **après** les onglets d'arcade (même séparateur), `jeuxDuCumul` l'écarte, `jeuSuivant` n'annonce jamais « Journée parfaite ! » pour lui. **Lot PA1b — la section « Party »** (`portail.ts`, `salle.css` : `.salle-party`, le fond de confettis) sous l'arcade, **sur le même modèle** (cartouches de la salle) : le jeu du jour **en tête** (« Classé aujourd'hui »), les autres « Jeu libre · classé le <date> » (la date vient de `party.prochains`, « Jeu libre » seul sans date) ; **absente tant qu'aucun jeu Party n'est `on`** (le serveur ne les liste pas). **L'onglet** du jeu du jour : après l'arcade, sous son séparateur « Party » (`Onglet.party`, `classement.vues.party`) ; il suit aussi le classement des groupes (`party` de `GET /api/groupes/classement`). Textes : `portail.party.*` du catalogue du portail.

## Côté kit (`packages/kit`)
`fiche.categorie === "party"` : le jeu passe une **`DefinitionJeuParty`** (la définition des autres jeux **moins** `themeDuJour`, `seuils`, `medaille`, `rediffusionDiamant`, `sansMedaille`, `sansFantome`) ; `brancherJeu` la complète par `definitionDeParty` (`types.ts`) : **un seul thème**, `THEME_UNIQUE` (`unique` : le catalogue du jeu a `theme.unique` et `accueil.phrase.unique`, la fiche n'a aucun thème), **aucune médaille ni fantôme**. **Lot PA1b** : l'accueil d'un jeu Party dit **« Classé aujourd'hui »** ou **« Jeu libre · classé le <date> »** (`party` du classement du jour, morceau à la demande `src/jeu/party.ts`, préfixe `party-` de `A_LA_DEMANDE_PAR_DEFAUT`, textes fr + en dans ce morceau : aucune clé de plus dans le catalogue du kit) ; **hors de son jour le jeu est libre** : jouable, jamais envoyé (`ContextePartie.libre`), son record reste sur l'appareil (`<id>:records`, noté « envoyé » pour que la file ne le réclame pas) et l'accueil montre **le meilleur record gardé, tous jours confondus**. Hors ligne (statut inconnu) le jeu tente l'envoi : le serveur refuse au besoin. Le jeu n'écrit que sa simulation, son rendu et ses textes ; le moule : `npm run nouveau-jeu -- --categorie party` (`docs/regles/racine/creer-un-jeu.md`). `FicheClient.categorie` vaut `party` (jamais « Journée parfaite ! » à l'arrivée).


## Plusieurs jeux Party au registre, et les copies d'un jeu Party (lot PA1c)
**Un seul jeu Party est classé chaque jour, et aucun test ne suppose qu'il n'y en a qu'un.** Dès que deux jeux Party sont au registre (Pile poil et le jeu que génère « Kit de bout en bout » ou `jeu-fictif`), tout ce qui joue un jeu Party **cherche le jour où son jeu est en tête, avec une horloge maîtrisée** (`t.clock.now`, jamais la date du calendrier) : (1) le test du serveur du moule (`scripts/modele-party/apps/api/test/cibles.test.ts.modele`, « aperçu de PR » : en aperçu tous les jeux Party du registre sont en lice, le test prend le premier jour où `party.classe` du classement de son jeu est vrai) ; (2) **la base de référence** (`apps/api/scripts/baseDeReference.ts` : `enTeteDansLaReference`, `jourClasseDansLaReference`, la fonction pure `jeuPartyDuJour` sur les jeux Party des fiches, tous en lice depuis le jour 0 — un jeu Party n'a de parties que les jours où il est en tête) et **les mesures d'envoi de `routesChaudes.ts`** (`RouteSpec.jour` : l'horloge de la mesure est celle d'un jour du tour de ce jeu, sinon `not_party_of_the_day`) ; (3) `routesChaudes.test.ts` : « portail jour (joueur) » lit **les jours joués de chaque jeu** (une instruction par jeu : 29 avec 10 fiches, 31 avec 12), le plafond d'instructions est donc **20 + une par fiche** (le plafond de lignes parcourues suit de même, 3 par fiche) — il n'est pas relâché, il suit le nombre de jeux. **Preuve** : `node scripts/jeu-fictif.mjs` (deux jeux Party au registre : Pile poil et `partyessai`) et `kit-bout-en-bout` sont verts.
**Les copies d'un jeu Party** (règle du lot R9, inchangée pour le reste) : **deux parties qui n'ont joué aucune entrée** (aucun appui, aucune touche) **ne sont pas des copies l'une de l'autre** ; une rediffusion sans entrée n'est jamais comparée (ni à celle de l'auteur — un jeu Party n'en a pas —, ni à une partie déjà classée). Le contrat Party le dit par **`entrees(rejeu)` qui rend `null`** quand la partie n'a rien joué (`ContratParty`, `jeux/party.ts` ; `ContratJeu.sansEntree` côté module, `refuserCopies` n'est pas appelé) ; le texte d'entrées vide est gardé comme empreinte, sans rien bloquer. Une partie qui a joué des entrées identiques à une autre reste refusée (`409 replay_copy`). Tests : `partyJeu.test.ts` (« copies »), `cibles.test.ts.modele` (« refuse les copies »).

## Turso sobre (lot R14)
README : `docs/plateforme/lots/lot-R14-recette-sobre.md` ; guide : `docs/plateforme/couts.md` § 10. **Le quota du mois de Turso (offre gratuite : 500 M de lignes lues, 10 M écrites) est commun à toutes les bases : la recette peut bloquer la production.** Turso compte les lignes **parcourues** (un `SCAN` lit toute la table, même pour une ligne rendue) et, en écriture, une ligne par table **et par index**.
- **Jamais de Turso dans un test ou un outil de mesure** : `openTestDb` = `:memory:` ou un fichier libSQL ; `openLibsql` lève sous Vitest (`VITEST`) devant tout hôte hors de la machine (`src/distant.ts`, `refusDistantEnTest`) ; `test/pasDeTurso.test.ts` (environnement du test sans base distante, aucun fichier de test avec `libsql://` hors liste de textes de configuration, workflows sans `libsql://` hors démarrage d'image refusé). Les mesures de lignes (`measure:lignes`, `recette:seed --mesure`) tournent sur un `file:` ; l'exact de Turso se lit avec un `sqld` local (`measure:portail`, `measure:jump-api`, `measure:budget`).
- **`--distant` obligatoire pour viser une base distante** : `recette:seed`, `lancement:remise-a-zero`, `base:sauvegarde`, `pseudos:migrate` (cible `TURSO_DATABASE_URL`), `smoke` complet (un serveur déployé ; `--lecture-seule` n'écrit rien). Sans le drapeau : sortie 1 et l'hôte nommé (jamais le jeton). Les workflows le passent en clair. Un nouveau script qui ouvre une base appelle `exigerDistant`.
- **`recette:seed` n'écrit que ce qui manque** (`src/recetteSeed.ts`) : un marqueur `recette_seed:<segment>:<date>` dans `meta` par segment (courses de Track d'un jour, essai de Jump du jour, classement d'un jour, « Démo » du jour), valeur `<génération de données>|<empreinte>` ; sauté s'il est présent, de la génération courante (une remise à zéro du lancement périme tout) et de la même empreinte (versions de la simulation et du générateur, `SEED_FORMAT` — **à incrémenter quand le contenu fictif change**). Les joueurs du classement ne sont effacés puis recréés que si un jour déjà écrit a changé ; « Démo » est recréé une fois par jour (sa série de 5 jours suit la date). `--refaire` rejoue tout, `--mesure` compte les lignes (base `file:`). Mesuré (29/10/2026, `file:` local) : premier passage ≈ 2 500 instructions, rien à faire ≈ **7 instructions, 0 écriture**, jour suivant ≈ 750. **Il ne tourne qu'au déploiement de la recette par défaut** (job `seed` de `recette.yml`, `action == 'default'`) et chaque jour ; **le smoke complet n'écrit que sur la révision par défaut** (`deploy-api.yml` : une révision de PR n'est vérifiée qu'en lecture seule).
- **Toute nouvelle requête vérifie son plan et ses lignes lues** : (1) `EXPLAIN QUERY PLAN` — le banc d'essai (`test/enregistreur.ts`, branché sur `openTestDb`) examine **chaque requête du serveur que les tests font tourner** et fait échouer le test sur un `SCAN` d'une grande table (`GRANDES_TABLES`) non justifié ; un parcours voulu s'écrit dans `PARCOURS_PERMIS` (`src/plans.ts`) avec sa raison chiffrée, sinon on ajoute l'index (migration **réversible** dans `MIGRATIONS` : `CREATE INDEX IF NOT EXISTS`, retour arrière `DROP INDEX`). Audit complet : `CDJ_SQL_DUMP=/tmp/sql.jsonl npx vitest run --project sqlite apps/api/test`, puis `npm run plans -w @cdj/api -- /tmp/sql.jsonl`. (2) **Lignes lues des routes chaudes** : `test/routesChaudes.test.ts` mesure sur la base de référence (300 joueurs, 14 jours : `scripts/baseDeReference.ts`) le portail `jour` et `classement`, le classement Track, `/api/me`, la lecture regroupée de Jump, le message en direct et un envoi de chaque jeu, à froid et à chaud ; plafonds : 100 lignes lues (770 pour le calcul du classement du jour), 10 parcourues, 30 instructions. Une nouvelle route chaude s'ajoute à `ROUTES_CHAUDES` (`scripts/routesChaudes.ts`).
- **Ce que mesure `src/comptage.ts`** : les pas de parcours complet (`nscan` de `sqlite_stmt`) + les lignes rendues, sur le client libSQL natif d'un `file:` ; **estimation basse** (les lignes d'index écartées par une recherche et les `COUNT` sur plage d'index ne sont pas vus), exacte pour ce que le plan appelle un `SCAN`. Les instructions passées en lot (transaction) sont comptées, pas leurs parcours.

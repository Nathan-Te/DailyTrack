## Plateforme (lot P0) — profil commun
- **DailyJump importe le module de profil commun** (`@cdj/profile`, `packages/profile/CLAUDE.md`) **sans rien afficher** : avec `?debug`, `__jump.profile` = `{ exists, name }` (une identité de la plateforme existe-t-elle dans ce navigateur, et son pseudo), lue par `readIdentity` sur `gameStorage()` : les clés `cdj:*` de DailyTrack (même origine, même stockage, même préfixe `apercu:` dans un aperçu). **Rien n'est créé ni écrit** : pas d'identifiant tant que le jeu n'envoie rien (lot P1). Test : `e2e/smoke.spec.ts`.
- Le serveur calcule le niveau du jour par **la même règle que `loadDaily`** (figé d'abord, preuve rejouée, sinon `dailyLevel`) : `GET /api/jump/day/<date>` (`apps/api/CLAUDE.md`, « Plateforme (lot P0) »). Depuis le lot P1, **`thawLevel` est dans `@cdj/jump-sim`** (le jeu et le serveur importent la même fonction ; `apps/jump/src/frozen.ts` ne fait que la réexporter avec `FROZEN_DAYS`). **Changer l'ordre de `loadDaily` (figé, puis généré) = changer `apps/api/src/jump.ts` dans le même lot** (le test `apps/api/test/jump.test.ts` le rappelle). **Le serveur de Jump (lot K2b) = son contrat (`contratJump`), son adaptateur de table (`ADAPTATEUR_JUMP`) et ses `routesPropres`** sur le module des jeux (`apps/api/CLAUDE.md`, « Module des jeux ») : les routes propres sont `lives` (vies), `day/<date>/ghost/first`, `deaths`, `carnage` et `bundle` ; `info`, `day`, `submit`, `board` et `me` ont les mêmes adresses et les mêmes réponses qu'avant. **Toute modification du serveur de Jump relance les trois bancs de réponses** (`npx vitest run --project sqlite apps/api/test/banc`).

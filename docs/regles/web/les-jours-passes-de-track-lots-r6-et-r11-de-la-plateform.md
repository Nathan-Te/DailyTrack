## Les jours passés de Track (lots R6 et R11 de la plateforme)
Guide : `docs/plateforme/mise-en-production.md`. **Rien ne change pour le joueur** (golden inchangés). Le circuit d'un jour est calculé **dans le navigateur** par le code du jeu (fil de travail) : si le générateur changeait pour un jour déjà joué, la course d'un joueur ne se rejouerait plus sur le circuit du serveur. Un jour passé est donc protégé par (1) **le registre des jours** (`packages/sim/src/jours-track.json`, lot R11 : la version du générateur de chaque jour protégé, lue par `generatorVersionOf` — **plus de date de bascule dans le code** ; un jour que le registre ne nomme pas prend la dernière version) ; (2) **`apps/api/test/jours-passes.json`** : l'empreinte de chaque jour protégé, que la PR « Jours figés » de chaque mise en production complète, vérifiée par `jours-passes.test.ts` dès la PR ; (3) le garde-fou de « Mettre en production », qui compare chaque jour protégé entre le code en production et la nouvelle construction et refuse toute différence. **Un lot de Track qui change le générateur monte `GENERATOR_VERSION` et n'écrit plus de date** (`packages/sim/CLAUDE.md`, « Registre des jours (lot R11) ») : le registre est écrit par la mise en production, qui décide du premier jour concerné ; garder l'ancienne version dans le code tant que le registre s'en sert. Le jeu et le serveur lisent le même fichier (`generatorVersionOf`) ; le fichier est dans le premier chargement (≈ 100 o par plage). L'outil `verify.html` prend la version à imposer (`window.__daily(date, generator)`) pour les circuits de référence des anciennes versions. Un onglet resté ouvert reçoit `409 sim_version` ou `409 track_mismatch` (traduits) si `SIM_VERSION` ou le circuit a changé ; son meilleur temps reste local.

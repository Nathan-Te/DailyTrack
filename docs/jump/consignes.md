# DailyJump — consignes

Jeu de plateformes quotidien à la Super Meat Boy, deuxième jeu du dépôt. Vision et plan de lots : `docs/jump/seed-dailyjump.md` (**ne pas modifier**, c'est Nathan qui le fait). Réponses et docs en français. Chaque lot de DailyJump ajoute **sa section ici**, jamais dans le `CLAUDE.md` racine.

## Emplacements
- `docs/jump/seed-dailyjump.md` — vision, piliers, plan en lots (le prompt de lot 0 le nomme `seed.md` : le fichier déposé s'appelle `seed-dailyjump.md`).
- `docs/jump/lots/` — un README d'une page par lot (`lot-0-socle.md`…).
- `packages/jump-sim` (`@cdj/jump-sim`) — simulation pure du saut.
- `apps/jump` (`@cdj/jump`) — le jeu (Vite + Three.js, caméra orthographique) ; affiche ce que calcule `jump-sim`.
- `packages/core` (`@cdj/core`) — socle partagé avec DailyTrack : PRNG (`Rng`, `mixSeed`), calendrier (`daysFromCivil`, `civilFromDays`, `formatDay`, `parseDay`), codage d'octets (`toBase64Url`, `fromBase64Url`, `pushVarint`, `readVarint`), et le test de pureté générique (`@cdj/core/testing`). Le jour de Paris (changement de jour) est dans `packages/clock` (`parisDay`), qui lit l'heure et n'est donc pas pur : jamais importé par une simulation.

## Règle du socle (`core`)
- `core` ne contient **aucune logique de jeu**. Tout ce qui y entre doit laisser **inchangés les golden des deux jeux**.
- On n'y déplace un module que lorsque le **deuxième** jeu en a besoin. `PREMIER_JOUR` reste propre à chaque jeu. Le format d'une rediffusion (champs d'une série, bornes, version) reste propre à chaque jeu ; seul le codage d'octets est commun. `math.ts` n'est pas dans `core` (le saut n'a pas besoin de trigonométrie).

## Règles de `jump-sim`
- **État entièrement en entiers** : 1 tuile = 4 096 unités (`UNITS_PER_TILE` : 16 px × 256 sous-pixels), vitesses en unités par tick, minuteries en ticks. Pas fixe à 120 Hz (`TICK_RATE`), jamais de `dt` variable.
- **`idiv(a, b)` pour toute division** : tronque vers zéro, ne renvoie jamais `-0`. Jamais de `/` sur l'état, jamais de `Math.floor` d'un quotient pour couper.
- **Mêmes interdits que `sim`** (pas de `Math.random`, `Date`, `performance`, `**`, fonctions transcendantes, imports extérieurs ; seul `@cdj/core` est permis), vérifiés par `test/purete.test.ts` qui utilise la liste commune de `@cdj/core/testing`.
- **`JUMP_SIM_VERSION`** +1 dès que la physique, un élément de niveau ou un niveau d'essai change le résultat d'un essai ; **`JUMP_GENERATOR_VERSION`** +1 dès que le niveau d'une date change. Puis régénérer les références (golden), comme pour DailyTrack. Valent 1 au lot 0.
- Un niveau est une grille ASCII (`parseLevel`, `level.ts`) : `#` bloc, `.` vide, `S` départ, `F` arrivée (les autres éléments entrent avec leurs lots).

## Conventions de `apps/jump`
- **`?debug`** expose `window.__jump` (même esprit que `__cdj` de DailyTrack) : `phase` (`loading` → `ready`, ou `no-webgl`), `day`, `simVersion`, `palette`, `probe()` (relit les pixels). Sans `?debug`, rien n'est exposé.
- **Stockage local préfixé `jump:`** (`storageKey()`, `storage.ts`) ; DailyTrack garde `cdj:`. Toujours sous `try/catch`.
- **Publication sous `/jump/`** du même site GitHub Pages : `pages.yml` construit `apps/web` à la racine et `apps/jump` dans `jump/` (aperçu de branche : `…/b/<branche>/jump/`). Chemins **relatifs** (`base: "./"`) pour que les aperçus de branche marchent.
- **Tout nouveau paramètre d'adresse rejoint la page d'admin** (à créer côté `apps/jump` avec le premier paramètre qui le demande). Le lot 0 n'en a pas d'autre que `?debug`.
- Rendu, son, effets : lecture seule de la simulation ; jamais l'inverse. Texte en français.

## Commandes
- `npm run dev:jump` — serveur de développement de `apps/jump`.
- `npm run build` — construit DailyTrack **et** DailyJump (`npm run build -w @cdj/jump` pour DailyJump seul).
- `npx vitest run packages/core packages/jump-sim apps/jump` — tests de DailyJump et du socle ; `npm test` lance tout (deux projets, `sqlite` puis `libsql`).
- `npm run typecheck` — `tsc -b` sur tous les espaces de travail.
- `npm run e2e:jump` — construit puis lance le test de fumée Playwright de `/jump/?debug` (`E2E_ALL_BROWSERS=1` pour Firefox et WebKit, `CHROMIUM_PATH` pour un Chromium déjà installé). En CI : une fois par navigateur, dans la part 1 de la matrice `e2e-parts`.

## Lot 1 — personnage
- **Simulation** (`packages/jump-sim`) : `stepPlayer(état, commande, niveau, réglages) → état`, pur, 120 Hz (`player.ts`) ; collisions boîte contre grille axe par axe, en ne parcourant que les tuiles nouvellement couvertes (`collide.ts` : `sweep`, `boxHits`, `floorDiv`) ; bac à sable écrit en ASCII (`sandbox.ts` : `SANDBOX_LEVEL`, repères `SANDBOX_MARKS`). Boîte de collision constante 3/4 × 3/4 de tuile (`PLAYER_WIDTH`, `PLAYER_HEIGHT`) ; le rendu dessine exactement cette boîte.
- **État 100 % entier** (drapeaux 0/1, côtés −1/0/1), divisions par `idiv` uniquement (`floorDiv` est bâtie dessus), jamais de `-0` (les vitesses rendues passent par `+ 0`). **`MAX_SPEED`** (2 048 unités/pas, une demi-tuile) < 1 tuile/pas, appliqué **à chaque pas** sur les deux axes quels que soient les réglages. **Toute nouvelle mécanique rejoint le fuzz d'intégrité** (`test/player.test.ts`, « intégrité (fuzz) » : commandes aléatoires du PRNG de `core`, graine fixe, réglages par défaut et au hasard ; tout reste `Number.isInteger`, sans `-0`, sous `MAX_SPEED`, hors des murs).
- **Commandes = 3 bits** (`INPUT_LEFT` 1, `INPUT_RIGHT` 2, `INPUT_JUMP` 4 = saut *tenu*) ; gauche + droite = neutre ; l'**appui** (front montant) est déduit dans la sim (`PlayerState.held`). **« Recommencer » n'est pas une commande de la sim** : c'est un événement de la session (`JumpSession.restart`, touche R, Start/Select).
- **Réglages** `JumpParams` (entiers, `DEFAULT_JUMP_PARAMS`, tableau en unités humaines dans `docs/jump/lots/lot-1-personnage.md`). **Tout changement de réglage par défaut, de physique ou du bac à sable ⇒ `JUMP_SIM_VERSION` +1** et golden régénérés **en comprenant pourquoi** : `UPDATE_GOLDEN=1 npx vitest run packages/jump-sim/test/golden.test.ts` (le test vérifie la version, les réglages et l'empreinte du bac à sable, puis rejoue les suites au pas près). Mesures : `MESURES=1 npx vitest run packages/jump-sim/test/mesures.test.ts`.
- **Une session aux réglages modifiés (`tuned`) n'est jamais enregistrée** (`JumpSession.tuned`, vrai dès qu'un pas a été joué avec d'autres réglages que les défauts ; « recommencer » aux défauts l'efface). Panneau `?debug&tune` (`tune.ts`) : un curseur par réglage, en unités humaines avec la valeur entière, « Copier les valeurs » (JSON), « Réinitialiser », mémorisé dans `jump:tune` (seulement en mode `tune`), badge « réglages modifiés ».
- **Tout nouveau paramètre d'adresse rejoint `apps/jump/src/urlOptions.ts`** (`URL_OPTIONS` : nom, description, valeurs ; `readUrlOptions` est le seul lecteur de l'adresse, un test le vérifie). La page d'admin de DailyJump lira cette liste.
- **Jeu** (`apps/jump`) : boucle à pas fixe (`loop.ts`, `FixedStepper`, au plus 30 pas par image), rendu interpolé entre `session.prev` et `session.state` ; entrées (`input.ts`) : clavier par `KeyboardEvent.code` (flèches, `KeyA`/`KeyD`, saut `Space`/`ArrowUp`/`KeyW`, R), manette (stick avec zone morte, croix, A/B saut, Start/Select recommencer), **aucun appui de saut perdu** (`JumpLatch`) ; caméra (`camera.ts`, affichage seul : avance, lissage, zone morte verticale, bornée au niveau) ; allure (`look.ts` : écrasement, étirement, regard — affichage seul).
- **`window.__jump`** (avec `?debug`) : `phase` (`ready` au chargement et après « recommencer », `playing` dès la première commande non nulle), `player` (tuiles, tuiles/s, `mode`, compteurs, `raw`), `params` (l'objet en vigueur), `tuned`, `ticks`, `manual(on)`, `advance(n)` (joue `n` pas **tout de suite, sans rendu**, renvoie `player`), `input(bits | null)`, `restart()`, `probe()`.
- **Tests de jeu en pas à pas** (`manual(true)` + `input` / `advance`), **jamais sur une durée** (`e2e/smoke.spec.ts`).
- **Zones partagées, en plus de la liste du `CLAUDE.md`** : `packages/clock` et `apps/api/Dockerfile`.

## Lot 1b — mobile
- **Toute nouvelle commande a son équivalent tactile** (et reste dans `Controls` : le tactile ne produit que les mêmes 3 bits, rien dans la simulation). Un bouton de plus = une zone ou un bouton dessiné, une entrée dans `touch.ts`, un test.
- **Les zones restent sans trou, la logique reste pure et testée** : `apps/jump/src/touch.ts` (zones `ZONE_SPANS`, `zoneAt`, `TouchPad`, `buttonRects`, aucun DOM) ; `touchUi.ts` ne fait que brancher le DOM (pointer events, boutons dessinés). Le toucher se décide par la **zone**, jamais par le bouton dessiné ; la bande haute (`BAND_PX`, recommencer, ⚙, plein écran) est exclue des zones de jeu. `?touch=1` force le tactile (la souris simule le doigt), `?touch=0` le coupe, `?zones=1` dessine zones et doigts.
- **Cibles ≥ 44 px, vérifiées en portrait et en paysage** (`e2e/mobile.spec.ts` : téléphone émulé, boutons, panneau de réglages et curseurs compris) ; un nouvel élément cliquable passe par ce test. Cadrage : `viewHeightTiles` (`camera.ts`), 18 tuiles de haut au poste, 13 sur téléphone en paysage, jamais moins de 10 tuiles de large.
- **Page** : `touch-action: none`, `overscroll-behavior: none`, corps fixe `100dvh`, `viewport-fit=cover`, marges `safe-area-inset-*` ; rien ne défile, ne se sélectionne, ne se zoome.
- **`tileOf` est le seul décalage permis dans la sim** (`v >> 12`, `collide.ts`, testé contre `Math.floor(v / 4096)` négatifs compris, jamais `-0`) ; **toute autre division passe par `idiv`**. Les golden et `JUMP_SIM_VERSION` n'ont pas bougé : c'est la preuve d'un calcul identique.
- **Tests de navigateur tactiles** : doigts posés par `Input.dispatchTouchEvent` (Chromium) ou par pointer events sur la couche `#touch` (Firefox, WebKit), toujours en pas à pas.

## Lot 2 — dangers et mort
- **Chaque élément de niveau a son caractère documenté** (légende et format du bloc annexe en tête de `packages/jump-sim/src/level.ts`), **sa boîte « juste »** (plus petite que le visuel quand c'est mortel : pics = moitié côté base, retrait de ¼ sur les flancs, dans le triangle ; scies = disque plein, les dents dessinées le dépassent), **ses tests** (`test/dangers.test.ts`) et **sa place dans `?scenario=dangers`** (galerie `DANGERS_LEVEL`, `levels.ts`). Un nouvel élément rejoint aussi le fuzz d'intégrité de l'essai.
- **Les éléments mobiles démarrent à l'entrée de leur section** (`section <nom> <col0>-<col1>` dans le bloc annexe ; un élément appartient à la section de son premier point ; avant, il attend à son départ et tue quand même). Position = fonction **entière et pure** des pas écoulés (`sawCenter`, `idiv`), exactement au départ à chaque cycle. La rotation des scies est un effet d'affichage.
- **Tout l'état du niveau est entier** (`AttemptState`, `attempt.ts` : scies par sections, blocs friables, ressort, chrono) **et revient à zéro à la mort** (égalité profonde avec `initialAttempt`, testée). `stepPlayer` (lot 1) ne connaît que la grille ; `stepAttempt` l'enveloppe.
- **Le monde attend la première commande** (une direction, ou un saut appuyé) : rien ne bouge, le chrono reste à 0.
- **Le temps est en pas** (`AttemptState.time`, du premier pas commandé au contact de `F` compris) ; l'affichage en secondes à 3 décimales (`formatTicks`) n'est que de l'affichage.
- **L'arrivée l'emporte sur la mort au même pas** (vérifiée d'abord, testée).
- **Pas de saut automatique à la réapparition** : un saut tenu depuis l'essai précédent ne compte qu'après avoir été relâché ; une direction tenue compte tout de suite. Réapparition `RESPAWN_TICKS` (18 pas = 0,15 s ; jamais plus de 24) après la mort, commandes ignorées entre-temps.
- **Recommencer n'est pas une mort** : c'est un événement de la session (`JumpSession.restart`), qui repart de `initialAttempt`.
- **Les distances au carré restent sous `Number.MAX_SAFE_INTEGER`** : bornes `MAX_LEVEL_WIDTH` / `MAX_LEVEL_HEIGHT` / `MAX_SAW_*` refusées par `parseLevel`, test « bornes » sur la plus grande carte possible. Toute nouvelle grandeur multipliée rejoint ce test.
- Bas de la grille **ouvert** (on en meurt), les trois autres bords restent pleins (`tileAt`).
- **Preuve de faisabilité** : `test/fixtures/essai-solution.json` (et `dangers-solution.json`), rejouées par `essai-solution.test.ts` et le golden ; trouvées par le chercheur hors simulation `test/solver.ts` (`SOLVE=1 npx vitest run packages/jump-sim/test/essai-solution.test.ts`). **Modifier le niveau d'essai ou la physique ⇒ `JUMP_SIM_VERSION` +1, `SOLVE=1`, puis `UPDATE_GOLDEN=1`.**
- **Jeu** : `?scenario=essai` (page par défaut) · `dangers` · `bac-a-sable` ; `?debug&hitbox` (boîtes justes et sections) ; `?fx=off` (ni éclats ni tremblement : `fx.ts`, pool recyclé, jamais d'objet créé en jeu). `__jump.attempt` (statut, chrono, morts, meilleur, dernière mort, scies, friables, sections), `__jump.fx`, `__jump.banner`. HUD (`hud.ts`) : chrono, meilleur temps, morts, sous la bande haute sur téléphone ; bandeau d'arrivée au-dessus de la couche tactile, bouton ≥ 44 px. Meilleur temps et morts : **session seulement** (lot 3 pour l'enregistrement) ; un essai aux réglages modifiés ne devient jamais le meilleur.
- Mesures : `MESURES=1 npx vitest run packages/jump-sim/test/mesures.test.ts --silent=false`. Outils tactiles des e2e communs : `apps/jump/e2e/phone.ts`.

## Lot 2b — points de passage
- **`C`** = point de passage (tuile vide repérée, posée sur un sol sûr, `Level.checkpoints` rangés de gauche à droite). Le toucher **vivant à la fin du pas** le retient (`AttemptState.checkpoint`) — **depuis le lot 4 : le franchir** (voir « Lot 4 — morceaux ») ; un point touché au pas d'une mort ne compte pas.
- **Mort après un point** : l'essai **continue** — le chrono tourne pendant l'attente (`RESPAWN_TICKS`) et après ; reprise posée sur le point, sans attendre de commande ; friables reposés, ressort au repos, sections du point et d'après remises à l'arrêt (elles repartent à leur entrée), sections d'avant inchangées (`checkpointAttempt`). **Sans point**, la mort termine l'essai comme au lot 2. **Recommencer (R) oublie le point** : départ, chrono à zéro. Un temps d'arrivée peut donc contenir des morts : le bandeau le dit (« essai sans faute » ou « N dans cet essai », `JumpSession.attemptDeaths`).
- Un niveau écrit à la main en met au début de chaque section et avant les passages longs ; jamais dans un danger. Un nouveau point dans un niveau d'essai change le niveau : **`JUMP_SIM_VERSION` +1**, solutions et golden régénérés (`JUMP_SIM_VERSION` vaut **2** depuis le lot 2b).


## Lot 3 — rediffusion
- **Le rejeu est la seule source de vérité de tout temps conservé** : un essai clos est rejoué (`replayAttempt`, `packages/jump-sim/src/replay.ts`) avant que la mémoire du jour (`apps/jump/src/memory.ts`) en garde quoi que ce soit ; le meilleur temps gardé (et affiché « Meilleur du jour ») est celui du rejeu, jamais celui du HUD ; au chargement, le meilleur essai est rejoué de nouveau.
- **Format** : séries `{ count, bits }` codées par `@cdj/core` (`varint(count × 8 + bits)`) ; en-tête = `JUMP_REPLAY_FORMAT`, `JUMP_SIM_VERSION`, identifiant du niveau (le scénario aujourd'hui, la date plus tard), départ (saut tenu ; point de passage, chrono et sections pour une vie) ; borne `MAX_ATTEMPT_TICKS` (10 min). Un essai commence au **premier pas commandé** : son chrono vaut le nombre de pas rejoués. Les reprises aux points de passage ne sont pas enregistrées (la sim les refait).
- **Une rediffusion d'une autre version est ignorée** (`JumpReplayError` de code `version` au rejeu ; la mémoire l'écarte sans bruit) ; trop longue ou mal formée : erreur claire (`length`, `format`).
- **Tout nouvel effet de la sim garde l'égalité entre jeu et rejeu** : `packages/jump-sim/test/replay.test.ts` (« rejeu = ce qui a été vécu », essai par essai, et chaque vie rejouée seule) doit rester vert ; un nouvel élément rejoint aussi ses sessions jouées et les essais fictifs de `replay-golden.test.ts` (empreintes comparées dans Chromium, Firefox et WebKit par `apps/jump/e2e/replay.spec.ts` sur `verify.html`). Changer le format ou les essais fictifs : `UPDATE_GOLDEN=1 npx vitest run packages/jump-sim/test/replay-golden.test.ts` ; après `SOLVE=1`, recopier le texte de la solution dans `src/solutions.ts`.
- **Vocabulaire** : un *essai* va du départ à l'arrivée, à une mort sans point de passage, ou à « recommencer » ; une *vie* est un tronçon d'essai entre deux réapparitions (sa rediffusion part de son point de départ).
- **Rien n'est enregistré en `tuned`** : ni meilleur essai, ni vies, ni taches (le badge le dit : « réglages modifiés : rien n'est enregistré ») ; ni en lecture (`?watch=best`) ni pendant le carnage.
- **Le stockage est protégé et le jeu marche sans** : tout accès passe par `try/catch` (`memory.ts`, interface `KeyValue` pour les tests) ; clés `jump:jour|meilleur|vies|morts:<niveau>`, `jump:fantome` ; purge au changement de jour, de niveau (empreinte `levelHash`) ou de version.
- **Le carnage et les taches sont du rendu seul, plafonnés et instanciés** : chaque vie a sa propre simulation (`carnage.ts`, logique pure testée), le dessin ne fait que lire (`actors.ts` : un `InstancedMesh` pour la foule, un pour les taches, pool d'éclats recyclé) ; au plus 300 vies et 300 taches gardées par niveau et par jour (au-delà, les plus anciennes s'estompent) ; les taches sont découpées au pochoir par les blocs pleins (jamais dans le vide). Les dangers montrés pendant le carnage sont ceux du monde du héros (léger décalage de phase des scies pour les autres vies, accepté).
- **`?fx=off` ne coupe pas les taches** (elles portent une information) : seulement les éclats et le tremblement.
- Outils : `?carnage=demo`, `?watch=best`, `?ghost=off` (dans `urlOptions.ts`) ; `?debug` → `__jump.replays` (lister, exporter, importer), `__jump.carnage` (`start`, `demo`, `skip`, `state`), `__jump.storage.clear()`, `__jump.ghost`, `__jump.stains`, `__jump.frameTimes`. Touche **G** et bouton 👻 : fantôme.

## Lot 4 — morceaux
- **Un morceau = un fichier texte** `packages/jump-sim/modules/<id>.txt` (l'id est le nom du fichier) : métadonnées `id`, `intention` (une phrase), `etiquettes` (`mural`, `precision`, `vertical`, `scie`, `friable`, `ressort`, `respiration`), **`format: 2`** (lot 6), `paliers` (rangées de la grille du **sol** à l'entrée et à la sortie), `repeter`, `variante` ; puis `grille:` (caractères de `level.ts`, sans `S`, `F` ni `C`) — **la grille commence à la première colonne du défi et finit à la dernière : aucun palier n'y est dessiné** ; puis le bloc annexe (seulement des `scie`). Format détaillé en tête de `packages/jump-sim/src/modules.ts`.
- **Variantes déclaratives** : `repeter: <param> colonnes|rangees <de>-<à>` — la plage est dessinée **une fois**, la variante dit combien de copies (0 la retire) ; `{param}` dans le bloc annexe (cycle d'une scie…) ; coordonnées du bloc annexe en repère du gabarit (`c,r` = première copie, `c',r` = dernière). 2 à 4 variantes par morceau.
- **Une seule fonction construit tout** : `buildModule(id, variante, { lancement? })` (pure) → niveau = colonne de garde (`PALIER_GUARD`) + **palier standard** d'entrée (départ `S` sur sa première colonne) + morceau (**une seule section** : ses scies démarrent à l'entrée) + palier standard de sortie + une colonne de piste et la colonne d'arrivée `F` (seulement pour finir le morceau joué seul). Identifiant de niveau : `module:<id>:<variante>`.
- **Palier standard (lot 6)** : `PALIER_LENGTH` = **2** colonnes de sol plein à la rangée déclarée, du plein dessous, **du vide au-dessus jusqu'en haut** (un rebord, pas un couloir) ; posé par `buildModule` **et** par l'assemblage, le même partout. Invariants (`palierProblems`, tests) : au moins 4 rangées libres au-dessus, aucune scie (sur tout son cycle) dans la boîte libre au-dessus, la première colonne du morceau libre au ras du sol ; hauteur ≤ 30 rangées ; solution de 1 à 6 s entre son entrée et sa sortie.
- **Point canonique = bord droit d'un palier** (`centerCol`, `isCleanRun`, `moduleSpan`) : une solution **sort** au premier pas où le centre du personnage franchit le bord droit de son palier de sortie, au sol, à `runSpeed`, en **course propre** (bouton relâché, rien dans le tampon, ni montée, ni mur : deux personnages dans cet état ne diffèrent que par leur position) ; le morceau suivant **entre en élan exactement là**. Entrée *arrêt* : immobile au début du palier d'entrée (premier morceau du niveau, reprise sur un point de passage). Entrée *élan* d'un morceau seul : même départ, lancé (drapeau « élan » de la rediffusion), droite tenue jusqu'au bord (`entryTick`). Une solution ne repasse jamais à gauche du palier d'entrée (ce qui précède n'est pas le même seul et assemblé). `ModuleSolution` : `ticks` (toute la rediffusion du morceau seul), `entryTick`, `exitTick` ; un morceau compte `exitTick − entryTick` pas dans le niveau du jour.
- **Tout changement d'un morceau ou de la simulation ⇒ `npm run solve:modules -w @cdj/jump-sim`** (incrémental : empreinte de la grille et `JUMP_SIM_VERSION`), puis **commiter** `modules/solutions.json` et `src/catalog.ts` (généré : un test vérifie qu'il est à jour, sinon « relancer solve:modules »). Le solveur (`tools/`, hors de `src/`) ne tourne jamais en production ni dans `npm test`. Mesures : `npm run measure:modules -w @cdj/jump-sim` (`-- --solveur` : temps du solveur complet).
- **Aucun morceau au pas près, raccord strict** : exigence = note de 1 à 5 d'après la gigue (changements de commande décalés au hasard de ±1, ±2, ±3 pas, 200 tirages chacun) : `exigenceOf` (`src/modules.ts`). Refusée (0) si elle réussit moins d'une fois sur deux à ±1, **ou si le raccord réussit moins de 9 fois sur 10** (lot 6, `RACCORD_MIN`) : la solution en élan rejouée depuis les 25 positions d'entrée possibles dans un pas de course (`RACCORD_POSITIONS`, de 0 à 375 unités au-delà du bord), jusqu'à une sortie propre, droite tenue au plus `RACCORD_TAIL` pas après ses commandes ; une variante refusée est adoucie ou retirée. Changer la règle ou la mesure ⇒ `EXIGENCE_VERSION` +1 (vaut 2) et `solve:modules`.
- **Un point de passage se prend en franchissant sa colonne** (lot 4, `JUMP_SIM_VERSION` 3) : le centre du personnage, vivant, passe sa colonne vers la droite, à n'importe quelle hauteur (le sauter le prend) ; un seul `C` par colonne ; la reprise se fait sur le fanion, au sol ; le fanion se dessine aussi comme une porte discrète sur la hauteur libre de sa colonne.
- **À partir du lot 5, tout changement du catalogue ⇒ `JUMP_GENERATOR_VERSION` +1** (le niveau d'une date change).
- **Jeu** : `?modules` (galerie), `?module=<id>&variante=<n>&entree=arret|elan` (en élan, couloir de lancement de `LAUNCH_TILES` = 5 tuiles), `&solution` (la solution stockée, rejouée) ; bandeau d'arrivée avec le temps de la solution et « Morceau suivant ». Mémoire, fantôme, carnage et taches par morceau (clés `jump:*:module:<id>:<n>:<entrée>`). Logique pure : `apps/jump/src/modulesInfo.ts` ; galerie : `gallery.ts` (chargée par `boot.ts`, sans Three.js).

## Lot 5 — niveau du jour
- **`dailyLevel(jour)`** (`packages/jump-sim/src/daily.ts`, pur ; `jour` = numéro de jour de `@cdj/core`) assemble des morceaux du catalogue et rend le niveau, la preuve (rediffusion de l'auteur), le temps de l'auteur, les médailles, l'exigence et les tirages essayés. **`PREMIER_JOUR_JUMP`** = 16/10/2026 (niveau n° 1, `levelNumber`). Graine : `Rng(mixSeed(mixSeed(jour, sel), tirage))`. **« Aujourd'hui » se lit par `@cdj/clock` (`parisDay`) dans le jeu, jamais dans la sim** (ni `Date` ni heure dans `jump-sim`).
- **Assemblage (lot 6)** : garde · palier de départ `S` · morceau 1 · **palier partagé** `C` · morceau 2 · … · morceau n · palier d'arrivée · `F`. Le palier de sortie d'un morceau **est** le palier d'entrée du suivant (les mêmes tuiles, **aucune colonne de raccord**), aligné par sa rangée, son vide montant jusqu'en haut du plus haut des deux voisins (`DailyLevel.paliers`) ; **le premier morceau part à l'arrêt, tous les suivants en élan** ; **hors des morceaux et des paliers tout est plein** (une rangée de blocs ferme le haut ; sous un morceau, le vide continue jusqu'en bas là où sa dernière rangée n'est pas un bloc) ; un point de passage `C` par morceau (sauf le premier, qui a le départ), **au début du palier qui le précède** (y reprendre = exactement l'entrée « arrêt » du morceau seul, testé) ; **chaque morceau est une section**. Hauteur totale ≤ **56** rangées (`MAX_DAILY_HEIGHT`, 48 au lot 5), 6 à 13 morceaux.
- **Durée** : on ajoute des morceaux tant que l'estimation (somme des durées des solutions de leur entrée à leur sortie ; `JOINT_TICKS` = **0** depuis le lot 6, 9 au lot 5) est sous `ESTIMATE_MIN_TICKS` (28 s), sans dépasser `ESTIMATE_MAX_TICKS` (32 s) ; **temps de l'auteur dans [25 ; 40] s** (`AUTHOR_MIN/MAX_TICKS`), centre 30 s (`AUTHOR_TARGET_TICKS`).
- **Course à vide (lot 6)** : temps au sol sans appui de saut, centre au-dessus d'un palier de raccord, sur la rediffusion de l'auteur (`palierTicksOf`, `DailyLevel.palierTicks`) : **cibles moins de 0,25 s par raccord en moyenne et moins de 6 % du temps de l'auteur au total** ; la seconde est une règle (`EMPTY_RUN_MAX` = 60 ‰, `dailyProblems`) ; les deux sont vérifiées par les tests sur 60 dates et mesurées par `measure:jump` (avec la plus longue course au sol sans saut).
- **Quotas** : au moins un `mural`, au moins une `scie`, jamais plus de **deux `precision` d'affilée**, **un seul `respiration`, au milieu** (son milieu entre 35 et 65 % du temps ; imposé seulement quand il ne pourrait plus y tomber, `FORCE_REST_SLACK`), jamais deux fois le même morceau.
- **Budget d'exigence** (la même exigence chaque jour, aucune difficulté selon le jour de la semaine) : somme des exigences ramenée à la durée, en dixièmes de point par minute, dans **[`EXIGENCE_RATE_MIN` 430 ; `EXIGENCE_RATE_MAX` 520]** (centre 475 ; 380–460 au lot 5 : sans course à vide, la même suite de morceaux tient en moins de temps) ; au moins un morceau d'exigence **≥ 4** (`EXIGENCE_PEAK`) ; **dernier tiers ≥ premier tiers** (moyenne pondérée par la durée) ; la variante de chaque morceau est la plus proche du profil visé `PROFILE_START` 1,3 → `PROFILE_END` 3,3. `dailyProblems(niveau)` liste ce qui ne va pas (les tests l'appliquent à 60 dates).
- **Repos sans historique** : trois groupes (`restGroup`, empreinte de l'identifiant avec `REST_SALT`, choisi pour des groupes de 9 aux étiquettes réparties) ; le jour `d` laisse au repos le groupe `d mod 3`. Le secours l'ignore.
- **Validation par rejeu** : les solutions sont mises bout à bout **sans course entre deux** : chacune jouée jusqu'à sa sortie canonique (le centre passe le bord droit du palier partagé, en course propre), la suivante reprend au pas d'après depuis son `entryTick` (une seule possibilité : le repli « l'autre pas » du lot 5 est retiré, le raccord strict l'a rendu inutile, mesuré) ; si la sortie vient un peu plus tard que dans la solution stockée, droite tenue (au plus `RACCORD_TAIL` pas, comme le test de raccord). **La rediffusion complète est rejouée par `replayAttempt`** : arrivée sans mort, toutes les règles, sinon tirage suivant. **`DAILY_DRAWS` = 6 tirages** par jour, on garde le meilleur valide (durée et exigence les plus proches du centre) ; sans tirage valide, jusqu'à `DAILY_MAX_ATTEMPTS` = 40, puis le **niveau de secours** (`FALLBACK_PIECES`, assemblé et validé de la même façon ; **jamais utilisé sur 120 dates**, mesuré).
- **Temps de l'auteur** = temps de la preuve rejouée, en pas. **Médailles en pas entiers** (`jumpMedalsFor`, `idiv`, arrondies au pas supérieur) : or ×1,10, argent ×1,30, bronze ×1,60 (`MEDAL_PERCENT`, à calibrer) ; l'auteur est le palier au-dessus de l'or.
- **Identifiant** : `jour-AAAA-MM-JJ-g<JUMP_GENERATOR_VERSION>` (`dailyLevelId` ; rediffusions, mémoire, fantôme, carnage, taches).
- **Tout changement qui modifie le niveau d'une date** (règles, seuils, sel, catalogue, solutions, assemblage) ⇒ **`JUMP_GENERATOR_VERSION` +1**, `UPDATE_GOLDEN=1 npx vitest run packages/jump-sim/test/golden-daily.test.ts`, puis **`npm run measure:jump -w @cdj/jump-sim`** (toute règle se juge à ses mesures : taux de validation, secours, durées, exigence, étiquettes, emploi des morceaux, jours consécutifs, hauteur, coûts).
- **Tests à dates fixes** : jamais « aujourd'hui » dans un test Vitest (60 dates depuis `PREMIER_JOUR_JUMP`, golden sur 6 dates fixes) ; en e2e, **horloge maîtrisée par décalage de `Date`** (`apps/jump/e2e/clock.ts` : `FIXED_NOW` = midi UTC le 20/10/2026, `atInstant`), **jamais `page.clock.install`**. Le site publié se simule en servant `https://nathan-te.github.io/DailyTrack/jump/…` par le serveur de test (`servePublished`).
- **Jeu** : la page par défaut (`/jump/`, sans `scenario` ni `module`) est le niveau du jour. `?seed=AAAA-MM-JJ` : une date ; **`isPreview(location)`** (`apps/jump/src/dailyInfo.ts`, pur) = aperçu de branche (`/b/<branche>/`) ou serveur local ; **sur le site publié, une date future est refusée** (niveau du jour, « Ce niveau n'est pas encore sorti »), `?debug` et `&solution` ne lèvent jamais ce refus ; une date passée = archive. C'est **une porte, pas une protection** : le générateur est dans le code publié ; la garantie viendra du serveur (phase 2). HUD : `#dayline` (« DailyJump #N », archive / à venir / aperçu, médaille visée) ; bandeau : médaille obtenue et temps de l'auteur ; palette = `paletteForDay(date du niveau)`. **Passage de minuit** : la partie continue, « Nouveau niveau disponible », le prochain « recommencer » recharge la page sur le nouveau jour. `&solution` : la rediffusion de l'auteur. `?debug` : limites des morceaux (identifiant, variante, exigence) et `__jump.daily`.

## Lot 7 — variété
- **Format 3** (`format: 3`, `MODULE_FORMAT`) : en plus du lot 6, **`famille:`** (obligatoire), **`enchainement: long`** et **`elan: oui`** (facultatifs), **`mutateurs:`** (liste) ; un fichier v2 est refusé. Format complet en tête de `packages/jump-sim/src/modules.ts`.
- **Mutateurs** (`MUTATORS`, purs et déterministes, `mutateTemplate`) : une transformation déclarative du **gabarit**, avant le déroulé des plages `repeter` (une zone posée sur une plage est recopiée avec elle) ; `denivele` agit après le déroulé. Chaque mutateur accepté a sa **zone** dans le bloc annexe, en coordonnées du gabarit (`a-b` ou `a`) :
  - `zone plafond <colonnes> <rangée>` → `+plafond` (`:nu`) plein du haut jusqu'à la rangée ; `+plafond:pics` la rangée garnie de `v` ;
  - `zone fosse <colonnes> <rangée>` → `+fosse` : fond vide (rien jusqu'en bas) ↔ fond de pics `^` posé sur du plein ;
  - `zone sol-friable <colonnes> <rangée>` → `+sol-friable` : `#` → `x` ; `zone ressort <colonnes> <rangée>` → `+ressort` : `#` → `*` ;
  - `zone patrouille <rayon> <cycle> <mode> <c,r>…` → `+patrouille[:cycle]` : une scie mobile de plus (id `mutee`) ;
  - `zone garde <colonnes> <rangées> <pic>` → `+garde` : ces tuiles vides prennent le pic (`<` `>` `^` `v`) ;
  - `zone denivele <colonnes jusqu'au bout>` → `+denivele:<k>` : la fin descend de k rangées (k < 0 : monte), la sortie aussi ; **jamais dans un couloir** (le plafond descend avec le sol) ni sur une scie.
  Une variante : `variante: haut=2 +plafond:pics +denivele:2` (des paramètres et **au plus 2 mutateurs**, `MAX_MUTATIONS`). Une zone qui ne s'y prête pas (tuile inattendue) est une erreur claire. **Une variante mutée est résolue, notée et retirée du fichier** si elle est au pas près, si son raccord passe sous 90 % ou si elle n'a pas de solution.
- **Au plus 6 variantes par morceau** (`MAX_VARIANTS`, refusé par `parseModule`), deux variantes identiques refusées.
- **Familles** : `famille:` regroupe les morceaux de même intention (`cheminee`, `cheminee-scie`, `cheminee-pics`… → `cheminee` ; un enchaînement long prend la famille de sa première intention). **Une seule famille de chaque par niveau** (règle de `compose` et de `dailyProblems`, testée sur 60 dates).
- **Règle des plats** (`tools/plats.ts`, test) : dans un morceau, un plat **sans défi** (colonnes consécutives au même sol plein ou friable, sans pic ni scie dans les 3 rangées au-dessus, sur tout le cycle des scies) ne dépasse pas **6 tuiles** (`FLAT_MAX`) ; seulement si l'élan est le défi lui-même : **`elan: oui`**, 9 tuiles au plus (`ELAN_FLAT_MAX`), et le morceau doit en avoir besoin (aujourd'hui : `saut-long`). Une respiration n'est jamais une course à plat (au moins trois sauts à faire, test).
- **Enchaînements longs** (`enchainement: long`) : deux intentions sans palier au milieu, solution de **5 à 8 s** entre l'entrée et la sortie (`LONG_MIN_TICKS`, `LONG_MAX_TICKS` ; les autres : 1 à 6 s) ; le solveur cherche jusqu'à 11 s. Le niveau du jour en met **1 ou 2** (`MIN_LONG`, `MAX_LONG`, imposé à partir de `FORCE_LONG_AT`).
- **Cibles**, mesurées par `npm run measure:jump -w @cdj/jump-sim` (120 dates) et vérifiées par des tests à seuils sur 60 dates : morceaux en commun entre deux jours consécutifs **≤ 1,5 en moyenne, 4 au plus** ; plus longue course au sol sans saut **≤ 1,2 s en moyenne, 2 s au plus** (`LONGEST_RUN_MAX`, règle du générateur ; `DailyLevel.longestRun`) ; course à vide aux raccords < 6 % ; secours jamais utilisé. Mesure seulement : un même morceau au plus 3 fois sur 7 jours glissants, familles par niveau, part des enchaînements longs, emploi des mutateurs.
- **Tout nouveau morceau** passe par `npm run solve:modules -w @cdj/jump-sim` (`--only=<id>` : seulement lui, les autres gardés tels quels) **et par la galerie** (`?modules`, filtres par étiquette et par famille, mutateurs de chaque variante) ; `npm run voir:module -w @cdj/jump-sim -- <id>` (outil d'écriture) montre chaque variante construite et ses plats. Puis `measure:modules`, le repos (`npm run repos:modules -w @cdj/jump-sim`), `JUMP_GENERATOR_VERSION` +1, golden, `measure:jump`.

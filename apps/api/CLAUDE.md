# `apps/api` : consignes du serveur et de la plateforme

Chargé quand on lit un fichier de `apps/api`. Contient (1) les règles du serveur de DailyTrack (classement, pseudos, Salon serveur, profil, jour de Paris, production Cloud Run + Turso) et (2) les **règles de la plateforme** (registre des jeux, identité commune, recette, aperçus, workflows) communes à tous les jeux — rubriques « Plateforme (lot P0) », « Emplacements » et « Recette (lot R1) » en bas. Vision de la phase 2 : `docs/plateforme/seed-phase-2.md` (**ne pas modifier**, c'est Nathan qui le fait). Synthèse de DailyTrack : `docs/orchestration.md`. Autres consignes : `packages/sim/CLAUDE.md`, `apps/web/CLAUDE.md`.

> **Renvois « voir <rubrique> »** : une rubrique citée mais absente de ce fichier se trouve dans un autre `CLAUDE.md` du dépôt ; l'index des rubriques est dans le `CLAUDE.md` racine. Pour l'état d'ensemble, partir de la synthèse ; n'ouvrir un README de lot que pour un détail.

## Classement (lot 5)
- `apps/api` : `createApi({ db, now })` (`src/api.ts`) ne dépend que de `Request`/`Response` et de `SqlDb` ; adaptateurs : Node (`server.ts`, Docker, Cloud Run) avec **Turso / libSQL** en production et SQLite en local, et Cloudflare Workers + D1 (`worker.ts`, non utilisé). **Le serveur ne fait jamais confiance à un temps annoncé** : il rejoue la rediffusion (`replayRace`) et enregistre son propre résultat.
- **Pseudos réservés (lot 30)** : **un pseudo appartient à son premier propriétaire, sur toute la base**. Clé d'unicité = `nameKey` (`pseudos.ts`) : NFD sans accents, minuscules, espaces réduits (« Nowy », « nowy » et « NÓWY » se confondent) ; colonne `players.name_key` + **index unique** `players_by_name_key` (SQLite et libSQL) ; vérifié avant le rejeu (bon marché) **et** garanti à l'écriture (`isUniqueViolation` → refus propre, jamais une 500). Même règle pour la première course (`submit`), `PUT /api/player` et le Salon : tout passe par `players.ts` (`resolveName` / `save`). Refus = `409 name_taken` + `suggestions` libres (le jeu affiche `erreur.name_taken` : « Ce pseudo est déjà utilisé. C'est le tien ? Charge ton code. » ; lot I6 : plus de `message` dans la réponse) (« Nowy2 », « Nowy_FR »…) ; le jeu montre ces pseudos à toucher et le bouton « Charger un code ». `GET /api/name?name=` répond seulement `{ available }` (+ suggestions libres si pris), limité à 40 par adresse et fenêtre ; **aucune liste de pseudos n'est exposée**. Pseudos refusés : mots interdits et noms réservés (`FORBIDDEN_WORDS`, `RESERVED_NAMES` dans `pseudos.ts`, liste courte et modifiable ; mot de 6 lettres ou plus refusé n'importe où, plus court seulement en mot entier : pas de faux positif sur « Technique »). Le changement de pseudo passe par le débit limité existant.
- **Migration des doublons** (`migratePseudos`, appelée par `ensureSchemaOn` : une seule fois par changement de schéma, au premier démarrage après le déploiement) : le joueur le plus **ancien** (`created_at`, première course) garde le pseudo, les autres reçoivent un suffixe provisoire (« Nowy·2 », `provisionalName`) et `rename_required = 1` ; **aucun temps n'est touché** ; rapport gardé dans `meta` (`pseudo_migration`). Le jeu leur propose, à leur prochaine visite, de choisir un nouveau pseudo ou de charger leur code. `npm run pseudos:migrate` (essai à blanc) / `-- --apply` : même fonction, avec le rapport, contre Turso (`TURSO_DATABASE_URL`/`TURSO_AUTH_TOKEN`) ou SQLite (`DB_PATH`) ; rattrape un joueur créé par l'ancienne révision pendant la bascule. Le suffixe d'affichage `disambiguateNames` (`Nom·2`) ne sert plus qu'aux données d'avant (démo) ; les comptes migrés portent leur suffixe dans leur pseudo.
- **« Aujourd'hui » = la date à Paris, grâce de 10 min après minuit de Paris** (lot 31 ; **remplace la règle « jour UTC »**) : seul le jour courant accepte des temps, puis le jour d'avant pendant 10 min ; un jour passé est figé. Voir « Jour de Paris (lot 31) ».
- Le client est dans `apps/web/src/{api,identity,online,profileSync}.ts` (depuis le lot P0, façades du module de profil commun `@cdj/profile`, `packages/profile`) ; adresse de l'API : `?api=` ou `VITE_API_URL`. Sans elle, aucun classement.
- Tests : `apps/api/test` (SQLite en mémoire, horloge injectée) ; e2e `leaderboard.spec.ts` (Playwright lance le vrai serveur : `npm run test:e2e` construit aussi `apps/api`). Outils `?debug` : `timescale=N`, `__cdj.autoplay(code)`.
- Le Worker ne tient pas dans les 10 ms de calcul de l'offre gratuite de Cloudflare (voir docs/lots/lot-5-classement.md).

## Garage (lot 41)
- **`GET /api/garage`** (`cdj.ts`, identifiant **obligatoire** en `X-Player-Id` : 400 `invalid_player` sinon ; 410 `code_revoked`) : `{ progres { jours, or, auteur }, voitures [{ id, debloquee, progres { fait, nombre } | null }] }`. **`POST /api/submit`** rend aussi `garage` (le même, plus `nouvelles` : les voitures que cette course débloque). Lectures en mémoire (120 par adresse, 60 par joueur et par fenêtre), aucune écriture.
- **Les règles** : `DEBLOCAGES` de `packages/sim/src/garage.ts` (une ligne par voiture, lue aussi par le jeu) ; **seuls les meilleurs temps du circuit du jour rejoués par le serveur comptent** (`results` ; jamais le Salon, jamais un temps annoncé), une médaille avec les seuils **de son jour** (`medalsFor(temps du pilote, jour)`). Les jours passés comptent : rien à migrer. **Lot 42 : six règles de plus** (fourgonnette, rallye, roadster, pick-up, muscle car, monoplace) : **la table `DEBLOCAGES` fait foi** (dix lignes ; ne pas la recopier ici, `packages/sim/test/garage.test.ts` la teste).
- **Coût** : une requête indexée (`results_by_player`, puis la clé de `circuits`), ≈ 2 lignes lues par jour joué par ce joueur, indépendante du nombre de classés ; la même requête s'ajoute à l'envoi. Aucune donnée gardée de plus (rien à effacer, mentions inchangées côté serveur).
- Tests : `apps/api/test/planning.test.ts`, bloc « Garage (lot 41) » (SQLite **et** libSQL ; dans ce fichier parce que la zone de Track était une liste fermée). **Zone** (lot de plateforme « suites de Track 2 ») : `apps/api/src/garage*.ts` et `apps/api/test/garage*.test.ts` sont des fichiers de Track (`scripts/zones-jeu.mjs`, `scripts/ci-scope.mjs`) : un lot de Track peut y ranger le Garage du serveur ; rien n'y est encore déplacé.
- **La voiture de chaque course et le choix du Garage (lot 51)** — README : `docs/lots/lot-51-nettete-voitures.md` ; types et règles : `packages/sim/src/garage.ts` (`VoitureDeCourse`, `voitureLue`, `coderVoiture` / `decoderVoiture`, `voitureAutorisee`, `VOITURE_PAR_DEFAUT` = la Sparrow en orange). **Données nouvelles** : `results.car` et `salon_runs.car` (texte `id.couleur.motif.teinte`, `NULL` pour une ligne d'avant ; migrations `ADD COLUMN` en avant seulement) et la table **`garage_choices`** (`player_id`, `car`, `minute` : le choix du Garage de chaque joueur, `TABLES_VIDEES`, effacée par `erase`, suit « Changer mon code »). **Une donnée à part : jamais dans la rediffusion** (`results.replay` est celle qui a été envoyée). **À l'envoi** (`POST /api/submit` et du Salon) : le corps peut porter `voiture` ; le serveur la garde **si elle est lisible et débloquée pour ce joueur** (`voitureAutorisee` sur la progression d'après cette course ; `garageOuvert` pour « Démo » en recette), **sinon la Sparrow en orange** ; un meilleur temps remplace la voiture avec lui, un temps moins bon la laisse ; la progression est lue **avant** l'écriture (la même requête indexée qu'avant : aucune lecture de plus). **Rendue** : `voiture` dans `GET /api/day/<date>/ghost` (`first`, `ahead`), dans chaque fantôme du Salon (`/ghosts`) et dans `best` de `GET /api/me` (toujours renseignée : la Sparrow en orange pour une course d'avant). **`PUT /api/garage`** (en-tête `X-Player-Id`, corps `{ voiture, minute }`, `minute` en minutes ; 404 `unknown_player` tant que le joueur n'est pas classé) : enregistre le choix ; **une voiture non débloquée est refusée** (`enregistre: false`, rien n'est écrit) ; **un choix illisible donne la Sparrow en orange** ; **le dernier choix l'emporte, à la minute près** (une minute plus ancienne que celle gardée est refusée, la même minute écrase, une minute dans le futur est ramenée à celle du serveur + 1) ; la réponse rend toujours ce que le serveur garde (`voiture`, `minute`). **Relu sans requête de plus** : `garage: { voiture, minute } | null` dans `GET /api/me` (que le jeu lit déjà au chargement) et `choix` dans `GET /api/garage`. Codes d'erreur : aucun de nouveau ; coût : `TRACK_PLAYER` (16 requêtes : le seul ajout est l'enregistrement du choix, une ligne écrite). Tests : `apps/api/test/garageVoiture.test.ts` (SQLite **et** libSQL), `packages/sim/test/garage.test.ts`. **Effacement et mentions** : le choix de voiture et la voiture de chaque course sont des données gardées (pages des mentions, `docs/plateforme/effacement.md`).
- **Recette** : le joueur « Démo » (`players.demo = 1`) reçoit les dix voitures ouvertes sur un serveur `ENVIRONMENT=recette` (`garageOuvert`, `cdj.ts`, lot de plateforme « le Garage de Démo »), jamais en production ; sa vraie progression (`progres`) reste celle de `portailDemo.ts` (voir « Portail (lot I2) »).
- Codes d'erreur et coût : route `/api/garage` dans `apps/api/test/codesErreur.test.ts` et `docs/plateforme/codes-erreur.md` ; `TRACK_PLAYER` de `apps/api/scripts/platformBudget.ts` (+1 requête par ouverture du Garage — 15 requêtes —, aucune de plus à l'envoi ; l'envoi lit une ligne indexée de plus par jour joué).

## Historique et mode démo (lot 11)
- **`PREMIER_JOUR`** (`packages/sim/src/calendar.ts`, ex-`LAUNCH_DAY`) : le circuit n° 1, **le 2026-10-13, date de la mise en ligne** (lot 28 ; provisoirement le 22/09 avant). Il ne change que la numérotation (`circuitNumber`), jamais un circuit : les golden gardent texte et temps, seul leur champ `number` suit (`UPDATE_GOLDEN=1 npx vitest run packages/sim/test/golden-daily.test.ts`) ; **avant ce jour l'en-tête n'affiche pas de numéro** et l'API refuse les temps (`unknown_day`). Les tests du générateur et de l'API sont ancrés sur des dates fixes (06/10 et 14/10/2026) ; un test ancré sur une date d'avant le premier jour doit le savoir (numéro ≤ 0, archives, démo : `?api=demo` couvre les 14 jours depuis `PREMIER_JOUR`).
- **`npm run history:seed`** (`apps/api/src/history.ts` + `scripts/history-seed.ts`) : 14 jours depuis `PREMIER_JOUR`, 8 à 15 pilotes `Démo …` par jour, conduits par le pilote automatique à des niveaux variés ; leurs courses passent par **`createApi(...).handle`** (rejeu serveur, aucun contournement) dans une base **en mémoire** ; joueurs marqués `players.demo = 1` (option `demoPlayers`, **jamais réglée par le serveur de production**) ; refus avec `DB_PATH`, `NODE_ENV=production` ou une base contenant de vrais joueurs (`assertDemoOnly`). Écrit `apps/web/public/demo/` (`index.json` + un fichier par jour : classement figé + fantôme du premier) ; déterministe, ≈ 10 s. **À relancer après tout changement de `SIM_VERSION` ou `GENERATOR_VERSION`** (le test `apps/web/test/demo.test.ts` le rappelle : « relancer history:seed »).
- **`?api=demo`** (`apps/web/src/demo.ts`, `DemoApi` : même interface `LeaderboardSource` que l'API réelle) : lecture seule des données statiques, rien n'est envoyé ; « aujourd'hui » figé à `DEMO_TODAY` (le lendemain de l'historique) donc aucun jour classable ; seul le fantôme du premier existe (pas « devant toi »). **`?day=AAAA-MM-JJ`** = `?seed=` ; ouvrir un jour passé avec classement (API ou démo) charge le fantôme du premier et affiche le classement figé. Archives : seuils de médailles, nombre de pilotes et ta place figée (`archiveExtras.ts`). Tests : `demo.test.ts`, `apps/api/test/history.test.ts`, `e2e/demo.spec.ts`.
- **Règle : les joueurs `demo` n'existent jamais en production** ; les données de démo sont un fichier statique du jeu, pas des lignes d'une base réelle.

## Admin et planning (lot 14)
- **Variantes** : `dailyCircuit(jour, variante = 0, thème?)` (`generator.ts`). **La variante 0 est exactement le circuit d'avant** (même texte, même id sans suffixe : golden et rediffusions de référence inchangés) ; une variante n ≥ 1 décale la graine de n × 1000 tentatives et ajoute `-v<n>` à l'id ; un thème imposé ajoute son nom : `jour-AAAA-MM-JJ-g<G>[-v<n>][-<thème>]` (`dailyTrackId(jour, thème, variante)`, `isVariant`, `MAX_VARIANT` = 99). **Changer la façon dont une variante est tirée = `GENERATOR_VERSION` +1** comme pour le reste du générateur.
- **Planning (API)** : table `planning` (jour → variante, thème imposé, date du choix). `getCircuit` lit le planning et **rejoue toujours le circuit en vigueur** (cache ignoré s'il est d'une autre variante ou version). Public : `GET /api/day/AAAA-MM-JJ` (`variant`, `theme`, `trackId`), `GET /api/planning` (jours remplacés jusqu'à aujourd'hui). Admin (`Authorization: Bearer`) : `GET /api/admin/overview`, `PUT` / `DELETE /api/admin/planning/AAAA-MM-JJ`.
- **Jeton** : `ADMIN_TOKEN` (variable d'environnement, ≥ 16 caractères, jamais dans le dépôt ; absent ou court = admin désactivé, routes en 404), comparaison à temps constant, 10 mauvais jetons par 10 min et par adresse puis 429.
- **Règle : un jour commencé est figé** — remplacement et retour à l'original refusés pour aujourd'hui et le passé (date de Paris, 409 `day_started`), au plus 60 jours à l'avance ; le circuit est généré et validé à l'enregistrement.

## Salon (lots 26 et 27)
- **Serveur du Salon (lot 27)** : `apps/api/src/salon.ts` (`createSalon`, branché dans `createApi` ; `errors.ts` porte `HttpError`). Routes du contrat (`now`, `board`, `ghosts`, `submit`) ; **plus de route `podiums`** (retirée au 27b). **Le serveur rejoue chaque envoi sur `salonCircuit(session)` et n'enregistre que son temps** ; accepté de `start` à `end + 3 s` (lot 31) (`session_future` / `session_closed` sinon), `track_mismatch`, `sim_version`, `not_finished` ; meilleur temps par joueur et par session ; joueur créé par une course valide (table `players` commune avec le jour). Tables `salon_runs` (avec la **`ref` publique** = empreinte salée de `session|identifiant`), `salon_sessions` (version du classement), `salon_circuits`, `salon_presence` (empreinte seule), `salon_throttle` (`salon_podiums` supprimée au 27b). **Une session finie est oubliée** (voir « Le Salon oublie », ci-dessous). **Débit** : un envoi / 5 s / joueur (UPSERT atomique), 60 envois par adresse et par 10 min comptés **en base** avant tout rejeu ; 600 lectures par adresse et par 10 min comptées **en mémoire** (par instance : une lecture n'écrit rien). **Circuits** : `api.tick()` (Node : toutes les 15 s) garde le circuit de la session et génère celui de la suivante **dans les 2 dernières minutes** (≈ 0,4 s sur le fil de Node) ; gardé en base. **`SALON_MINUTES`** (0,5–60, **tests et local seulement, jamais en production** ; répété dans `/api/health`) ; le jeu lit la durée dans `now`. `PRAGMA synchronous = NORMAL` (WAL) : un fsync par lecture-écriture bloquait le fil (mesuré). Tests : `apps/api/test/salon.test.ts`, e2e `salon-serveur.spec.ts` (vrai serveur sur le port 8788 avec `SALON_MINUTES=1`, deux navigateurs). **Charge mesurée** (`npm run measure:salon`) : 50 joueurs = 3,2 % du fil (0,64 ms par joueur et par seconde, rejeu ≈ 18 ms, lecture ≈ 0,6 ms), ≈ 770 joueurs à 50 % sur un Xeon 2,8 GHz ; détail et réserves : `docs/lots/lot-27-salon-serveur.md`.

### Le Salon oublie (retouche 27b)
- **Règle : une session finie est oubliée.** Décision de Nathan : une fois le circuit changé, on ne garde **rien** de la session précédente — ni courses, ni classement, ni podium, ni circuit. À `fin + 20 s` (depuis le lot 31 : la fenêtre de lecture `SALON_SERVE_MS`, pendant laquelle le classement final et ses fantômes restent servis pour le podium du jeu ; les envois, eux, sont clos à `fin + 3 s`), `salon_runs`, `salon_sessions` et `salon_circuits` de cette session sont **effacés** ; `board` / `ghosts` répondent 404 pour elle ; plus de table `salon_podiums` (supprimée par `MIGRATIONS`), plus de route `GET /api/salon/podiums`. Même règle en mode démo (`DemoSalonApi.forget` : rien de la session précédente après la bascule, la course du joueur comprise).
- **Nettoyage à la demande, jamais en tâche de fond** (`forget`, `apps/api/src/salon.ts`) : appelé au début de chaque route du Salon, il compare un entier (la dernière session oubliée par **cette instance**) et ne fait des `DELETE` qu'à la première requête qui voit une session terminée ; une instance qui démarre refait le nettoyage une fois (rattrape un arrêt prolongé, ou les sessions gardées 48 h par la version précédente). Sur Cloud Run le service peut être éteint : rien ne dépend d'une minuterie (`api.tick()` ne sert plus qu'à préparer le circuit suivant).
- **Présence espacée** : au plus **une écriture par joueur et par 30 s** (`PRESENCE_WRITE_MS`) — l'instance retient sa dernière écriture (aucune requête dans l'intervalle) et l'upsert est **conditionnel** (`WHERE seen_at <= excluded.seen_at − 30 s` : une autre instance ne le fait pas écrire de plus) ; présent = vu dans la dernière minute (`PRESENCE_MS` 60 s, le double de l'intervalle, sinon un joueur qui lit en continu clignoterait). **Un spectateur ne compte pas** : sans identifiant de joueur (`SalonApi.now(null)`, `board(session, null)`), le serveur n'écrit rien.
- **Écritures en base** (Turso facture les lignes écrites) : `npm run measure:salon` compte les lignes écrites par table (`changes()`) ; mesures avant / après et décisions dans `docs/lots/lot-27b-salon-oubli.md`. Piège trouvé par la mesure : le **débit des lectures** (`rate`) écrivait aussi à chaque lecture (947 lignes par joueur et par heure, autant que la présence) : il est maintenant en mémoire.

## Finale du Salon (lot 31)
- **Serveur** : un envoi n'est accepté que jusqu'à **`fin + 3 s`** (`SALON_GRACE_MS`, était 60 s) ; marge réseau justifiée dans le code et `docs/lots/lot-31-futur-finale.md` (une course finie *avant* l'heure pile peut arriver après ; une course non finie à l'heure pile n'est jamais envoyée). La session reste **lue** (classement, fantômes) jusqu'à **`fin + 20 s`** (`SALON_SERVE_MS`) pour le podium, puis oubliée (27b). Sessions toujours alignées sur l'horloge (xx:00, xx:10…) ; `?salonMinutes` suit la même règle.

## Jour de Paris (lot 31)
- **« Aujourd'hui » = la date à Paris** (Europe/Paris, heure d'été comprise), la même pour tout le monde au même instant, où que soit le joueur (décision du 14/10/2026 ; **remplace la règle « jour UTC »**). Une seule fonction, **hors de `sim`** : `packages/clock` (`@cdj/clock`, `parisDay(ms)`, `parisDayStart(jour)`, `msUntilNextParisDay(ms)`), qui lit `Intl.DateTimeFormat` avec `timeZone: "Europe/Paris"` et se **contrôle** contre la règle de l'Union européenne (dernier dimanche de mars à 01 h UTC → dernier dimanche d'octobre à 01 h UTC) sur des instants de contrôle ; sans fuseaux dans l'environnement, c'est la règle seule (`parisClockSource` : `intl` ou `table`, rendu par `/api/health` → `clock`). `sim` reçoit toujours une date : **les circuits de chaque date ne changent pas**, seul l'instant où « aujourd'hui » passe au jour suivant bouge (aucune version à monter).
- **API** : jour accepté pour un envoi, **grâce de 10 min après minuit de Paris** (`GRACE_MS`), classement du jour, jours figés du planning, `GET /api/day`, `/api/me`, admin : tout passe par `today = parisDay(now())` et `parisDayStart`. Un jour peut durer **23 h, 24 h ou 25 h** (changements d'heure : 25/10/2026, 28/03/2027) : ne jamais supposer 86 400 000 ms.
- **Jeu** : accueil « Prochain circuit dans HH:MM:SS (minuit, heure de Paris) » (`#home-nextday`) ; à zéro la page se recharge sur le nouveau circuit (une course en cours n'est pas interrompue : l'accueil est fermé ; son temps compte s'il est envoyé pendant la grâce). Admin : « Aujourd'hui (Paris) ».

- **Secrets** (Secret Manager → variables d'environnement, jamais dans le dépôt, la configuration en clair ni les journaux) : `TURSO_AUTH_TOKEN`, `ADMIN_TOKEN`, `RATE_SALT`. Variables non secrètes : `TURSO_DATABASE_URL`, `ALLOWED_ORIGINS`, `TRUST_PROXY=1`, `GIT_SHA`.
- **Configuration** (`apps/api/src/config.ts`, pure et testée) : `readConfig(env)` ; `server.ts` sort en erreur (code 1, ligne JSON « configuration refusée ») si **`SALON_MINUTES` est réglée en production** (`NODE_ENV=production`, posé par l'image), si `ALLOWED_ORIGINS` ou `RATE_SALT` (≥ 16 caractères) manquent en production, ou si **`TURSO_DATABASE_URL` manque sur Cloud Run** (`K_SERVICE` : le disque est effacé à chaque redémarrage). Hors Cloud Run et sans Turso : SQLite local (`DB_PATH`), comme avant.
- **Base** : interface `SqlDb` (`db.ts`) ; implémentations SQLite (`node:sqlite`, `node-sqlite.ts`), D1 (`d1.ts`) et **libSQL / Turso** (`libsql.ts` + `libsql-open.ts`). Turso : client HTTP pur JavaScript embarqué dans le paquet (`@libsql/client/http`, `libsql://` lu comme `https://` : aucune connexion qui dure) ; `file:` (développement, tests) : client natif chargé à la demande, absent de l'image. **Une instruction = un aller-retour réseau** : les lectures indépendantes se font en parallèle (`board`), le schéma en un lot (`SqlDb.batch`). **Schéma** : `ensureSchemaOn` crée ou met à jour au premier appel de chaque instance ; l'empreinte du schéma est dans la table `meta` (`schemaVersion()`, calculée du texte de `SCHEMA` + `MIGRATIONS` : **aucun numéro à incrémenter**), une instance qui trouve la bonne empreinte ne fait qu'une lecture. Un échec au démarrage n'est pas gardé (la requête suivante réessaie). Piège : `rowsAffected` de libSQL vaut 0 pour une instruction avec `RETURNING`.
- **Tests sur les deux bases** : `vitest.config.ts` a deux projets (`sqlite`, `libsql`) ; les tests d'API passent par `openTestDb()` (`apps/api/test/helpers.ts`, fichier libSQL temporaire : `:memory:` y perdrait la base). Toute nouvelle requête SQL doit passer sur les deux (`npm test` le fait).
- **CORS** (lot R4 : les origines viennent de `scripts/domaine.mjs`, voir « Domaine et origines (lot R4) ») : `ALLOWED_ORIGINS` (virgules ou points-virgules) = origines, **sans chemin** (`https://playdujour.com`) ; l'origine de la requête est répétée si elle est listée (`Vary: Origin`), sinon aucun en-tête CORS. `*` autorise tout. `ALLOW_ORIGIN` (une seule valeur) reste pour les anciennes installations.
- **Adresse du client** : `TRUST_PROXY=<n>` = nombre de proxys de confiance, l'adresse est lue **depuis la droite** de `X-Forwarded-For` (chaque proxy ajoute la sienne à la fin ; le début est falsifiable par le client et ferait tomber la limite de débit). **2 derrière Firebase** (mesuré au lot R5) ; un appel direct à `run.app` peut alors inventer cette entrée : voir « Sécurité, mentions et effacement (lot R5) ».
- **Règle : pas de tâche de fond indispensable.** Cloud Run n'alloue du calcul que pendant une requête et éteint le conteneur sans joueurs. Le circuit du jour (`getCircuit`) et celui d'une session du Salon (`circuitFor`) sont **générés par la première requête qui en a besoin** (≈ 0,2–0,5 s), **un seul calcul même si deux requêtes arrivent ensemble** (promesse en cours par jour / session), puis gardés en base ; avec deux instances le calcul peut se faire deux fois, le résultat et l'écriture sont identiques (déterministe). `api.tick()` (préparation du circuit suivant du Salon, toutes les 15 s) ne tourne **qu'hors production**. L'oubli du Salon est déjà à la demande (27b).
- **Débit avec 2 instances** : les envois (par adresse, par joueur, échecs d'admin) sont comptés **en base** (exacts quelle que soit l'instance) ; les lectures du Salon sont comptées **en mémoire par instance** (la limite réelle est au plus doublée, voir 27b) ; la présence est limitée en base (`seen_at`).
- **`/api/health`** : `{ ok, db, simVersion, generatorVersion, today, salonMinutes, salonOverride, revision? }`, **503 `db: "error"`** si la base ne répond pas. **Journaux** (`log.ts`) : une ligne JSON par événement (`severity`, `message`, champs courts) ; démarrage, schéma, circuit généré, temps accepté, 429, 5xx. **Jamais** de rediffusion, de pseudo, d'identifiant ni d'adresse (test `production.test.ts`) ; les lectures ordinaires ne sont pas journalisées.
- **Code de transfert** : voir « Profil (lot 30) » (depuis le lot 30 le code ne contient plus que l'identifiant secret, `CDJ2`) ; cartes du profil : accueil et **Réglages › Profil**.
- **Sauvegarde automatique (lot R12)** : avant chaque mise en production (et à chaque `essai`, pour la recette), le job `sauvegarde` de `production.yml` lit **toute la base en lecture seule** (`npm run base:sauvegarde -w @cdj/api` : `src/sauvegarde.ts`, une transaction de lecture ; texte SQL au format de `sqlite3 .dump`, **restauré dans SQLite et recompté avant d'être gardé** ; testé : `test/sauvegarde.test.ts`) et le dépose dans le bucket privé **`gs://dailytrack-511513-sauvegardes/production/…sql.gz`** (`…/recette/…` pour un essai ; région `europe-west1`), **effacé au bout de `SAUVEGARDE_JOURS` = 30 jours** (`config/sauvegarde-cycle.json`, dit dans les mentions légales). Le jeton lu est un **jeton Turso en lecture seule** (`cdj-turso-lecture` / `cdj-recette-turso-lecture`, Secret Manager) que seul le compte `cdj-sauvegarde` lit, et ce compte, seul le job de l'environnement GitHub `sauvegarde` (limité à `main`) le prend ; `cdj-deploy` n'y a aucun accès. Jamais en artefact ni dans un journal (le résumé : noms de tables et nombres de lignes). **Restaurer** : `gcloud storage cp <fichier> . && gunzip … && turso db create <nouvelle base> --from-dump <fichier>.sql` (commande exacte dans le résumé du run ; installation et restauration : `docs/plateforme/mise-en-production.md`, annexe C). Le retour arrière, lui, ne touche jamais la base.
- **Budget** (`npm run measure:budget`, résultats dans le README du lot 28) : un joueur du circuit du jour = ≈ 9 requêtes ; 30 minutes de Salon = ≈ 560 requêtes (le Salon interroge toutes les 5 s) : **ce sont les requêtes du Salon qui limitent l'offre gratuite** (2 millions par mois), puis les lignes lues de Turso quand beaucoup de joueurs sont présents.

## Le garde-fou des jours et la répétition (lot R6)
README : `docs/plateforme/lots/lot-R6-garde-fou-des-jours.md` ; liste de contrôle de Nathan : `docs/plateforme/mise-en-production.md`. Code : `scripts/mise-en-production.mjs` (jour de bascule, comparaison, inventaire, jours servis ; testé : `apps/portail/test/miseEnProduction.test.ts`), `apps/api/scripts/empreintes.ts` + `empreintes-jours.ts` (`npm run jours:empreintes`), `scripts/base-migree.mjs`, `.github/workflows/production.yml`.
- **Le jour de bascule** = le premier jour de Paris qui commence après le déploiement, calculé **au clic** (`jourDeBascule`, calendrier et non des heures : un jour dure 23, 24 ou 25 h). Avant lui, **aucun jour ne change** ; à partir de lui, 14 jours (`JOURS_REGENERES`) sont régénérés avec le nouveau code et doivent être valides (ni circuit ni niveau de secours). `deploy-api.yml` et `deploy-site.yml` re-vérifient, **après la validation de Nathan**, que le jour de bascule n'a pas commencé (`bascule-valide`, entrée `bascule_le`) ; le retour arrière est refusé une fois ce jour commencé (`apres_le_jour_j` pour passer outre ; l'étiquette `prod-…` note `basculement:`).
- **Le garde-fou** (job `figer` de `production.yml`, avant tout déploiement) : (1) `jours-servis` remet les jours figés que la production sert (PR « Jours figés » fusionnées depuis l'étiquette) ; (2) `freeze:days` **jusqu'à la veille de la bascule** avec le code en production ; (3) `empreintes` du code en production **et** de la nouvelle construction (jours figés superposés), de la journée n° 1 à bascule + 13 ; (4) `comparer` : **une différence avant la bascule = `exit 1`** (jours en cause dans le résumé) ; (5) `base-migree` : le serveur en production sur la base que le nouveau code a migrée, puis son `smoke`. **Ce que sert un jour** (`empreintes.ts`) : Track `dailyCircuit(jour)` (id, texte, temps du pilote, médailles, thème), Jump le fichier figé s'il se vérifie (`thawLevel`), sinon `dailyLevel`. Les empreintes des jours passés sont gardées dans `apps/api/test/jours-passes.json` (ajoutées par la PR « robot ») : `jours-passes.test.ts` fait échouer une PR qui changerait un jour passé.
- **Jours protégés et registre de Track (lot R11, décision de Nathan)** — README : `docs/plateforme/lots/lot-R11-track-fige-ses-circuits.md`. Le garde-fou ne protège que **les jours d'avant le lancement, les jours déjà figés (une plage du registre de Track, un fichier de Jump) et les jours qui ont au moins un résultat en production** ; un jour à partir de la journée n° 1 sans aucun résultat est régénéré avec le code déployé. (1) `proteges` lit les jours qui ont des résultats **en lecture seule** (`lireResultats`, `scripts/mise-en-production.mjs` : un `GET /api/portail/classement?date=` par jour non figé, sans identifiant ni corps ; `classes` = les joueurs qui ont fini au moins un jeu ce jour-là ; un `429` attend la fenêtre ; **toute autre réponse arrête**, sans cette lecture les jours à protéger sont inconnus) ; (2) `jours-figes-filtrer` retire de `freeze:days` les niveaux de Jump des jours sans résultat ; (3) `registre` demande au code en production sa version de chaque jour protégé (`apps/api/scripts/registre-jours.ts`, copié dans le dépôt visé comme `empreintes-jours.ts` : il marche avec un code d'avant le registre, où la version se choisissait par une date) et `registre-fusion` l'ajoute à `packages/sim/src/jours-track.json` — **une version différente, ou un jour du dépôt au-delà de la veille de la bascule, arrête** ; (4) `empreintes` part du plus ancien niveau figé de Jump (les jours d'avant le lancement « restent tels quels ») et `comparer --proteges` ne tolère une différence que sur un jour sans résultat ; `empreintes-fusion --proteges` ne garde dans `jours-passes.json` que les jours protégés ; (5) `deploy-api.yml` et `deploy-site.yml` fusionnent le registre (artefact `registre-track` : `jours-track.json` et `proteges.json`) avant la construction et **relisent les résultats des jours régénérés** (`proteges-verifier`) : un résultat arrivé pendant la validation de Nathan arrête. `jours-servis --registre` remet le registre de la dernière PR « Jours figés » dans le code en production (même raison que les niveaux de Jump). Tests : `apps/portail/test/miseEnProduction.test.ts` (jour avec un résultat protégé, sans résultat régénéré, d'avant le lancement inchangé ; lecture seule ; fusion du registre ; ligne de commande), `apps/api/test/joursProteges.test.ts` (la lecture contre le vrai serveur : Track, Jump, rien ; aucune écriture de donnée), `jours-passes.test.ts`, `packages/sim/test/registreJours.test.ts`.
- **Répétition** : lot R12, **une étape de chaque mise en production** (la même construction sur la recette, à l'heure réelle, `smoke --lecture-seule` puis `smoke` complet ; un échec arrête avant la sauvegarde et la production) ; seule, avec une heure simulée : `mode: repetition` (`heure_simulee` à Paris, `reference` pour traiter un commit comme « le code en production »), **ni CI, ni sauvegarde, ni étiquette, ni production**.

Tests : `jumpVieuxOnglets.test.ts`.

## Profil (lot 30)
- **Le serveur fait foi, le stockage local n'est qu'un cache.** Un profil = un identifiant secret (`players.id`, 128 bits tirés par le navigateur) + un pseudo réservé + ses temps (`results`). Plusieurs appareils partagent le même profil en chargeant le même **code de transfert**.
- **`GET /api/me`** (identifiant dans l'en-tête **`X-Player-Id`**, jamais dans l'adresse, qui finit dans les journaux de l'hébergeur ; CORS l'autorise) : `{ name, renameRequired, today, simVersion, stats: { days, medals{author,gold,silver,bronze}, bestRank{date,rank,participants}, streak }, best (temps du jour + `trackId`, `splits`, **rediffusion** + `simVersion`, pour le fantôme « ton record »), past[] (`date`, `trackId`, `ms`, `medal` : les médailles des archives) }`. Erreurs : `404 unknown_player` (jamais classé), `410 code_revoked`. Limité à 60 lectures par joueur et 200 par adresse et fenêtre. **Coût** : ≈ 8 instructions et 2 lignes écrites (compteurs de débit) + ≈ 2 lignes lues par jour d'historique ; la **place d'un jour terminé est calculée une fois** (`results.final_rank` / `final_total`, au premier `GET /api/me` après la minute de grâce) puis gardée : sans cela chaque synchronisation relisait le classement de chaque jour (mesuré : 5 770 lignes lues pour 120 jours contre 248). Mesures : `docs/lots/lot-30-pseudos.md`, `npm run measure:budget`.
- **Synchronisation** (`apps/web/src/profileSync.ts`, `ProfileSync` ; la fusion `mergeProfile` est pure et testée) : au **lancement** et au **retour sur l'accueil** (au plus une fois par 30 s, `SYNC_GAP_MS`), le jeu lit le profil et le fusionne avec le cache — **le meilleur gagne** : pseudo du serveur ; temps du jour du serveur plus rapide que le local → il le remplace **avec sa rediffusion** (`best` rechargé, fantôme « ton record » mis à jour sans course en cours) ; jours passés écrits sans rediffusion (médailles des archives) ; meilleure place retenue (`cdj:rank:`) ; `cdj:sub:<circuit>` prend la valeur du serveur. **Rien n'est jamais supprimé** : un record local meilleur que celui du serveur (fait hors ligne) reste, et `syncProfile` (main.ts) l'**envoie** (`online.submit`, le serveur le rejoue — `needsSubmit`). État observable : `online.sync.state` (`idle|syncing|ok|offline|revoked|unknown|disabled`, `known`, `renameRequired`, `nameProblem`, `error`), `__cdj.sync` avec `?debug`. **Hors ligne** : le cache local sert et la carte du profil le dit discrètement (« Hors ligne : voici le profil de cet appareil… »). Pas de serveur / démonstration : `disabled`, rien n'est synchronisé. Un `fetch` dont le corps est vide sur un 200 (page qui se décharge) est une panne réseau (`api.ts`, `call`), pas une réponse.
- **Pseudo** (`Online.rename`) : joueur connu du serveur → `PUT /api/player` (les autres appareils le voient à leur prochaine synchronisation) ; pas encore classé ou pseudo qui partira avec la course (`viaSubmit`) → `GET /api/name` (libre ou non) ; hors ligne → local pour un joueur que le serveur ne connaît pas, **refusé** pour un joueur connu. Pseudo pris : message, suggestions libres à toucher, bouton « Charger un code » (formulaire de l'arrivée, du Salon et de la carte du profil). Compte renommé par la migration : message sur la carte du profil (`cdj:notice:rename` retient « Garder ce pseudo »).
- **Code de transfert simplifié** (`transfer.ts`) : **`CDJ2.<identifiant : 32 hexadécimaux>.<CRC-32 sur 8 hexadécimaux>`** (46 caractères). « Charger un code » lit le profil **sur le serveur** (`GET /api/me` avec cet identifiant), montre le pseudo et les statistiques du serveur, demande confirmation, puis `applyIdentity` : identifiant et pseudo remplacés, cache des records / places / temps confirmés effacé (il appartenait à l'ancienne identité), **sauf le record d'aujourd'hui pas encore confirmé par le serveur** (`pendingTrackIds`), qui sera envoyé au nom du profil chargé ; rechargement, la synchronisation remplit le reste. Sans serveur (démonstration, aucune API) : « Pas de serveur ici », rien ne change. Les **anciens codes `CDJ1`** (lot 28, avec records) restent acceptés : leurs rediffusions d'hier et d'aujourd'hui sont envoyées au serveur pour validation (`legacyReplays`, `ProfileHost.submitLegacy`), les autres sont ignorées — le serveur ne garde que ce qu'il a rejoué. Le code contient l'identifiant secret : à garder comme un mot de passe.
- **Révocation — « Changer mon code »** (Réglages › Profil et carte du profil de l'accueil, **confirmation obligatoire**) : `POST /api/me/code` avec l'ancien identifiant en en-tête et **`{ newId }` tiré par le jeu** dans le corps ; une transaction (`SqlDb.batch`) copie les `results` et le profil sur le nouvel identifiant, **inscrit l'ancien dans `revoked_codes` (empreinte SHA-256 seulement)** et oublie les courses du Salon en cours ; le pseudo et tous les temps sont conservés. Ensuite l'ancien identifiant est refusé en **410 `code_revoked`** (« Ce code n'est plus valide… ») par `/api/me`, `submit`, `PUT /api/player`, le Salon et un second changement ; les lectures publiques (classement, fantômes) ne lui rendent rien. Limité à 3 par joueur et fenêtre. **Rejouable** : le nouvel identifiant est gardé (`cdj:player:next`) jusqu'à la réponse ; si elle se perd, la même demande réussit encore, et la synchronisation adopte `cdj:player:next` quand l'ancien code est refusé. Les autres appareils voient « Ce code n'est plus valide » (carte du profil, formulaires) et chargent le nouveau code.
- **Règles** : aucun changement de `sim` ni des versions (`SIM_VERSION` et `GENERATOR_VERSION` inchangées, golden et `history:seed` inchangés) ; le serveur ne fait toujours pas confiance à un temps annoncé (un record envoyé par la synchronisation est rejoué comme les autres) ; les joueurs de démonstration ont un identifiant **stable par nom** (`fictionalId`, `history.ts`) puisqu'un pseudo n'appartient qu'à un joueur ; **tout nouvel endpoint qui prend un identifiant secret le lit dans l'en-tête `X-Player-Id` et refuse un code révoqué** (`players.assertActive`) ; ne jamais mettre l'identifiant dans une adresse ni un journal ; un nouvel appel qui crée ou renomme un joueur passe par `players.resolveName` / `save`.
- Tests : `apps/api/test/pseudos.test.ts` (unicité, casse et accents, libération, Salon, course simultanée, migration d'une base à doublons, `GET /api/me`, révocation, transaction, débit ; SQLite **et** libSQL), `apps/web/test/{profileSync,transfer,online,api}.test.ts` ; e2e `profil.spec.ts` (serveur dédié sur le port **8790**, plusieurs appareils : pseudo refusé puis code chargé, record vu sur l'autre appareil avec fantôme et médaille, pseudo changé, hors ligne puis réseau revenu, code changé et ancien code refusé). **Piège de test** : les pages ouvertes qui ne servent plus continuent de dessiner en rendu logiciel et affament la page qu'on regarde (le délai de 8 s d'un appel à l'API court pendant que le fil principal est occupé) → les mettre en sommeil avec `__cdj.manual(true)` (`sleep` / `wake` de `profil.spec.ts`).

## Plateforme (lot P0)
Un seul serveur pour tous les jeux du portail : `createApi` (`api.ts`) n'assemble plus que la plateforme et le registre. README : `docs/plateforme/lots/lot-P0-socle.md`.
- **Registre des jeux** (`games.ts` : types ; `registry.ts` : la liste `GAMES`) : **une définition par jeu** (`GameDefinition`) = son code (`cdj`, `jump`), le préfixe de ses routes, ses tables (noms) et leurs instructions de création (`schema`), ses versions, `create(plateforme, options)` ; le jeu créé (`GameInstance`) rend ses routes (`route`), sa fonction **niveau du jour** (`dailyLevel`), sa **validation** d'un essai (`validate` : DailyTrack, rejeu `replayRace` ; DailyJump au lot P1), et ses crochets facultatifs (`onRename`, `rotateStatements`, `profile`, `tick`). **DailyTrack** (`cdj.ts`) garde ses routes historiques sous `/api` (jamais déplacées sous `/api/cdj`) : son préfixe est le plus court, il passe en dernier. Le schéma = `PLATFORM_SCHEMA` (`db.ts` : `players`, `revoked_codes`, `rate`) + le `schema` de chaque jeu, dans l'ordre du registre ; son texte fait l'empreinte de `meta`.
- **Écrit une fois pour la plateforme** : identité, pseudo, profil, code (`identity.ts` : `PUT /api/player`, `GET /api/name`, `GET /api/me`, `POST /api/me/code`), joueurs et pseudos (`players.ts`, `pseudos.ts`), limitation de débit (`platform.ts` : `hit` **en base** pour les envois, `readHit` **en mémoire** pour les lectures, `hashKey` salé), corps de requête (`readJson`, `MAX_BODY_BYTES`), « aujourd'hui » à Paris, schéma ; configuration (`config.ts`), journaux (`log.ts`). Un jeu les reçoit (`Platform`) et ne les réécrit pas.
- **Espace `/api/<jeu>/`** : tout nouveau jeu prend `/api/<code>/` ; DailyJump : `/api/jump/info` (`simVersion`, `generatorVersion`, `today` de Paris, `frozenDays` de l'image, `environment`) et `/api/jump/day/<AAAA-MM-JJ>` (`id`, `hash`, `authorTicks`, `medals`, `theme`, `number`, `source` `fige|genere` ; **jamais la grille**). Lecture seule au lot P0 ; tables `jump_levels`, puis `jump_results` (lot P1 : `POST /api/jump/submit`, `GET /api/jump/day/<date>/board`, voir « Classement de DailyJump (lot P1) »).
- **Règle : le serveur calcule le niveau par la même règle que le client.** DailyJump : d'abord le **fichier figé** de la date (`apps/jump/public/levels/`, embarqué dans le paquet par `scripts/build-node.mjs`, option `jumpFrozen` de `createApi`), accepté seulement si tout se vérifie et **si sa preuve se rejoue** (depuis le lot P1, **la fonction même du jeu** : `thawLevel` de `@cdj/jump-sim` ; `thawFrozen` de `jump.ts` ne fait que la mettre à la forme de `/api/jump/day`) ; sinon `dailyLevel(jour)` de `@cdj/jump-sim`. Gardé en base (`jump_levels`, colonne `rule` = versions + empreinte du fichier figé : une autre règle = recalcul), **un seul calcul même si deux requêtes arrivent ensemble** (promesse en cours par jour). Dates futures refusées (404 « Ce niveau n'est pas encore sorti »), comme avant le premier niveau. **Preuve** : `apps/api/test/jump.test.ts` compare 60 dates et chaque jour figé à `loadDaily` d'`apps/jump` ; un fichier figé abîmé est refusé des deux côtés pour la même raison. Un nouveau jour figé entre dans l'image au prochain déploiement (`api-image` vérifie chaque fichier).
- **Règles d'identité (communes)** : le préfixe `cdj:*` est celui de la plateforme (DailyTrack l'écrit, DailyJump le lit : même origine, même stockage, même préfixe d'aperçu `apercu:`) ; code de transfert **`CDJ2.<32 hexadécimaux>.<CRC-32 sur 8 hexadécimaux>`** (lecture des anciens `CDJ1` dans DailyTrack) ; **un pseudo appartient à son premier propriétaire**, sur toute la base et pour tous les jeux (`players.resolveName` / `save`) ; identifiant secret en en-tête `X-Player-Id`, code révoqué refusé (`players.assertActive`). Côté client, tout passe par `@cdj/profile` (`packages/profile/CLAUDE.md`).
- **Tout nouveau point d'accès a son coût mesuré** (requêtes, lignes Turso lues et écrites, calcul) avant la production : `npm run measure:jump-api -w @cdj/api` (DailyJump, sqld local), `npm run measure:budget` (DailyTrack). `/api/jump/day` : hors cache 2 instructions, 2 lignes lues, 1 écrite, ≈ 0,4 s (généré) ou ≈ 20 ms (figé) ; relu en base 1 ligne lue ; en mémoire 0. `/api/jump/info` : 0.

## Les morts de tout le monde (lot P3)
README : `docs/plateforme/lots/lot-P3-morts.md`. Code : `apps/api/src/jumpLives.ts` (branché par `jump.ts`) ; aide pure de validation : `checkLife` de `@cdj/jump-sim` ; tests `apps/api/test/jumpLives.test.ts` (SQLite **et** libSQL).
- **Décision de Nathan : au plus 30 morts par joueur et par jour** (`JUMP_LIVES_PER_DAY`), appliqué par le jeu **et** vérifié par le serveur ; **seules les vies qui finissent par une mort** comptent (une vie dont le rejeu finit autrement est écartée, `not_death`). Au-delà de 30, les vies en trop sont refusées sans être rejouées et la réponse le dit (`overCap`, `cap` ; lot I6 : plus de `message`). **Chaque mort compte une fois : un joueur pèse au plus 30 morts dans la carte** (voulu).
- **`POST /api/jump/lives`** (identifiant en **`X-Player-Id`**, corps `{ levelId, simVersion, generatorVersion, lives[] }`). **Ordre de validation** : (1) **débit compté en base avant tout** (par adresse `jlip:` à `limits.perClient`, par joueur `jlp:` à `JUMP_LIVES_LOTS_PER_PLAYER` = 20 lots par fenêtre ; compteurs propres aux vies) ; (2) **taille** (`readJson`, 413) ; (3) **le niveau du jour seulement** (`dailyDayOf` : la règle de `submit`, grâce de 10 min ; archive → 409 `day_closed`, thème forcé / futur → 409 `not_daily`) ; (4) **versions** (409 `version`) ; puis le joueur : **seul un joueur qui existe déjà dans `players`** (un résultat valide dans un jeu de la plateforme) envoie des vies, sinon **404 `unknown_player`** (le jeu les garde et les envoie après sa première arrivée acceptée) ; code révoqué 410 ; (5) **plafonds** : 30 vies par lot (413 `too_many_lives`), 8 000 caractères et 2 min de jeu par vie (`JUMP_LIFE_MAX_TICKS`), 5 min de jeu par lot (`JUMP_LOT_MAX_TICKS`) → `too_long`, puis le plafond du jour ; (6) **rejeu de chaque vie** (`checkLife` : en-tête atteignable dans ce niveau, une seule vie qui s'arrête à sa fin, **fin, position et cause calculées par le serveur**). **Une vie invalide est écartée seule**, le reste du lot est accepté ; la réponse donne le sort de chaque vie (`results` : `ok`, `duplicate`, `invalid`, `not_death`, `over_cap`, `too_long`), `accepted`, `dayCount`, `cap`. **Déduplication** : même joueur, même rediffusion (empreinte SHA-256, 48 bits) = comptée une fois, même si un lot est renvoyé.
- **Règle : jamais une ligne écrite par mort ; au plus deux lignes écrites par lot** (hors compteurs de débit, communs à toutes les routes d'envoi ; testé en comptant `changes()` par table) : `jump_lives` (**une ligne par joueur et par jour**, ses vies retenues en JSON compact `[empreinte, col, row, cause, section, rediffusion]`, ≈ 4 ko pour 30 vies ; écriture **conditionnelle** sur `rev`, deux lots simultanés du même joueur ne s'écrasent pas : le second relit et refait la fusion, sans rejouer de nouveau) et `jump_deaths` (**une ligne par jour** : `version` avance à chaque lot accepté ; elle garde la carte et l'échantillon calculés, `built`, `built_at`, `frozen`). Un lot sans vie retenue (doublons, plafond) n'écrit rien.
- **`GET /api/jump/day/<date>/deaths`** : `{ date, levelId, open, players, deaths, tiles }`, `tiles` = `[col, row, morts, cause dominante]` (à égalité, la plus petite cause), **les `JUMP_MAP_TILES` (300) tuiles les plus meurtrières** (`buildDeathMap`, pur). **`GET /api/jump/day/<date>/carnage`** : `{ date, levelId, open, simVersion, generatorVersion, players, dayPlayers, lives[{ replay, section, p }] }` : **≈ 150 vies** (`sampleCarnage`, pur), **au plus 3 par joueur**, **tour à tour une par section** (toutes les sections représentées), **déterministe à partir du jour** (joueurs mélangés par une empreinte du jour et de leur identifiant ; les premières vies de chacun d'abord) ; `p` = numéro de joueur **propre à l'échantillon**, **jamais l'identifiant** ni le pseudo.
- **Carte et échantillon calculés ensemble**, **au plus toutes les 3 minutes** (`JUMP_MAP_REFRESH_MS`) et seulement si des vies sont arrivées depuis (`version` ≠ `built`), à partir de toutes les lignes du jour (une ligne lue par joueur), puis **gardés en base** (la ligne du jour : toutes les instances la lisent) **et en mémoire par instance** (3 min ; un jour fermé sans limite de temps, 64 jours). Un seul calcul même si deux lectures arrivent ensemble. Lectures limitées **en mémoire** (`readHit`, comme les autres lectures).
- **Règle : les vies brutes d'un jour sont oubliées à la fin du jour** (principe du Salon, retouche 27b ; **pas de tâche de fond**) : `forget`, appelé au début de **toute** route `/api/jump/…`, compare un entier (le dernier jour fermé déjà traité par **cette instance**) ; à la première requête qui voit un jour terminé (après la grâce), pour chaque jour fermé qui a encore des vies : **carte finale et échantillon final calculés et figés** (`frozen = 1`, upsert conditionnel `WHERE frozen = 0` : une instance en retard n'écrase jamais une carte figée), puis **`DELETE` des vies brutes**, dans une transaction (`SqlDb.batch`). Une instance qui démarre le refait une fois. Les archives lisent la carte et l'échantillon figés.
- « Changer mon code » : les vies du jour suivent le joueur (`rotateStatements`). `/api/jump/me` **ne change pas** (décision de Nathan : le § 3 du prompt est retiré ; morts et essais du jour restent locaux au jeu).
- **Journaux** : « DailyJump : vies du jour » (`day`, `received`, `accepted`, `duplicates`, `invalid`, `notDeath`, `overCap`), « carte des morts calculée », « vies du jour oubliées, carte et échantillon figés » ; jamais de rediffusion, de pseudo, d'identifiant ni d'adresse (testé).
- **Joueurs fictifs** : `fictionalJumps` rend aussi leurs **vies qui finissent par une mort** (au plus 30, celles de leurs essais fictifs) ; `seedJumpDays` les envoie par le vrai `createApi` (un lot par joueur, après son essai) : `jump:seed` (démonstration : `deaths` et `carnage` dans chaque jour de `apps/jump/public/demo/`, figés pour les jours passés) et `recette:seed` (le jour courant). **`smoke`** : un inconnu refusé (404), un lot de vies accepté et une vie forgée (en-tête incohérent) écartée seule, le même lot renvoyé non compté deux fois, la carte, l'échantillon (sans identifiant).
- **Coût mesuré** (`npm run measure:jump-api -w @cdj/api`, sqld local ; détail : README du lot) : lot de 10 vies 7 à 9 instructions, 9 lignes lues (134 au premier lot de la fenêtre : ménage des compteurs), 4 écrites dont 2 de débit, ≈ 40 ms (rejeu de 10 vies ≈ 5 ms) ; carte recalculée à 1 000 joueurs : 3 instructions, 1 003 lignes lues, 1 écrite, ≈ 190 ms, réponse 0,6 ko ; échantillon 23 ko ; oubli d'un jour de 1 000 joueurs ≈ 3 000 lignes lues, 1 002 écrites (effacements compris). **Joueur type avec le lot P3** : 30 requêtes, 1 252 lignes lues, 32 écrites (P2 : 19, 1 084, 17) ; l'offre gratuite tient jusqu'à ≈ 2 200 joueurs DailyJump par jour (les requêtes de Cloud Run limitent d'abord).

- **La date du lancement** : une seule source, `config/lancement.json` (voir le `CLAUDE.md` racine) ; le serveur la prend de `@cdj/core/lancement` (`createApi({ premierJourDuJour })` pour les tests ; `LANCEMENT_PREMIER_JOUR` pour la **recette et le local seulement**, **refusée en production** par `readConfig`). - **La remise à zéro** (`remiseAZero(db, { now, applique })`) : **en une transaction** (`SqlDb.batch`), `DELETE` de chaque table de `TABLES_VIDEES`, effacement des clés de `meta` qui nomment d'anciens joueurs (`pseudo_migration`), et écriture d'une **nouvelle génération de données**. **La liste est calculée du schéma** (`planDeRemiseAZero` lit les `CREATE TABLE` de `SCHEMA` : plateforme + chaque jeu du registre) : **chaque table est ou vidée (`TABLES_VIDEES`, elle tient une donnée de joueur ou de partie) ou gardée (`TABLES_GARDEES` : `planning`, `circuits`, `jump_levels`, `meta` — le planning de l'administration, deux caches déterministes, la table de service)** ; le test échoue pour une table du schéma classée nulle part (ou citée à tort), et pour une table gardée qui a une colonne nommant un joueur, un pseudo ou une rediffusion. **Toute nouvelle table liée à un joueur rejoint `TABLES_VIDEES` — et le crochet `erase` de son jeu** (effacement d'un joueur). Ne rend que des **nombres de lignes** : rien de personnel (le dépôt est public, les journaux aussi). Les jours figés (fichiers) et la configuration ne sont pas dans la base.
- **La génération de données** : `meta.generation` = l'instant de la remise à zéro en millisecondes (croissant : toujours supérieur à la précédente ; 0 tant que la base n'a jamais été remise à zéro). `Platform.generation()` la lit **au plus toutes les 30 s par instance** (`GENERATION_TTL_MS`, une ligne), `api.ts` l'appelle au début de chaque requête ; **quand elle change, l'instance oublie sa mémoire** (`onGenerationChange` → `onErased` de chaque jeu et `portail.oublier` : classements gardés, premier d'un jour fermé, cartes des morts) — **pas de redémarrage de révision** (décision justifiée : `gcloud run services update` créerait une révision à partir du modèle du dernier déploiement, qui peut être celui d'une PR, et la recette épingle son trafic sur une révision nommée ; la lecture de la génération vide la mémoire de toutes les instances, sans rien redéployer). Elle est **servie** par `GET /api/portail/jour` (`generation`, partie publique, cache 60 s), la lecture regroupée de DailyJump (`bundle`) et `GET /api/day/<date>` de DailyTrack : un navigateur en garde une plus ancienne = il repart de zéro (`packages/profile/CLAUDE.md`, « Nouveau départ »). Un cache qui rend une vieille réponse ne vide jamais un joueur neuf (la génération est monotone côté navigateur). **Coût** : une ligne lue par instance et par 30 s d'activité, aucune écriture.
- **Le workflow « Lancement : remise à zéro »** (`workflow_dispatch` seulement, aucun autre workflow ne le lance) : cible `recette` ou `production`, **deux confirmations saisies** (le nom de la base : celui de Turso ou le premier mot complet de l'adresse — `nomDeBaseCorrespond` ; la phrase « tout le monde repart de zéro »), `sauvegarde_faite` (exigée pour la production : la sauvegarde est une étape de Nathan sur son ordinateur, commande exacte dans `docs/plateforme/lancement.md`), `essai_a_blanc` (compte, n'écrit rien). **Gardes** (étape « Gardes », testée en bash sans secrets, puis refaites par le script) : production **depuis `main` seulement**, après la validation de Nathan (environnement `production`) ; **la règle des noms de base** (« recette » dans le nom de la recette, jamais dans celui de la production, jamais la même base) ; **la production exige que le serveur déployé serve une date de lancement d'aujourd'hui ou de demain** (`refusDuLancement`, lu sur `https://playdujour.com/api/portail/jour`). Le jeton de la base est lu dans Secret Manager (production `cdj-turso-token`, recette `cdj-recette-turso-token`), masqué, jamais écrit ; `PERMISSION_DENIED` = la commande à lancer une fois est donnée dans le résumé. **Aucun artefact, aucun journal personnel.** Après : attente de 40 s (la génération est lue au plus toutes les 30 s), puis `smoke --lecture-seule --vide` **contre le service lui-même** (pas Hosting, dont le cache garde 30 à 60 s l'ancien classement) : génération annoncée, aucun classé aujourd'hui dans les deux jeux ni au classement du jour du portail, aucune mort. Un `recette:seed` (cron de 00 h 17 UTC, déploiement) qui passe entre la remise à zéro et la vérification peut la faire échouer : relancer.
- **`LANCEMENT_PREMIER_JOUR`** (recette) : posée par `deploy-api.yml` depuis la variable du dépôt `RECETTE_PREMIER_JOUR` (la production ne la reçoit jamais) ; `deploy-site.yml` pose `VITE_LANCEMENT_PREMIER_JOUR` pour la recette de même.

## Recette (lot R1)
- **Rien ne part en production sans passer par la recette.** Une PR qui touche le serveur (`SERVER_PATHS` : `apps/api`, `packages/sim`, `core`, `clock`, `jump-sim`, le module de profil, `apps/jump/public/levels`, le verrou npm…) déploie sa révision sur le serveur de recette (`recette.yml`) ; une fusion dans main met d'abord à jour la recette par défaut, puis seulement la production (`production.yml`).
- **Un lot qui touche le serveur donne dans son README** l'adresse de sa révision de recette (commentaire « Recette » de la PR : `https://b-<branche>-<empreinte>---<service de recette>`) et **le scénario à jouer sur l'aperçu** de sa PR (lot R4 : le canal Firebase `https://<site de recette>--pr-<n>-<empreinte>.web.app/`, lien dans le même commentaire, branché sur sa révision ; avant : `/b/<branche>/` de GitHub Pages), avec ce qu'on doit y voir.
- **La production part par le bouton « Mettre en production » seulement** (`production.yml`, lot R4) ; **lot R12 : son lancement par Nathan, sur `main`, vaut validation** (plus de « Review deployments » ; `verifier` refuse un autre acteur que le propriétaire du dépôt ; l'environnement `production` reste limité à `main`). Un agent ne lance ni ne relance jamais un workflow (403), ne crée ni ressource ni secret : il prépare le dépôt et le guide.
- **Les aperçus n'écrivent jamais dans le stockage ni dans la base de production.**
  - Base : un aperçu parle à la recette (lot R4 : `/api/` renvoyé vers `cdj-api-recette`, ou l'adresse directe de sa révision étiquetée), **jamais** à la production (`deploy-site.yml` refuse de publier sinon ; `scripts/domaine.mjs` refuse une origine d'aperçu ou de recette pour la production).
  - Stockage local : chaque jeu a **un seul point d'accès** (`apps/web/src/storage.ts`, `apps/jump/src/storage.ts` : `gameStorage()`). Lot R4 : production, recette et chaque aperçu sont des **origines distinctes** (le navigateur sépare leur stockage ; test `apps/portail/test/domaine.test.ts`) ; le préfixe de construction (`VITE_STORAGE` : `apercu:cdj:*` / `apercu:jump:*`) ne sert plus qu'au serveur de développement. **Aucun autre fichier ne touche `localStorage` ni `sessionStorage`** (tests `storage.test.ts` des deux jeux) ; un nouveau jeu fait de même.
- **Règle des noms de base** : la base de recette a « recette » dans son nom, la base de production jamais. `apps/api/src/config.ts` refuse de démarrer sinon (`ENVIRONMENT=recette` sur une base sans « recette », production sur une base « recette ») ; les workflows le vérifient aussi avant de construire.

La recette permet ce que la production refuse toujours : `TEST_CLOCK_OFFSET_MS` (tester minuit) et `SALON_MINUTES` (Salon court), par « Run workflow » de `recette.yml` sur une branche. Toutes les autres règles d'un serveur en ligne s'y appliquent (origines, sel, Turso).

Sans configuration : sauté avec le message habituel.

- **Sans configuration, tout est sauté avec un message** (« recette non configurée : voir docs/plateforme/recette.md ») et la CI reste verte ; un nouveau workflow qui dépend de la recette fait de même.

## Sécurité, mentions et effacement (lot R5)
README : `docs/plateforme/lots/lot-R5-securite-mentions.md` ; procédure d'effacement : `docs/plateforme/effacement.md` ; page publique : `apps/portail/mentions-legales/index.html` (`playdujour.com/mentions-legales/`).
- **Comment l'adresse du client est établie** (`node-server.ts`) : `clientKey` = l'entrée de `X-Forwarded-For` à la position `TRUST_PROXY` depuis la droite (**2** derrière Firebase : l'adresse du joueur telle que Firebase l'a vue) ; `peerKey` = la **dernière** entrée (l'**adresse de connexion**, écrite par le frontal de Google : l'appelant lui-même pour un appel direct à `run.app`, un relais de Firebase sinon ; **jamais écrite par le client**), **seulement si elle est publique** (`isPublicAddress` : mesuré sur la recette, un appel venu du réseau interne de Google y porte `0.0.0.0` — les appels de Firebase peuvent arriver ainsi, et tous les joueurs partageraient alors la même). Sans proxy de confiance (local, tests, e2e) : pas de `peerKey`. Mesure (recette, 20/10/2026) : par Firebase, une adresse inventée par le client n'est jamais lue ; en direct, avec `TRUST_PROXY=2`, l'avant-dernière entrée est celle que l'appelant écrit (faille du R4).
- **Ce qui est refusé** : (1) **toute limite par adresse compte aussi l'adresse de connexion**, à `limite × PEER_FACTOR` (10 ; variable `PEER_FACTOR` de 0 à 100, 0 = coupé, sans redéployer le code), en mémoire par instance (`Platform.hitAddress` pour les envois, `readHitAddress` pour les lectures, `peerHit` seul pour l'admin et les lectures du Salon) : un appel direct qui invente une adresse différente à chaque fois est refusé (429) au plus tard après 10 fois la limite (`GET /api/name` : 400 vérifications ; envois : 600 par fenêtre de 10 min et par instance). **Règle : une nouvelle limite par adresse passe par `hitAddress` / `readHitAddress`, jamais `hit(hashKey(…, info.clientKey))` seul.** (2) **Plafond global de rejeux** : `REPLAYS_PER_MINUTE` (600) par minute et **par instance** (`spendReplays`, appelé juste avant chaque rejeu, après les vérifications bon marché : débit, taille, jour, versions, identifiant du niveau, forme de la rediffusion) ; au-delà, **503 `busy`** avec `Retry-After`, sans rejeu ; un lot de vies compte une unité par 10 vies. Réglé par `server.ts` ; `createApi` sans `replaysPerMinute` n'a pas de plafond (outils de démonstration en mémoire, tests). (3) Pourquoi pas mieux : l'accès direct ne peut pas être fermé (Firebase Hosting appelle l'adresse `run.app` publique, qui doit accepter les appels non authentifiés ; l'entrée `internal` de Cloud Run n'accepte pas Firebase : README du lot R5, sources), et aucun en-tête posé par Firebase ne se distingue d'un en-tête inventé.
- **Risque restant** : un appel direct qui arrive par le **réseau interne de Google** (depuis une machine de Google Cloud) porte `0.0.0.0` : seule l'adresse qu'il écrit compte, comme avant le lot R5 (borné par le plafond global). Un abus réparti sur **beaucoup d'adresses réelles** (réseau de machines) n'est borné que par le plafond global : il peut alors occuper les 600 rejeux par minute d'une instance (503 pour les vrais joueurs pendant l'abus) — **la disponibilité**, pas le coût (`max-instances=2`) ni les données (le rejeu reste la seule source d'un temps ; limite par joueur en base). Par Firebase, l'adresse de connexion d'un relais est partagée par des joueurs : si un jour un relais porte plus de 10 fois la limite d'un joueur sur une instance, des 429 apparaîtraient (journal « débit : limite de l'adresse de connexion » : le surveiller ; mesurer avec `node scripts/sonde-proxy.mjs entetes`).
- **Route de sonde** `GET /api/sonde/entetes` (**recette seulement**, 404 ailleurs, n'écrit et ne journalise rien) : hôte, noms des en-têtes, nombre d'entrées de `X-Forwarded-For`, adresse de connexion ; `node scripts/sonde-proxy.mjs entetes <direct> <par Firebase>` compare les deux, `… faille <direct>` prouve que la faille est fermée.
- **Effacement d'un joueur** : `POST /api/admin/effacer` (jeton d'admin `ADMIN_TOKEN`, comme `/api/admin/*` ; corps `{ code: "CDJ2.…", confirmer?: true }` ; sans `confirmer`, essai à blanc ; code remplacé → 410, inconnu → 404) : en une transaction, le joueur (pseudo libéré), la chaîne de ses codes révoqués, et ce que chaque jeu garde de lui (crochet **`erase`** du registre : DailyTrack `results` — places finales des jours concernés remises à recalculer —, `salon_runs` + version de session, présence et délai du Salon ; DailyJump `jump_results`, `jump_lives` + version de la carte du jour) ; puis `onErased` (mémoires de l'instance). **Classements passés : la ligne est retirée** (pas anonymisée : un « Joueur effacé » garderait une rediffusion qui n'est plus à personne et un fantôme de premier ; ici le suivant devient premier). Le premier d'un jour fermé gardé en mémoire expire en `CLOSED_GHOST_TTL_MS` (10 min) sur les autres instances ; le cache de Firebase garde les lectures publiques d'un jour fermé jusqu'à 24 h (une publication du site le vide). Journal : « joueur effacé » avec les nombres seulement. Tests : `apps/api/test/effacement.test.ts` (SQLite et libSQL).
- **Règle : toute nouvelle donnée gardée met à jour la page de confidentialité** (`apps/portail/mentions-legales/index.html` : ce qui est gardé, pourquoi, combien de temps — une durée du code y porte `data-constante`) **et le crochet `erase` de son jeu**. Le test `apps/portail/test/mentions.test.ts` échoue si une table de la base n'y est pas décrite ou si une durée affichée n'est pas la constante du code.

## Codes d'erreur (lot I1 ; lot I6 : plus de `message`)
Documentation : `docs/plateforme/codes-erreur.md` (la forme, la règle, le tableau code | statut | sens | routes principales).
- **Lot I6 : les erreurs n'ont plus de `message` ; seul le code compte.** Le client traduit `erreur.<code>` (catalogue commun de `@cdj/ui`, français et anglais) ; le texte passé à `HttpError` explique le refus à qui lit le code, il ne sort jamais. (La réponse des vies de Jump n'a plus de `message` non plus : `overCap` et `cap` disent le plafond.)
- **Forme de toute réponse d'erreur** : `{ error: "<code>", …détails }` (`reply` d'`api.ts`) ; erreur inattendue : `500 { error: "internal" }` (`ERREUR_INTERNE`, la même dans `api.ts` et `node-server.ts`) ; `/api/health` en 503 garde `ok` et `db` et ajoute `error: "db_unavailable"`.
- **Liste unique** : `src/codesErreur.ts` (`CODES_ERREUR` : code → statut HTTP + sens ; `CodeErreur`, `estCodeErreur`, `corpsErreur`). **Un code = un statut, imposé par le typage** : `HttpError<C>` (`errors.ts`) déduit `C` du code et n'accepte que le statut de la liste (un autre statut fait échouer `tsc`). Jamais de corps d'erreur écrit à la main.
- **Toute nouvelle erreur** : un code de la liste (ou un code ajouté à la liste avec son statut et son sens), une ligne dans `docs/plateforme/codes-erreur.md`, et sa traduction `erreur.<code>` dans le catalogue commun de `packages/ui` (**français et anglais**), dans le même lot.
- Tests : `apps/api/test/codesErreur.test.ts` (parcours de toutes les routes × méthodes × corps × en-têtes, analyse des sources, accord avec la documentation) et `verifierErreur` (`apps/api/test/helpers.ts`), appliqué par `makeApi().call` à chaque réponse d'erreur de tous les tests de l'API — **lot I6 : il refuse une réponse d'erreur qui porte un `message`** ; SQLite **et** libSQL.

### Portail (lot I3, refait au lot A1) — la journée partagée, classement au chrono
README : `docs/plateforme/lots/lot-I3-journee-partagee.md`, puis `docs/plateforme/lots/lot-A1-diamant-et-classement-chrono.md`. Code : `src/portail.ts` (routes, cache), `src/classementDuJour.ts` (calcul pur : cumul, ordre, place), `src/classementDemo.ts` (joueurs de la recette) ; tests `test/classementDuJour.test.ts`, `test/classement.test.ts`, `test/classementDemo.test.ts`, `test/smokeLecture.test.ts` (SQLite **et** libSQL).
- **Médaille Diamant (lot A1) : « médaille diamant = clé `auteur` dans les données »** (`author` dans l'API, `auteur` dans la base, les rediffusions, les fichiers de niveaux, l'administration en JSON). Seul son **nom affiché** change (« Diamant » / “Diamond”) : renommer l'identifiant imposerait une migration pour rien. « Le temps de l'auteur » (générateur, validation, outils) reste la notion telle quelle.
- **Numéro de journée commun** : `PREMIER_JOUR_DU_JOUR` (`@cdj/core/lancement`, réexportée par `portail.ts`) = **la date de `config/lancement.json`** (lot R8 : le lundi 26/10/2026 ; avant, 23/10/2026), jour de Paris, une constante de la **plateforme** (pas d'un jeu). `GET /api/portail/jour` rend `journee` (le numéro, ou `null` avant ce jour : rien n'est affiché), `lancement` (la date) et `generation` (lot R8). Lue aussi par le portail (`apps/portail/src/jours.ts`, test d'accord) : voir « Lancement public et remise à zéro (lot R8) ».
- **Plus de barème de points (lot A1)** : `BAREME_POINTS`, `pointsDe` et `sommeDesRangs` sont retirés — plus rien ne les lisait (le profil commun, la série et la « journée parfaite » ne comptaient que des jours finis et des médailles, jamais des points ; seuls la tuile et `/classement/` du portail, `smoke` et `measure:portail` les utilisaient). La médaille n'est plus qu'une **pastille** à côté du temps.
- **Classement du jour au chrono** (`classerLaJournee`, pur). Chaque jeu déclare au crochet `portail` ses **classés du jour** (`classes(day)` : dans l'ordre de son classement prouvé, avec `tempsMs` — le temps **rejoué par le serveur**, en ms (Jump arrondit ses pas) —, la médaille lue sur les seuils du jour et l'horodatage de l'essai) ; la route agrège **sans connaître les jeux** (un jeu n° 3 entre tout seul : sa vue, son temps au cumul, testé). Jump classe bien **au temps** (en pas, puis premier envoyé, puis identifiant : `RANK_SQL`) comme Track (ms, puis premier envoyé). **Trois vues** : (1) **un jeu** (`vue` = le dossier du jeu sur le site : `track`, `jump`) : le meilleur temps prouvé du jour de chaque joueur, croissant, **dans l'ordre même du classement du jeu** ; (2) **`cumul`** (défaut) : **d'abord** les joueurs qui ont fini **tous les jeux du jour**, par la **somme** de leurs meilleurs temps (croissante), **puis** (sous la séparation « Un jeu sur deux » côté portail) ceux qui n'en ont fini qu'une partie, par leur **meilleur rang** dans un jeu (le 1er de Track, le 1er de Jump, puis les 2es… ; à rang égal le jeu du registre d'abord) ; à égalité de cumul, **le premier à avoir atteint ce temps** (l'horodatage le plus tardif de ses essais classés), enfin l'identifiant (ordre stable). Un jour où un seul jeu existe : tous sont « complets ». Seul le classement prouvé compte : **aucun temps annoncé n'entre**.
- **Calculé au plus une fois par fenêtre et par instance** (`CLASSEMENT_FENETRE_MS` = 45 s pour le jour ouvert, aujourd'hui et hier pendant la grâce de 10 min ; 10 min pour un jour fermé ; un seul calcul même si deux requêtes arrivent ensemble ; 16 jours gardés au plus ; vidé par l'effacement d'un joueur) : une lecture de `results` et de `jump_results` — **1,9 ligne lue par joueur du jour**, 0 écrite (les mêmes requêtes qu'avant le lot A1 : le temps était déjà lu). **Les trois vues partagent ce calcul** ; seuls les **pseudos du haut de chaque vue** sont lus au premier besoin de la vue (une requête de ≤ 50 lignes par vue et par fenêtre) et gardés avec lui. Chiffres : `docs/plateforme/couts.md` § 6, `measure:portail`, `CLASSEMENT_JOUR` (`scripts/platformBudget.ts`).
- **`GET /api/portail/jour` avec joueur** rend en plus, dans `joueur`, **`cumulMs`** (la somme de ses temps, **`null` tant qu'il n'a pas fini tous les jeux du jour**), `rangDuJour` et `classesDuJour` (`null` tant qu'aucun jeu n'est fini aujourd'hui) — **à la place de `points`**. Sa place est exacte (ses états à l'instant) ; **celle d'un joueur déjà classé vient du classement gardé** (`etat(id, day, connu)` : le coût d'une visite ne croît plus avec le nombre de joueurs : 9 lignes lues à 100, 1 000 comme à 10 000 ; un retard de 45 s au plus) ; un joueur qui vient de finir, ou dont le cumul a changé, est **placé** (`placer`) après tous ceux qui valent son temps ou le devancent.
- **`GET /api/portail/classement?date=AAAA-MM-JJ&vue=cumul|track|jump`** (défaut : aujourd'hui, `cumul`) : `{ date, journee, ouvert, vue, jeux[{ jeu, site, nom }], classes, top[≤ 50 : { rang, pseudo, tempsMs, complet, resultats{ <jeu>: { rang, tempsMs, medaille } | null } }] }` — `tempsMs` : le temps de la vue (le cumul, ou le temps du jeu ; **`null` au cumul d'un joueur qui n'a pas tout fini**), `complet` : faux = sous « Un jeu sur deux » (toujours vrai dans la vue d'un jeu), `classes` : le nombre de lignes **de la vue** ; avec `X-Player-Id`, en plus `moi` (`{ …, classes }` ou `null` : rien fini dans cette vue ce jour-là) et `top[i].moi: true` si tu y es. **Jamais un identifiant dans la réponse.** `vue` inconnue, ou un jeu qui n'existe pas ce jour-là : 400 `invalid_view` (le portail retombe alors sur le cumul). Jours passés lisibles (archives, figés : leur classement **se relit avec la règle du jour**, rien n'est réécrit en base), jour futur ou avant le premier jeu : 404 `unknown_day`, date illisible : 400 `invalid_date`. **Cache** : sans identifiant, `public, max-age=min(30 s, secondes jusqu'à minuit)` (jour fermé : 24 h) ; avec identifiant, `private, no-cache` ; les deux portent `Vary: X-Player-Id` ; chaque vue a son adresse (donc son cache) ; joueur inconnu : 404 `unknown_player` (le corps porte quand même le classement public), code révoqué : 410. Mêmes limites de lecture que `jour`.
- **Vérification `Vary` (par Firebase Hosting)** : le cache de Hosting (Fastly) **honore** `Vary: X-Player-Id` — mesuré sur la recette le 20/10/2026 : une lecture de `/api/portail/jour` avec `X-Player-Id` faite juste après deux lectures sans (servies du cache : `x-cache: HIT`) reçoit l'état du joueur (`private, no-cache`, `MISS`), et la lecture sans identifiant d'après est de nouveau la réponse publique, sans `joueur`. **Règle qui en découle : une seule adresse, deux réponses** (publique en cache court, personnelle `private`), pas de seconde adresse ; si un jour Hosting ignorait `Vary`, la réponse publique serait servie sans l'état du joueur (jamais l'état d'un autre) et la vérification ci-dessous le dirait. `smoke --lecture-seule --par-hosting [--joueur-demo]` (`scripts/smokeRead.ts`, `varyParHosting`) la refait : deux lectures sans identifiant, une avec (l'état du joueur de démonstration, ou un identifiant inventé : 404, jamais la réponse publique gardée), une sans (jamais l'état d'un joueur), pour `/jour` et `/classement` ; **le seul identifiant permis en lecture seule est celui qu'on nomme, sur des `GET` du portail seulement** (testé). Lancé par le job `hosting` de `recette.yml` après chaque fusion (adresse de Hosting, `--joueur-demo`).
- **Joueurs de démonstration du classement** (recette seulement) : `seedClassementDemo` (`recette:seed`) crée **20 joueurs « Démo … »** (résultats variés dans les deux jeux), par le vrai `createApi`, **effacés puis recréés** à chaque passage ; `--demo-seulement --classement` (e2e). **Lot A1 : les trois cas** — les deux jeux finis, **un seul** (sous « Un jeu sur deux »), et **des égalités** (le joueur d'indice 1 de chaque dizaine rejoue la course et l'essai du joueur d'indice 0 : mêmes temps dans chaque jeu et au cumul, le premier arrivé passe devant ; `allowCopies` est vrai pour eux seuls). Aucun module du serveur ne les importe (testé).

## Sécurité du serveur (lot R7)
Rapport : `docs/plateforme/audit-securite-2026-10.md`. Règles qui en découlent (tests : `apps/api/test/auditR7.test.ts`) :
- **Le plafond de rejeux est proportionnel à la durée** : `platform.spendReplays(replayUnits(replay.runs))` (`replayCost.ts` : une unité par `REPLAY_TICKS_PER_UNIT` = 5 000 pas). Un nouveau rejeu côté serveur appelle `spendReplays` avec ses unités **juste avant** de rejouer, après les vérifications bon marché. Une rediffusion qui ne finit jamais coûte 200 à 350 ms (mesuré) : elle ne vaut jamais « 1 ».
- **Une lecture publique qui parcourt les temps du jour a sa limite** (`readHitAddress`) : classement et fantômes de Track `BOARD_READS_PER_CLIENT` = 300 par fenêtre ; ne jamais ajouter de route de lecture sans limite ni cache.
- **Administration** : jeton Bearer en en-tête, jamais dans l'adresse (`?token=` ignoré), comparaison des empreintes à temps constant, 10 échecs par fenêtre → 429 y compris pour le bon jeton ; **chaque action est journalisée** (`admin : circuit remplacé`, `jeton refusé`…) **sans** jeton, adresse ni pseudo ; au démarrage, `adminTokenWarning` signale un jeton de moins de 32 caractères (≥ 32 : `openssl rand -hex 24`). Une nouvelle route `/api/admin/*` passe par `requireAdmin` et se journalise.
- **Compteurs de débit** : l'adresse de connexion (mémoire) est comptée **avant** d'écrire un compteur en base (`hitAddress`) ; le ménage de `rate` se fait une fois par fenêtre et par instance.
- **En-têtes de réponse** : `SECURITY_HEADERS` (`api.ts`) sur toutes les réponses (JSON seulement).
- **Validation** : toute entrée (corps, en-tête, paramètre d'adresse) est validée avant la base ; aucune requête SQL construite par concaténation d'une donnée (des `?` seulement ; `${}` réservé aux listes de `?` et aux constantes).
- Journaux : ni identifiant, ni pseudo, ni adresse, ni jeton, ni rediffusion.

## La preuve de l'auteur et les copies (lot R9)
README : `docs/plateforme/lots/lot-R9-avant-le-partage.md`. Audit : S-08, S-16 (`docs/plateforme/audit-securite-2026-10.md`).
- **La preuve de l'auteur d'un niveau ne sort jamais du serveur.** Celle de Jump (`preuve` des fichiers figés de `apps/jump/public/levels/`, rediffusion de l'auteur) reste dans le dépôt et **dans l'image du serveur** (qui la rejoue : `thawLevel`, strict) ; **aucun fichier publié** ni aucune réponse de l'API ne la porte (`/api/jump/day/<date>` ne rend ni grille ni preuve ; la construction de production de Jump retire le champ, `scripts/site.mjs` le revérifie : `apps/jump/CLAUDE.md`, « Lot R9 »). Celle de Track (la rediffusion du pilote automatique) n'a jamais été servie : le serveur n'en garde que le temps (`circuits.author_ms`) et, depuis ce lot, l'**empreinte** de ses entrées. Un nouveau fichier ou une nouvelle route qui montrerait une rediffusion d'auteur est refusé.
- **Refus des copies** (`copies.ts`, `cdj.ts` `submit`, `jump.ts` `submit`) : un envoi au **classement du jour** dont les **entrées** sont celles de la rediffusion de l'auteur du niveau, ou d'une rediffusion **déjà classée d'un autre joueur ce jour-là**, est refusé : **`409 replay_copy`** (liste unique `codesErreur.ts`, `erreur.replay_copy` au catalogue commun fr + en, `docs/plateforme/codes-erreur.md`). **L'empreinte** = SHA-256 des entrées **effectivement jouées** (`trackInputs` : jusqu'à l'arrivée, les pas ajoutés après la ligne sont ignorés comme par le rejeu ; `jumpInputs` ; séries voisines de même commande recollées : le codage d'octets n'est pas unique). Gardée **avec chaque résultat** (`results.inputs_hash`, `jump_results.inputs_hash`, index `(day, inputs_hash)`) et pour l'auteur du jour (`circuits.author_hash`, `jump_levels.author_hash`, calculée avec le niveau). **Migration en avant** : `ALTER TABLE … ADD COLUMN` (+ index **après** les colonnes, dans `MIGRATIONS`) ; une ligne d'avant a `NULL` et ne bloque personne ; un circuit ou un niveau sans empreinte d'auteur est **recalculé** tant que son jour est ouvert (un jour fermé n'accepte plus rien).
- **Ce qui n'est pas concerné** : le même joueur qui renvoie sa propre course (autre `player_id` seulement) ; le Salon (classement de session, rien à copier du jour) ; **l'ordre d'arrivée** ne change rien (la première course classée garde sa place, la copie est refusée avant toute écriture — pas même le joueur, comme un essai invalide). **Limite assumée** : une rediffusion **modifiée** (une commande changée à un endroit sans effet) a une autre empreinte ; la plausibilité des entrées est le lot L-ROB. Deux copies simultanées (même milliseconde) peuvent passer toutes deux (lecture puis écriture, pas de contrainte unique : une contrainte aurait contredit la clé `(day, player_id)` d'un meilleur temps remplacé).
- **`allowCopies`** (option de `createApi`, `api.ts`) : **faux par défaut** — c'est le réglage du serveur de production, que `server.ts` ne règle jamais et que `readConfig` ne connaît pas (test `copies.test.ts`) ; **vrai** pour les outils qui fabriquent des données fictives (`history:seed`, `jump:seed`, `recette:seed`, démos du portail et du classement : des « Démo » dont l'un a la preuve de l'auteur), les scripts de mesure et le `makeApi` des tests (`helpers.ts` : beaucoup de tests rejouent la même course pour plusieurs joueurs). **Un test de classement qui a besoin de plusieurs joueurs de même temps** peut s'en passer ; **un test de la règle elle-même** passe `allowCopies: false` (`copies.test.ts`, SQLite et libSQL). **Un spec e2e ou un outil qui envoie une course à un vrai serveur ne peut plus rejouer la preuve ni envoyer deux fois la même** : il prend une course fictive qui arrive d'une graine tirée au hasard (`honestRun`, `apps/jump/e2e/jours.ts` ; `smoke.ts` : adhérence et graine tirées au hasard à chaque passage, puisque la recette garde les courses des passages d'avant).
- **Coût** : une instruction indexée de plus par envoi (`results_by_inputs` / `jump_results_by_inputs`, 0 ou 1 ligne lue, rien d'écrit de plus que la colonne) — non mesurée sur Turso (pas de `sqld` ici), le modèle de `scripts/platformBudget.ts` ne change pas (ses « requêtes » sont des requêtes HTTP).

# DailyJump — `apps/jump` : consignes du jeu (rendu, interface, sensations, tactile)

Chargé quand on lit un fichier de `apps/jump`. Le jeu affiche ce que calcule `packages/jump-sim` : rendu, son, effets = lecture seule de la simulation. **Partir de la synthèse `docs/jump/synthese.md`** (chaque point renvoie au README du lot) ; n'ouvrir un README de `docs/jump/lots/` que pour un détail. Vision : `docs/jump/seed-dailyjump.md` (**ne pas modifier**). Réponses et docs en français. Chaque lot de DailyJump ajoute **sa section** dans le `CLAUDE.md` de la zone qu'il touche, jamais dans le `CLAUDE.md` racine. Règles de la simulation, des morceaux et du générateur : `packages/jump-sim/CLAUDE.md`.

> **Renvois « voir <rubrique> »** : une rubrique citée mais absente de ce fichier se trouve dans un autre `CLAUDE.md` du dépôt ; l'index des rubriques est dans le `CLAUDE.md` racine. Pour l'état d'ensemble, partir de la synthèse ; n'ouvrir un README de lot que pour un détail.

## Emplacements
- `docs/jump/seed-dailyjump.md` — vision, piliers, plan en lots (le prompt de lot 0 le nomme `seed.md` : le fichier déposé s'appelle `seed-dailyjump.md`).
- `docs/jump/lots/` — un README d'une page par lot (`lot-0-socle.md`…).
- `packages/jump-sim` (`@cdj/jump-sim`) — simulation pure du saut.
- `apps/jump` (`@cdj/jump`) — le jeu (Vite + Three.js, caméra orthographique) ; affiche ce que calcule `jump-sim`.
- `packages/core` (`@cdj/core`) — socle partagé avec DailyTrack : PRNG (`Rng`, `mixSeed`), calendrier (`daysFromCivil`, `civilFromDays`, `formatDay`, `parseDay`), codage d'octets (`toBase64Url`, `fromBase64Url`, `pushVarint`, `readVarint`), et le test de pureté générique (`@cdj/core/testing`). Le jour de Paris (changement de jour) est dans `packages/clock` (`parisDay`), qui lit l'heure et n'est donc pas pur : jamais importé par une simulation.

## Conventions de `apps/jump`
- **Interface et socle commun** : **fait au lot I5** — toute l'interface passe par le socle `@cdj/ui` et les catalogues `fr` + `en` (aucune chaîne ni couleur en dur) : voir « Interface Du Jour (lot I5) ». Rendu, son, effets : lecture seule de la simulation.
- **`?debug`** expose `window.__jump` (même esprit que `__cdj` de DailyTrack) : `phase` (`loading` → `ready`, ou `no-webgl`), `day`, `simVersion`, `palette`, `probe()` (relit les pixels). Sans `?debug`, rien n'est exposé.
- **Stockage local préfixé `jump:`** (`storageKey()`, `storage.ts`) ; DailyTrack garde `cdj:`. Toujours sous `try/catch`.
- **Publication sous `/jump/`** du même site GitHub Pages : `pages.yml` construit `apps/web` à la racine et `apps/jump` dans `jump/` (aperçu de branche : `…/b/<branche>/jump/`). Chemins **relatifs** (`base: "./"`) pour que les aperçus de branche marchent.
- **Tout nouveau paramètre d'adresse rejoint la page d'admin** (à créer côté `apps/jump` avec le premier paramètre qui le demande). Le lot 0 n'en a pas d'autre que `?debug`.
- Rendu, son, effets : lecture seule de la simulation ; jamais l'inverse. Texte par les catalogues, en français et en anglais (lot I5).
- **Tests e2e et CI de PR courte (lot R10 de la plateforme)** : une PR ne lance que les specs liés à ses fichiers (`e2e/zones.json` de la racine : clés `jump/…`), sur Chromium ; tout tourne sur les trois navigateurs sur `main`, la nuit et dans le lot de mise en production. **Tout nouveau spec déclare ses zones dans `e2e/zones.json`** (`apps/web/test/ciZones.test.ts` l'exige) **et sa durée dans `e2e/durees.json`** ; **préférer un test unitaire** quand le navigateur n'est pas nécessaire ; **jamais d'attente en temps réel longue**. Avant de pousser : `npm run verifier`. Règles de CI, quarantaine et règle d'arrêt : `CLAUDE.md` racine, « Tests et CI ».

## Commandes
- `npm run dev:jump` — serveur de développement de `apps/jump`.
- `npm run build` — construit DailyTrack **et** DailyJump (`npm run build -w @cdj/jump` pour DailyJump seul).
- `npx vitest run packages/core packages/jump-sim apps/jump` — tests de DailyJump et du socle ; `npm test` lance tout (deux projets, `sqlite` puis `libsql`).
- `npm run typecheck` — `tsc -b` sur tous les espaces de travail.
- `npm run e2e:jump` — construit puis lance les tests e2e Playwright de DailyJump (`E2E_ALL_BROWSERS=1` pour Firefox et WebKit, `CHROMIUM_PATH` pour un Chromium déjà installé ; arguments Playwright après `--` : `npm run e2e:jump -- smoke --project=chromium`).
- Alias racine (lot 3c, sans autre changement) : `npm run solve:modules` (`-w @cdj/jump-sim`), `npm run measure:jump` (`-w @cdj/jump-sim`), `npm run freeze:days -- <date | demain>` (`-w @cdj/jump`). Arguments après `--`.
- **CI : les e2e de DailyJump suivent exactement les règles de CI de DailyTrack** (lot 3c, retouche 29b de DailyTrack) : leurs specs sont des parts de la même matrice `e2e-parts` (`suite: jump`, projets Playwright `jump-chromium|firefox|webkit` en CI ; Chromium en parts composées par durée, `apps/jump/e2e/durees.json`, un test à la fois ; Firefox et WebKit en `--shard` ; **lot R10 : une PR n'a que ses specs liés, sur Chromium, dans la matrice `e2e-pr`**), leurs rapports « blob » entrent dans la fusion et le verdict unique `e2e`, **une relance** en CI (`retries: 1`) et un test qui réussit à la relance est **« instable »** : nommé dans le résumé du run, annoté, jamais caché (au run de nuit il fait échouer le job). Un rouge désigne un vrai problème, nommé. **Un nouveau spec e2e s'ajoute à `apps/jump/e2e/durees.json`** (le test `apps/jump/test/ciE2e.test.ts` l'exige ; les durées Chromium par fichier, préfixées « jump/ », sont dans le résumé du run `e2e`). Les outils `MESURE` et `CAPTURES` se sautent d'eux-mêmes avec leur motif (« outil de mesure : MESURE=1 ») : ni l'un ni l'autre n'est défini en CI. Le site publié contient `apps/jump/public/levels/` (étape « Vérifier les niveaux figés publiés » de `pages.yml`).

## Lot 1 — personnage
- **Une session aux réglages modifiés (`tuned`) n'est jamais enregistrée** (`JumpSession.tuned`, vrai dès qu'un pas a été joué avec d'autres réglages que les défauts ; « recommencer » aux défauts l'efface). Panneau `?debug&tune` (`tune.ts`) : un curseur par réglage, en unités humaines avec la valeur entière, « Copier les valeurs » (JSON), « Réinitialiser », mémorisé dans `jump:tune` (seulement en mode `tune`), badge « réglages modifiés ».
- **Tout nouveau paramètre d'adresse rejoint `apps/jump/src/urlOptions.ts`** (`URL_OPTIONS` : nom, description, valeurs ; `readUrlOptions` est le seul lecteur de l'adresse, un test le vérifie). La page d'admin de DailyJump lira cette liste.
- **Jeu** (`apps/jump`) : boucle à pas fixe (`loop.ts`, `FixedStepper`, au plus 30 pas par image), rendu interpolé entre `session.prev` et `session.state` ; entrées (`input.ts`) : clavier par `KeyboardEvent.code` (flèches, `KeyA`/`KeyD`, saut `Space`/`ArrowUp`/`KeyW`, R), manette (stick avec zone morte, croix, A/B saut, Start/Select recommencer), **aucun appui de saut perdu** (`JumpLatch`) ; caméra (`camera.ts`, affichage seul : avance, lissage, zone morte verticale, bornée au niveau) ; allure (`look.ts` : écrasement, étirement, regard — affichage seul).
- **`window.__jump`** (avec `?debug`) : `phase` (`ready` au chargement et après « recommencer », `playing` dès la première commande non nulle), `player` (tuiles, tuiles/s, `mode`, compteurs, `raw`), `params` (l'objet en vigueur), `tuned`, `ticks`, `manual(on)`, `advance(n)` (joue `n` pas **tout de suite, sans rendu**, renvoie `player`), `input(bits | null)`, `restart()`, `probe()`.
- **Tests de jeu en pas à pas** (`manual(true)` + `input` / `advance`), **jamais sur une durée** (`e2e/smoke.spec.ts`).
- **Zones partagées, en plus de la liste du `CLAUDE.md`** : `packages/clock` et `apps/api/Dockerfile`.

## Lot 1b — mobile
> **Lot I5 : l'interface a changé** — voir « Interface Du Jour (lot I5) » plus bas, qui remplace la bande haute de boutons (recommencer, ⚙, plein écran : dans la pause) et la place des boutons dessinés (aux bords) ; **les zones du lot 1b ne changent pas**.
- **Toute nouvelle commande a son équivalent tactile** (et reste dans `Controls` : le tactile ne produit que les mêmes 3 bits, rien dans la simulation). Un bouton de plus = une zone ou un bouton dessiné, une entrée dans `touch.ts`, un test.
- **Les zones restent sans trou, la logique reste pure et testée** : `apps/jump/src/touch.ts` (zones `ZONE_SPANS`, `zoneAt`, `TouchPad`, `buttonRects`, aucun DOM) ; `touchUi.ts` ne fait que brancher le DOM (pointer events, boutons dessinés). Le toucher se décide par la **zone**, jamais par le bouton dessiné ; la bande haute (`BAND_PX`, recommencer, ⚙, plein écran) est exclue des zones de jeu. `?touch=1` force le tactile (la souris simule le doigt), `?touch=0` le coupe, `?zones=1` dessine zones et doigts.
- **Cibles ≥ 44 px, vérifiées en portrait et en paysage** (`e2e/mobile.spec.ts` : téléphone émulé, boutons, panneau de réglages et curseurs compris) ; un nouvel élément cliquable passe par ce test. Cadrage : `viewHeightTiles` (`camera.ts`), 18 tuiles de haut au poste, 13 sur téléphone en paysage, jamais moins de 10 tuiles de large.
- **Page** : `touch-action: none`, `overscroll-behavior: none`, corps fixe `100dvh`, `viewport-fit=cover`, marges `safe-area-inset-*` ; rien ne défile, ne se sélectionne, ne se zoome.
- **Tests de navigateur tactiles** : doigts posés par `Input.dispatchTouchEvent` (Chromium) ou par pointer events sur la couche `#touch` (Firefox, WebKit), toujours en pas à pas.

## Lot 2 — dangers et mort
> **Lot I5 : l'interface a changé** — voir « Interface Du Jour (lot I5) » plus bas, qui remplace le HUD décrit ici (chrono, meilleur, morts : la bande compacte et l'autocollant des morts).
- **Recommencer n'est pas une mort** : c'est un événement de la session (`JumpSession.restart`), qui repart de `initialAttempt`.
- **Jeu** : `?scenario=essai` (page par défaut) · `dangers` · `bac-a-sable` ; `?debug&hitbox` (boîtes justes et sections) ; `?fx=off` (ni éclats ni tremblement : `fx.ts`, pool recyclé, jamais d'objet créé en jeu). `__jump.attempt` (statut, chrono, morts, meilleur, dernière mort, scies, friables, sections), `__jump.fx`, `__jump.banner`. HUD (`hud.ts`) : chrono, meilleur temps, morts, sous la bande haute sur téléphone ; bandeau d'arrivée au-dessus de la couche tactile, bouton ≥ 44 px. Meilleur temps et morts : **session seulement** (lot 3 pour l'enregistrement) ; un essai aux réglages modifiés ne devient jamais le meilleur.

## Lot 3 — rediffusion
- **Rien n'est enregistré en `tuned`** : ni meilleur essai, ni vies, ni taches (le badge le dit : « réglages modifiés : rien n'est enregistré ») ; ni en lecture (`?watch=best`) ni pendant le carnage.
- **Le stockage est protégé et le jeu marche sans** : tout accès passe par `try/catch` (`memory.ts`, interface `KeyValue` pour les tests) ; clés `jump:jour|meilleur|vies|morts:<niveau>`, `jump:fantome` ; purge au changement de jour, de niveau (empreinte `levelHash`) ou de version.
- **Le carnage et les taches sont du rendu seul, plafonnés et instanciés** : chaque vie a sa propre simulation (`carnage.ts`, logique pure testée), le dessin ne fait que lire (`actors.ts` : un `InstancedMesh` pour la foule, un pour les taches, pool d'éclats recyclé) ; au plus 300 vies et 300 taches gardées par niveau et par jour (au-delà, les plus anciennes s'estompent) ; les taches sont découpées au pochoir par les blocs pleins (jamais dans le vide). Les dangers montrés pendant le carnage sont ceux du monde du héros (léger décalage de phase des scies pour les autres vies, accepté).
- **`?fx=off` ne coupe pas les taches** (elles portent une information) : seulement les éclats et le tremblement.
- Outils : `?carnage=demo`, `?watch=best`, `?ghost=off` (dans `urlOptions.ts`) ; `?debug` → `__jump.replays` (lister, exporter, importer), `__jump.carnage` (`start`, `demo`, `skip`, `state`), `__jump.storage.clear()`, `__jump.ghost`, `__jump.stains`, `__jump.frameTimes`. Touche **G** et bouton 👻 : fantôme.

## Lot 4 — morceaux
- **Jeu** : `?modules` (galerie), `?module=<id>&variante=<n>&entree=arret|elan` (en élan, couloir de lancement de `LAUNCH_TILES` = 5 tuiles), `&solution` (la solution stockée, rejouée) ; bandeau d'arrivée avec le temps de la solution et « Morceau suivant ». Mémoire, fantôme, carnage et taches par morceau (clés `jump:*:module:<id>:<n>:<entrée>`). Logique pure : `apps/jump/src/modulesInfo.ts` ; galerie : `gallery.ts` (chargée par `boot.ts`, sans Three.js).

## Lot 5 — niveau du jour
- **Jeu** : la page par défaut (`/jump/`, sans `scenario` ni `module`) est le niveau du jour. `?seed=AAAA-MM-JJ` : une date ; **`isPreview(location)`** (`apps/jump/src/dailyInfo.ts`, pur) = aperçu de branche (`/b/<branche>/`) ou serveur local ; **sur le site publié, une date future est refusée** (niveau du jour, « Ce niveau n'est pas encore sorti »), `?debug` et `&solution` ne lèvent jamais ce refus ; une date passée = archive. C'est **une porte, pas une protection** : le générateur est dans le code publié ; la garantie viendra du serveur (phase 2). HUD : `#dayline` (« DailyJump #N », archive / à venir / aperçu, médaille visée) ; bandeau : médaille obtenue et temps de l'auteur ; palette = `paletteForDay(date du niveau)`. **Passage de minuit** : la partie continue, « Nouveau niveau disponible », le prochain « recommencer » recharge la page sur le nouveau jour. `&solution` : la rediffusion de l'auteur. `?debug` : limites des morceaux (identifiant, variante, exigence) et `__jump.daily`.

## Lot 8 — sensations
> **Lot I5 : l'interface a changé** — voir « Interface Du Jour (lot I5) » plus bas, qui remplace le menu ⏸ décrit ici : la pause porte les actions, les réglages sont un écran à part (`#settings`) ; « ⏸ Menu » est le bouton `#pausebtn` en haut à gauche partout.
- **Les effets s'abonnent aux événements, jamais à la sim directement** : `eventsBetween(avant, après, niveau, réglages)` (`apps/jump/src/events.ts`, pur, testé) compare deux états successifs d'un essai et rend `saut`, `sautMural`, `atterrissage` (intensité), `pas` (cadence), `glisseDebut` / `glisseFin`, `mort` (cause), `reapparition`, `pointDePassage`, `arrivee`, `ressort`, `friableCraque`, `friableTombe` ; le jeu y ajoute `medaille`. Le son (`audio.ts`), les particules, la secousse et les vibrations (`feel.ts`) ne lisent que cette liste (`dispatch`, main.ts). Le carnage n'en garde, pour les autres vies, que `mort` et `arrivee`, au débit plafonné (`CarnageFilter`) ; ses taches, elles, ne sont jamais filtrées. `?debug` : `__jump.events` (200 derniers), `__jump.audio`, `__jump.effects`, `__jump.settings`, `__jump.menu`.
- **Tout effet est plafonné et passe par un pool** (`Particles` 220, éclats de la mort 64, carnage 384, traînée 5, 3 voix de scie, polyphonie `MAX_VOICES`, sons de mort du carnage `CARNAGE_SOUNDS_PER_100MS`) ; **`?fx=off` le coupe, sauf les taches** (`feelLevels` : particules, secousses, traînée ; l'écrasement revient à l'amplitude du lot 1).
- **Tout nouvel élément de jeu vient avec son événement, son son et ses particules** (une ligne de `eventsBetween`, une recette de `soundFor`, un cas de `feelEvent`, et leurs tests dans `apps/jump/test/sensations.test.ts`).
- **L'audio est procédural, sans fichier** (oscillateurs et bruit filtré) ; contexte créé ou réveillé au premier geste (`pointerdown`, `pointerup`, `touchend`, `keydown`…, exigence d'iOS), suspendu quand l'onglet est caché ; trois bus (effets, ambiance — vide jusqu'au lot 9 —, général). La logique (correspondance, atténuation des scies, plafonds, débits, gains) est dans `audioLogic.ts`, pure et testée.
- **Les réglages du joueur ne rendent jamais une partie `tuned`** : `jump:settings` (`settings.ts`, lectures et écritures protégées, `SETTINGS_VERSION`) ; seuls les réglages du personnage (`?debug&tune`) le font. Menu ⏸ : Échap ou P, **Start** à la manette (**Select** reste « recommencer »), ⏸ dans la bande haute au téléphone, « ⏸ Menu » en bas à gauche sur ordinateur ; ouvert, **aucun pas de simulation** (chrono figé) et le clavier ne commande plus le personnage. Un nouveau réglage = un champ de `PlayerSettings`, son défaut, un contrôle du menu (≥ 44 px), un test.
- **Le mouvement réduit est respecté** : actif par défaut si le système le demande (`prefers-reduced-motion`), il coupe particules, secousses et traînée, garde un écrasement discret et pose le fanion sans animation.

## Lot 7b — chargement rapide, respirations, tension
- **La génération du niveau du jour se fait dans un worker de module** (`apps/jump/src/dailyWorker.ts`, Vite) et **`dailyLoader.ts` est le seul point d'appel** (`loadDaily`, attendu en tête de `main.ts`). Ordre : cache, worker, puis repli sur le fil principal (worker absent, script non chargé, erreur, 20 s sans réponse). Pendant la génération la page affiche **« Préparation du niveau… »** (`#prep`) ; un cache valide n'affiche rien. `__jump.daily.load` (`?debug`) dit d'où vient le niveau (`cache`, `worker`, `principal`), s'il a été généré pendant ce chargement, pourquoi le cache a été refusé, la durée du chargement et le temps de fil principal.
- **Le niveau voyage sous forme de charge JSON** (`dailyWork.ts` : `toPayload` / `fromPayload`, sans `Level` ni médailles, qui se recalculent) : le même chemin sert le worker et le cache, donc le résultat du worker est celui de `dailyLevel` à l'empreinte près (testé sur 4 dates). **Format de la charge** : `PAYLOAD_FORMAT` (le monter si ses champs changent).
- **Cache** (`dailyCache.ts`) : clé `jump:niveau:<identifiant du niveau>` (l'identifiant porte `JUMP_GENERATOR_VERSION`) ; la charge garde `JUMP_SIM_VERSION` et `JUMP_GENERATOR_VERSION`, comparés à la lecture. **À la relecture la preuve est rejouée** (`replayAttempt` : arrivée sans mort au temps de l'auteur, empreinte du texte, rediffusion canonique) ; si elle échoue, le cache est retiré et le niveau régénéré. **Purge** : chaque entrée garde la date de Paris de son écriture, celles d'un autre jour sont balayées à chaque lecture et écriture, et la mémoire du jour (`memory.ts`) retire aussi la clé `niveau:` d'un niveau périmé. Lectures et écritures protégées (`try/catch`, `KeyValue`) : le jeu marche sans stockage. Un niveau n'est jamais cru sur parole : ni le cache sans sa preuve rejouée, ni rien d'autre n'entre dans la sim.
- **Mesure du chargement** : `MESURE=1 npx playwright test mesure-chargement --project=chromium` (dans `apps/jump`, processeur ×1 et ×4, cache vide ou plein, avec et sans worker).

## Lot 8b — animation du personnage, essai d'élan progressif
- **L'animation du personnage est de l'affichage seul, calée sur la distance** (`apps/jump/src/look.ts`) : le cycle des pieds avance avec la distance parcourue au sol (`Look.stride`, un cycle = deux `STRIDE_TILES`, un pied se pose à chaque bruit de pas), jamais avec le temps. Pieds et yeux font partie du personnage (toujours animés) ; rebond, penché, respiration et inclinaison du dérapage suivent `FeelLevels.body` (0 avec le mouvement réduit ou « effets : aucun »). Au repos, corps + pieds remplissent exactement la boîte de collision (`?debug&hitbox`). Événement `derapage` (demi-tour au sol au-dessus de `SKID_SPEED` × la course) : le seul qui lit les commandes (`EventInputs`, celle du pas et celle d'avant). `__jump.look` avec `?debug`.

## Lot 9 — thèmes
- **(Remplacé au lot 11 : le thème est maintenant une donnée du générateur, voir « Lot 11 — thèmes jouables ».) Le thème est cosmétique et hors de l'identifiant du niveau** : `themeForDay(jour)` (`apps/jump/src/themes.ts`, pur, jamais deux jours de suite le même : jour pair tiré parmi les cinq, jour impair parmi ceux que n'ont pas ses voisins) ; `?theme=<nom>` l'impose (accents permis, permis aussi sur le site publié, gardé par les liens internes). Ni la sim, ni l'identifiant, ni `JUMP_SIM_VERSION` / `JUMP_GENERATOR_VERSION` ne le lisent. **Il le reste tant qu'aucun élément de jeu ne dépend de lui** : une glace glissante, un vent par thème… seraient des éléments de jeu, dans leur propre lot (et alors le thème entrerait dans l'identifiant et les versions). La palette du jour est celle du thème (`paletteForDay`).
- **Couleurs réservées** : les dangers (pics, scies) ont le même rouge partout (`HAZARD`), cerné de sombre (`HAZARD_OUTLINE`) ; le personnage le même jaune partout (`PLAYER`), taches et éclats compris (**depuis le lot P2, les fantômes ne sont plus jaunes** : ils ont leurs couleurs, voir « Plateforme (lot P2) »). Ressorts et arrivée : teinte à ≥ 30° des deux. Une face qui porte un pic n'a ni contour ni garniture.
- **Un décor ne ressemble jamais à un danger** (`decor.ts`) : formes rectangle, disque, demi-disque seulement (aucune pointe, aucune dent), jamais au plafond, jamais de la teinte des dangers ; **≥ `DECOR_KEEPOUT` (1,5 tuile)** d'un pic, du trajet complet d'une scie, d'un ressort, d'un fanion, du départ, de l'arrivée (boîte contre boîte) ; dans des cases vides ; **toujours derrière** tuiles, dangers et personnage (`DECOR_Z`) ; plafond `DECOR_PER_COLUMN` (0,4 par colonne, dont `DECOR_WALL_SHARE` 45 % sur les murs) ; effets réduits (ou « aucun », `?fx=off`) : la moitié (`lite`) et un seul plan de parallaxe ; mouvement réduit : parallaxe figée (`FeelLevels.decorLite`, `parallaxLite`, `parallaxMotion`). Graine du décor et des plans : identifiant du niveau + thème.
- **Seuils de contraste testés** (`apps/jump/test/themes.test.ts`, `contrast.ts`) : danger ≥ 3:1 contre le ciel, chaque plan, chaque couleur de tuile pleine, et son cerne ; personnage ≥ 3:1 contre les mêmes ; friable ≥ 2,5:1 contre le bord et le plein profond des tuiles, teinte à ≥ 40° du rouge ; plans du fond ≤ 1,6:1 contre le ciel, et leur plein ≥ 1,45:1 sous les tuiles (un fond ne doit jamais passer pour un sol). Ambiance : crête ≤ `AMBIENCE_HEADROOM` (0,6) × la crête du saut.
- **Auto-tuilage fusionné** : `tileArt.ts` / `decor.ts` / `parallax.ts` construisent des tampons purs (`artKit.ts` : positions, couleurs **linéaires** par sommet, indices) ; `scene.ts` en fait une géométrie par tronçon de `CHUNK_COLUMNS` (32) colonnes, matériaux en double face. **Jamais un maillage par tuile, rien de créé en jeu.** Le dessin d'une tuile reste dans sa case (bosses de garniture ≤ `TRIM_BUMP` au-dessus d'une face libre : `insideTiles`, testé) ; les blocs pleins écrivent toujours le pochoir des taches.
- **Tout nouveau thème** = une entrée de `THEME_NAMES` et `THEMES` (palette, `TileStyle` : coins, couleurs, garniture, motif ; décors ; 2 ou 3 plans ; ambiance dans `AMBIENCES`), puis `themes.test.ts` vert (contrastes, décor, ambiance), `e2e/themes.spec.ts` (il boucle sur la liste), une capture (`CAPTURES=1 npx playwright test themes --project=chromium` dans `apps/jump`) et la mesure `MESURE=1 npx playwright test mesure-themes --project=chromium` (< 16,7 ms à ×4). ## Tests e2e et CI (lots 15b et 17)
Deux erreurs de CI se sont répétées (lot I7 : plein écran sur WebKit ; lot 15 : « Prêt… » et secousse de la mort) : un test qui échoue sur Firefox ou WebKit n'apparaît qu'à la CI complète (`main`, nuit, lot de mise en production). Détail : `docs/jump/lots/lot-15b-ci-webkit.md`.
- **Un lot Jump s'arrête quand la CI de sa PR est verte** ; la CI complète (Firefox, WebKit) est contrôlée et réparée par le lot de mise en production (`docs/orchestration.md` § 12). Un lot qui touche la simulation, l'horloge, le générateur ou des tests e2e teste en local ce que la CI de PR lancera (`npm run verifier`) et **ne pousse pas de commit « à vide »** pour avoir les trois navigateurs (le mot-clé `[ci complet]` n'existe plus, lot R10). Une différence entre navigateurs (WebKit : plein écran, secousse…) se traite par la capacité (`hasWebGL`, `pleinEcranDisponible`), pas par le nom du navigateur.
- **Étiquette de PR (lot 21)** : si le nom de la branche ne contient pas « jump », le lot **pose lui-même l'étiquette `jeu:jump`** sur sa PR (sinon la CI la traite comme une PR de la plateforme : job `zones`, `scripts/zones-jeu.mjs`).
- **Un test e2e lit un état dans la même évaluation que le pas qui le produit**, jamais après une image en temps réel : entre deux `page.evaluate`, le jeu dessine (la secousse de la mort s'use à chaque image, l'horloge d'un « Prêt… » avance) ; un navigateur plus lent laisse passer des images, et le test devient une course sur une durée. Un état que seul le dessin pose (`scene.clockFade`…) s'**attend** (`waitForFunction` sur l'état), il ne se lit pas après un délai.
- **Une capacité absente se teste, jamais le nom du navigateur** (`hasWebGL`, `pleinEcranDisponible` : `test.skip` motivé sur la capacité).
- **Ce qui est long se calcule avant d'ouvrir la page** (un essai fictif, un niveau du jour) : le jeu tourne en temps réel dès qu'il est prêt, et le temps passé à chercher décalerait une rediffusion jouée ensuite.
- Un nouveau spec s'ajoute à `e2e/durees.json` **et à `e2e/zones.json` de la racine** (ses zones : ce que sa PR doit lancer).

## Annonce des éléments à horloge (lot 18)
README : `docs/jump/lots/lot-18-lisibilite.md` ; rythme de la nuit (générateur g13) : `packages/jump-sim/CLAUDE.md`, « Rythme de la nuit (lot 18) ». Retour de Nathan : les blocs de la nuit changent trop vite et l'indicateur arrive presque en même temps que la disparition ; les feuilles des rafales s'arrêtent net.
- **Principe (valable pour tout élément à horloge, présent et à venir)** : il **annonce chacun de ses changements d'état**, assez tôt, par **un signe continu et simple** (une jauge qui descend ou monte, une vitesse qui décroît). L'annonce se calcule à partir de la fonction de l'horloge (`blinkPhase`, `gustPhase`, `announce.ts`, pur) : elle connaît l'avenir de façon exacte. **Interdits** : tout clignotement rapide — **rien au-dessus de 3 Hz** (`FLICKER_MAX_HZ`), par lisibilité et pour la sécurité des personnes photosensibles ; **le rouge des dangers** (couleurs neutres de la charte ou celles du bloc, jamais `HAZARD`). **L'affichage ne ment jamais** : il ne montre jamais un état que la simulation n'a pas (un bloc plein reste cerné d'un trait plein et sa face opaque jusqu'au pas où il disparaît ; un bloc absent n'a qu'un contour pointillé et, au plus, un remplissage translucide jusqu'au pas où il revient ; les feuilles sont à l'arrêt exactement quand la rafale cesse). Une nouvelle mécanique à horloge ajoute son annonce **et** ses tests (jauge pleine hors annonce, vide / pleine pile au pas du changement, aucun va-et-vient, carnage).
- **Durées** (`ANNOUNCE` dans `announce.ts`, en secondes, réglables dans `?debug&tune`, section « Caméra et secousses », quatre curseurs mémorisés dans `jump:camera` comme les autres) : disparition d'un clignotant **0,6 s** (`vanish`), réapparition **0,4 s** (`appear`), début d'une rafale **0,4 s** (`gustLead`), fin d'une rafale **0,4 s** (`gustTail`). **Si une phase est plus courte que l'annonce, l'annonce couvre au plus la moitié de la phase** (`announceWindow`). Le carnage (35 %, lot 17) s'applique toujours.
- **Nuit, blocs clignotants** (`blocks.ts`, `dynamicArt.ts`) : pendant les dernières 0,6 s de la phase présente, la **face se vide comme une jauge qui descend** (la face part du bas du bloc, sa hauteur est le niveau ; un trait clair marque le niveau) et finit **vide pile au pas de la disparition** (`blinkGauge` : `pas restants / (fenêtre + 1)`, 1 hors annonce : l'annonce compte exactement 72 pas, tous strictement entre 0 et 1) ; le contour reste plein et franc. **Absent, le bloc reste en contour pointillé discret** (cinq tirets par côté) ; pendant les 0,4 s avant son retour, le contour **se remplit** (remplissage translucide, contour qui se renforce) et la jauge est **pleine pile au pas de la réapparition**. Un bloc qui attend la sortie du personnage garde le contour épais sans face. Les blocs alternés du néon ne changent pas. **Retiré** : l'ancien vacillement (la face qui clignotait de 7 à 16 Hz) et son repli « mouvement réduit » ; la jauge est la même avec ou sans mouvement réduit (rien ne clignote). `BlockLook` = `{ solid, fill, waiting }` (plus de `wobble`) ; l'événement `blocVacille` (deux étincelles) part au début de l'annonce de la disparition.
- **Forêt, rafales** (`wind.ts`, `windArt.ts`) : les feuilles **frémissent** 0,4 s avant le début (amplitude croissante, 2,9 Hz : `WIND_TREMBLE_RAD`), vont à **pleine vitesse** pendant la rafale, **ralentissent pendant les 0,4 s qui précèdent la fin** (vitesse proportionnelle aux pas restants) et sont **à l'arrêt exactement quand la rafale cesse** : `WindLook` = `{ blowing, announce (frémissement), flow (vitesse 0 à 1), intensity }`, `flowStep(zone, flow, dt)`. Hors rafale il n'y a plus de dérive lente (`WIND_FLOAT` retirée) : l'ondulation et la rotation des feuilles s'arrêtent avec le flux (`swing` cumulé au rythme de `flow`). **Les flèches du mouvement réduit suivent la même logique** (`arrowOpacity(look)` : éteintes, elles s'éclaircissent avant le début, allumées pendant la rafale, s'éteignent avant la fin). **La force du vent dans la simulation ne change pas** (`windBlows` reste un interrupteur ; l'annonce n'est qu'un dessin).
- **Outils** (`?debug`) : `__jump.blocks` — `fills` (hauteur de face dessinée de chaque clignotant), `simFills` (le niveau de la simulation), `draining`, `refilling`, `dotted`, `levelLine` (retirés : `wobbling`, `wobbleOpacity`) ; `__jump.wind` — `flow`, `intensity`, `announce`.
- **Tests** : `test/annonce.test.ts` (jauge pleine hors annonce, vide pile à la disparition, pleine pile à la réapparition, durées, moitié de phase ; feuilles à l'arrêt exactement à la fin de la rafale, ralenti monotone ; flèches ; **aucun clignotement au-dessus de 3 Hz** sur les séries de la jauge, des opacités dessinées, de la vitesse et des flèches, et garde-fou sur les sources ; curseurs de `?debug&tune`) ; `blocks.test.ts` et `vent.test.ts` adaptés ; e2e `nuit-neon.spec.ts` (jauge dessinée = jauge de la simulation, identique avec ou sans mouvement réduit, contour pointillé), `foret.spec.ts` (ralenti et arrêt de la rafale dans la vraie page, flèches).

- **Aspect** (`src/platformArt.ts`, pur côté tampons, un groupe par plateforme, rien de créé en jeu) : une **dalle crème cernée d'encre** (`PLATFORM_LOOK` : `--dj-papier`, `--dj-encre`, couleurs neutres de la charte) — **jamais rouge** (dangers), **jamais jaune** (personnage), distincte des blocs pleins (qui sont colorés et pleins) —, lisible à 3:1 (face ou cerne) sur le ciel et chaque plan de chaque thème ; **des chevrons** posés sur la dalle dans le sens du mouvement ; **le trajet en pointillés neutres** (deux lignes, crème et encre, qui alternent) et l'empreinte de chaque extrémité. Le dessin est interpolé entre deux pas comme les scies (`update(avant, après, alpha, fade)`), la position vient de `platformAt` de la simulation, jamais recalculée à part.
- **Le ralenti annonce le demi-tour** (`platformLook`, `platformPeak`, `announce.ts`, pur) : la vitesse affichée est la vitesse **de la simulation** en part de sa pointe (0 à 1) ; les chevrons **s'estompent avec elle** (presque éteints aux extrémités, pleins au milieu) et **se retournent au demi-cycle**. Même principe que le lot 18 : un signe continu, jamais un clignotement (la série de vitesse ne varie jamais de plus de 15 % de la pointe d'un pas à l'autre, jamais plus de 3 pics par seconde : `FLICKER_MAX_HZ`), identique avec ou sans mouvement réduit. L'affichage ne ment pas : la dalle est dessinée exactement où la simulation la met.
- **Carnage** : comme les autres éléments à horloge, **35 % d'opacité** (`scene.clockFade`, `CARNAGE.clockOpacity`) ; la dalle est faite de **pièces qui ne se recouvrent pas** (face, cerne en anneau, chevrons, trajet) pour que l'estompage ne s'additionne pas, opaque et sans mélange hors carnage. Un trait ou une pointe qui apparaîtrait ne ferait pas passer la dalle pour un danger.
- **Outils** : `?modules` — l'étiquette **« plateforme mobile »** (`TAG_LABELS.plateforme`) filtre au moins six morceaux, chacun ouvert dans la galerie avec sa plateforme ; les intentions des morceaux viennent de `public/outils/intentions.json` (lues à la demande par la galerie, plus dans le catalogue embarqué : budget de poids) ; `?semaine` — la miniature dessine les plateformes en crème (largeur, extrémités : `semaineDayOf(...).platforms`), `&generateur=14` montre la même semaine telle que l'aurait faite g14 (recalculée par la référence v4 du générateur, aucun fichier) ; `?debug` — `__jump.platforms` (`count`, `x`/`y` dessinés en tuiles, `speed`, `dir`, `opacity`, la simulation `sim`, `phases`, `ride` : la plateforme qui porte le personnage, −1 sinon). `?debug&hitbox` n'ajoute rien : la dalle est déjà son propre contour.
- **Tests** : `test/plateformes.test.ts` (couleurs et contrastes, ralenti, aucun clignotement, dessin posé où la simulation la met, carnage 35 %, trajet neutre, galerie, miniature) ; e2e `plateformes.spec.ts` (dalle dessinée = simulation et chevrons dans `?module=chaland`, filtre de la galerie, **niveau du jour v5 : la preuve de l'auteur, jouée pas à pas dans la page, est portée par une plateforme sans mourir**) ; ligne `plateformes.spec.ts` dans `e2e/durees.json`. Captures du README : `docs/jump/lots/img/lot-20-*.png`.

## Économie des lots (lot 21)
Nathan veut des CI de PR courtes et moins de jetons par lot : un lot Jump s'y tient.
- **Mesures sur 120 dates** (`measure:jump`, `variete:jump`) ; **365 seulement si le lot porte sur la variété**.
- **La référence avant / après se lit dans le README du lot précédent** : on ne relance pas l'ancien générateur (sauf `--generateur=<n>` quand un lot garde une référence).
- **Outils de morceaux avec `--only=<id>`** sur les morceaux touchés (sauf `solve:modules`, voir `packages/jump-sim/CLAUDE.md`, « Rythme de la nuit »).
- **Sorties de commandes courtes** (`| tail`, `| grep`) ; **pas de relecture complète des gros fichiers de données** (`catalog.ts`, `phases.json`, `solutions.json`, golden) : on les cherche, on ne les lit pas.
- **README de lot court** : ce qui a changé, ce qui reste à décider, le scénario en 2 clics. Des tableaux seulement quand ils portent une décision.

## Catalogue et générateur à la demande (lot 21)
README : `docs/jump/lots/lot-21-poids-fictifs.md`. **Le catalogue des morceaux, le générateur et le solveur de la preuve ne sont pas dans le premier chargement.**
- **Règle** : avec un niveau figé (`public/levels/AAAA-MM-JJ.json`) ou un cache valide, la page ne charge ni le catalogue ni le générateur. Ils ne sont chargés qu'**à la demande** : par le **fil de travail** (`dailyWorker.ts`) quand le fichier figé manque (jour pas encore figé, aperçu, `?seed=` d'un jour non figé), par le **repli sur le fil principal** (`import("./dailyGen")`, `dailyLoader.ts`) si le fil échoue, par `?module=` (`modulesInfo.ts`, `main.ts`), `?modules` (galerie), `?semaine` (outil) et `?carnage=demo` (`demoFictifs.ts`). `dailyGen.ts` est **le seul fichier de la page qui importe `dailyLevel`** ; `dailyWork.ts` (charge transportable, cache) ne l'importe plus.
- **Ce qui le permet** (à ne pas défaire) : `packages/jump-sim/package.json` `"sideEffects": false` ; les deux seuls appels de haut niveau de `modules.ts` (`MODULES`, `MODULE_SOLUTIONS`) sont annotés `/* @__PURE__ */` ; `textHash` (`texthash.ts`), `MODULE_ENTRIES` et `PALIER_LENGTH` (`constants.ts`), le numéro et l'identifiant du niveau, les médailles (`jours.ts`) vivent dans de petits fichiers que `modules.ts` et `daily.ts` réexportent ; `urlOptions.ts` lit l'**index léger** `moduleIndex.ts` (identifiant et nombre de variantes de chaque morceau, **écrit par `solve:modules`** avec le catalogue, test dans `modules.test.ts`). **Une importation du jeu qui ramène `modules.ts`, `catalog.ts` ou `daily.ts` dans le premier chargement fait échouer `e2e/poids.spec.ts`** (« le premier chargement ne contient ni le catalogue ni le générateur »).
- **Un seul exemplaire du générateur** : le fil de travail est une **entrée de la même construction** (`vite.config.ts`, `filDuGenerateur`, module virtuel `virtual:jump-fil-generateur`, `workerNavigateur.ts`) et non un « worker Vite » construit à part (qui recopiait 56 ko compressés) : il partage ses fichiers avec le repli et avec la page. Son fichier garde le nom `dailyWorker-<empreinte>.js` (`chargement.spec.ts` l'intercepte). Contrepartie mesurée : un jour sans fichier figé charge ses fichiers l'un après l'autre (le fil importe le générateur, qui importe le catalogue) — plus lent sur un réseau mobile lent (README du lot).
- **`?debug`** : une ligne **`origine`** de la surimpression (`originLine`, `dailyInfo.ts`) dit d'où vient le niveau et si le catalogue a été chargé : « fichier figé, catalogue non chargé », « cache, catalogue non chargé », « généré (worker), catalogue chargé (worker) », « généré (fil principal), catalogue chargé » ; `__jump.daily.load.catalog` (`non`, `worker`, `principal`). Mesure : `MESURE=1 npx playwright test mesure-lot-21 --project=chromium` (`RESEAU=1` : réseau mobile lent).
- **Joueurs fictifs** : voir `packages/jump-sim/CLAUDE.md`, « Joueurs fictifs qui reprennent bien (lot 21) » ; le carnage de démonstration d'un jour (`?carnage=demo`) les utilise.

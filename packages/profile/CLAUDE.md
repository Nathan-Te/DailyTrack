# `packages/profile` (`@cdj/profile`) : le profil commun à tous les jeux, côté client

Chargé quand on lit un fichier de `packages/profile`. **Zone partagée** (un seul propriétaire à la fois ; un lot n'y touche que si son prompt le dit). Créé au lot P0 de la plateforme (`docs/plateforme/lots/lot-P0-socle.md`) en extrayant d'`apps/web` (lot 30 de DailyTrack) le code d'identité, **sans le changer**. Vision : `docs/plateforme/seed-phase-2.md` (ne pas modifier). Règles du serveur et de la plateforme : `apps/api/CLAUDE.md` (« Plateforme (lot P0) », « Profil (lot 30) »).

## Ce que contient le module
- `identity.ts` — clés de la plateforme (`PLATFORM_PREFIX` = `cdj:`, `PLAYER_KEY` `cdj:player`, `NAME_KEY` `cdj:name`, `NEXT_KEY` `cdj:player:next`, `NOTICE_PREFIX` `cdj:notice:`, lot P4 : `IDENTITY_REV_KEY` `cdj:identite:rev`, `IDENTITY_CODE_REV_KEY` `cdj:identite:code`), `noteIdentityChange` / `identityRevisionSeen` / `readIdentityRevision` (lot P4, ci-dessous), `createIdentity(stockage)` (lecture et création de l'identifiant secret de 128 bits, pseudo, « Changer mon code » en cours), `readIdentity` (existe-t-elle, et son pseudo, **sans rien créer** : `__jump.profile`), `writeIdentity` (code chargé), `readPlayerId`, `isValidName` / `normalizeName` (miroir de `cleanName` du serveur), `keysWith`.
- `transfer.ts` — code de transfert **`CDJ2.<identifiant : 32 hexadécimaux>.<CRC-32 sur 8 hexadécimaux>`** (46 caractères) : `encodeTransfer`, `decodeTransfer(code, legacy?)`, `crc32`. Les anciens codes `CDJ1` (records de DailyTrack) se lisent dans DailyTrack (`apps/web/src/transfer.ts`), passés en `legacy`.
- `client.ts` — `call` (délai de 8 s, erreurs traduites, corps vide = panne réseau, `suggestions` de pseudo gardées), `ProfileClient` : `GET /api/me`, `GET /api/name`, `PUT /api/player`, `POST /api/me/code` ; `MeProfile`, `ApiResult`. L'identifiant secret voyage dans l'en-tête `X-Player-Id`.
- `sync.ts` — `ProfileSync<M, S, P>` (au plus une synchronisation par 30 s, une seule à la fois, adoption de `cdj:player:next` après un « Changer mon code » dont la réponse s'est perdue) ; la fusion est **celle du jeu** (`merge`), la part commune est `mergeName` (le pseudo du serveur gagne). **Lot P2 : générique sur le profil du jeu** (`P extends SyncedProfile` = `{ name, renameRequired, stats }`, défaut `MeProfile`, celui de DailyTrack, dont le comportement et les types ne changent pas) : un jeu lui donne **son** `me` (DailyJump : `GET /api/jump/me`, `apps/jump/src/jumpProfile.ts`) et **sa** fusion. `SyncView` (ce que `Profile` demande de la synchronisation) ne lit plus que `state.known` : n'importe quel `ProfileSync` de jeu convient.
- `langue.ts` (lot I1) — la langue commune de la plateforme (rubrique « Langue commune (lot I1) »).
- `profile.ts` — `Profile` : `rename` (propriété du premier, suggestions, hors ligne), `changeCode` (rotation et révocation), `NAME_TAKEN_MESSAGE`.

## Invariants
- **Mêmes clés, même format, mêmes requêtes que DailyTrack avant le lot P0** : les clés `cdj:*` sont celles de la plateforme ; le format du code ne change pas ; les chemins, en-têtes et corps des requêtes non plus. **Le comportement de DailyTrack reste identique** (ses façades `identity.ts`, `transfer.ts`, `api.ts`, `profileSync.ts`, `online.ts` délèguent ici).
- **Aucun accès direct au stockage ni au réseau** : le stockage est injecté (le `gameStorage()` de chaque jeu ; les deux jeux partagent l'origine — `playdujour.com`, `/track/` et `/jump/` — donc la même identité ; la recette et chaque aperçu sont d'autres origines depuis le lot R4), `fetch` est injectable. Ni `localStorage`, ni `document`, ni `window`, ni `location` (test `purete.test.ts`).
- **Aucune logique de jeu** : le module n'importe aucun paquet (ni `@cdj/sim`, ni `@cdj/jump-sim`) ; les records, médailles et la fusion des temps sont au jeu.
- Un pseudo appartient à son premier propriétaire (serveur) ; le code se garde comme un mot de passe ; un code révoqué rend `410 code_revoked`.
- Textes en français. Une clé, un format ou une requête qui change = les deux jeux et le serveur ensemble, avec une migration.

## Ce que le module offre à un jeu pour son profil (lot P2)
- Lire l'identité **sans la créer** (`readIdentity`, `readPlayerId`) ; la créer au premier envoi (`createIdentity(...).getPlayerId()`) ; écrire celle d'un code chargé (`writeIdentity` : identifiant, pseudo, « Changer mon code » en cours et avis oubliés) — le jeu y ajoute l'effacement de **son** cache de l'ancienne identité.
- Le code `CDJ2` (`encodeTransfer`, `decodeTransfer`), le pseudo (`Profile.rename` : propriété du premier, suggestions, hors ligne) et la rotation (`Profile.changeCode`).
- La synchronisation (`ProfileSync<M, S, P>`) avec le profil **du jeu** (`/api/<jeu>/me`) et sa fusion « le meilleur gagne » ; un code révoqué (410) donne `status: "revoked"` sans rien effacer.
- Le texte de l'interface (« Ton profil est le même dans tous les jeux… ») et la mise en page restent à chaque jeu (DOM interdit ici).

## Révision d'identité de la plateforme (lot P4)
- **Le compteur** (`identity.ts`) : `cdj:identite:rev` (révision) et `cdj:identite:code` (révision du dernier **code chargé**). **Tout jeu qui change l'identité l'avance** : la première création de l'identifiant et une rotation (« Changer mon code », adoption de `cdj:player:next`) le font **ici**, dans `createIdentity` ; un **code chargé**, c'est **le jeu qui le charge** qui appelle `noteIdentityChange(stockage, "code", <sa clé vue>)` (après avoir vidé son cache ; `writeIdentity` n'avance rien, pour qu'un jeu qui réagit au démarrage ne relance pas les autres).
- **Tout jeu le lit au démarrage**, avant de lire son cache : `identityRevisionSeen(stockage, <sa clé vue>)` rend `"code"` si un code a été chargé **ailleurs** depuis sa dernière visite — le jeu vide alors son cache de l'ancienne identité exactement comme quand le code est chargé chez lui (DailyTrack : `applyIdentity` ; DailyJump : rangs connus et jours passés) — sinon `"aucun"` (première visite depuis le lot P4, rotation, création : même profil, rien n'est effacé). La révision est notée comme vue dans les deux cas. Clés vues : `cdj:identite:vue` (DailyTrack), `jump:identite:vue` (DailyJump) ; un nouveau jeu prend `<jeu>:identite:vue`.
- Tests : `packages/profile/test/revision.test.ts` (paliers, aucun aller-retour, création et rotation, stockage refusé) ; dans les jeux : `apps/web/test/revisionIdentite.test.ts`, `apps/jump/test/revisionIdentite.test.ts`, e2e `apps/web/e2e/identite-plateforme.spec.ts` (code chargé dans DailyJump, puis DailyTrack ouvert).

## Plus d'import par l'adresse (lot R5)
- **Le code de transfert est le seul moyen de déplacer un profil** (Réglages › Profil : « Copier mon code », puis « Charger un code » ailleurs : une action volontaire, profil lu sur le serveur et confirmé). L'import par fragment du lot R4 (`migration.ts`, `#dujour=…`) est **retiré**, avec ses tests et ses appels dans les deux jeux : il n'avait plus d'usage (plus de redirection depuis GitHub Pages) et un lien piégé pouvait implanter l'identité d'un autre chez un joueur qui n'en avait pas encore.
- **Règle : rien dans l'adresse d'une page (paramètre, fragment) ne crée, n'importe ni ne remplace une identité.** **Seule exception (lot I2), hors production** : `/?demo=joueur` du portail, sur la recette et les aperçus, installe le joueur de démonstration connu de la recette (jamais un autre), avec confirmation s'il y a déjà une identité ; la construction de production n'en contient rien (`apps/portail/CLAUDE.md`). Tests : `apps/web/e2e/domaine.spec.ts` (un lien `#dujour=…` n'a aucun effet) et `apps/portail/test/mentions.test.ts` (plus aucune trace de l'import dans le module, les jeux, le portail et les scripts).

## Le profil commun du portail (lot I2)
- Le portail (`apps/portail/src/profil.ts`, page `/profil/`) se sert du module **sans fonction nouvelle** : `readIdentity` / `readPlayerId` (lire sans créer), `encodeTransfer` / `decodeTransfer` (le code), `ProfileClient.rename` (le pseudo, mêmes refus), `call` (sa lecture `GET /api/portail/profil`), `writeIdentity` puis `noteIdentityChange(stockage, "code")` (un code chargé : sans clé vue, le portail n'ayant pas de cache ; les jeux vident le leur à leur prochain démarrage). Même stockage `cdj:*`, mêmes routes que Réglages › Profil des jeux.

## Langue commune (lot I1)
- `langue.ts` : **`LANGUE_KEY` = `cdj:langue`** (`fr` ou `en`), **la même pour le portail et tous les jeux** (même origine, même stockage). `detecterLangue(navigator.languages)` : la **première** langue du navigateur ; tout ce qui commence par `fr` → français, sinon anglais (liste vide → anglais). `lireLangue(stockage, navigator.languages)` → `{ langue, choisie }` : le choix mémorisé s'il est valide, sinon la détection (**rien n'est écrit** tant que le joueur n'a pas choisi : la détection suit son navigateur). `ecrireLangue(stockage, langue)` : un choix explicite (choix de langue du portail ; plus tard, des jeux). Ne lève jamais ; `navigator` est passé par l'appelant (pureté).
- Les jeux n'affichent encore rien selon la langue (lots I4, I5) : ils liront la langue par `lireLangue` sur leur `gameStorage()`, sans toucher à la détection. La page des mentions décrit cette donnée (règle de fidélité). Tests : `test/langue.test.ts` ; e2e `apps/web/e2e/portail.spec.ts`.
